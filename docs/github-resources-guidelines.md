# 首页 GitHub 项目精选规范

适用位置：首页「工具与工作流」`#resources`。本文件是该模块选品、文案与上下架的维护依据，由 `CONVENTIONS.md` 引用。

## 1. 展示目的与数量

用具体项目呈现作者怎样把对 AI 的理解落实为产品，并把实践整理成可复用的方法。同时帮助 AI 从业者、产品同行和知识工作者在短时间内看懂「对我有什么用」和「怎么开始」。

每项必须同时具备 **读者使用价值** 与 **作者代表性**。代表性要落到项目中的具体流程、产品取舍或协作方法，不靠「有产品思维」「系统化」等自我评价，也不能把文档或原型推导为实际用户效果。

- 默认精选 3 项，通常保持 2–4 项；不足时可以少放，不为凑数量降低标准。
- GitHub 新增或公开仓库后，先进入候选评估，不自动同步到首页。
- 按读者理解顺序、可用程度与代表性排序；不同项目应补充不同的实践维度，同类项目优先保留最有用、入口最完整的一项。
- 其他项目通过模块唯一的「更多 GitHub 项目」入口发现。首页不维护第二份完整仓库目录。

## 2. 入选条件

每个项目都应能回答以下问题：

| 判断 | 入选所需信息 |
| --- | --- |
| 对谁有用？ | 明确的读者场景，例如整理资料、让 AI 使用本地文件、持续跟进信息 |
| 能带来什么变化？ | 一个具体收益，能用普通语言说明；不靠技术栈、仓库名或代码量解释价值 |
| 别人能复用吗？ | 有清晰的起步步骤和所需环境，不依赖作者的私人账号、内部数据或本机绝对路径才能理解和使用 |
| 是否有可核对的依据？ | 公开文档、实际输出示例或验证记录能支撑主要能力；限制和未完成项有明确说明 |
| 能体现作者的什么？ | 指明一项由项目支撑的能力或取舍，例如完整资料流程、受控文件访问、协作与续接方法 |
| 为什么需要一个首页位置？ | 相比已展示项目有不同的任务或代表性增量；能解释新增或替换的理由 |

纯备份、无新增价值的 fork、零散脚本、未完成实验、只适合作者个人的监测配置，以及功能高度重复的仓库，通常不进入首页。被暂缓的项目可在用途或使用路径改善后重新评估。

## 3. 可用状态

- **可复用**：有公开的使用路径、适用条件和代表性结果；可按实际类型标注「本地工具」「AI 工作流」。
- **试用**：核心能力和使用步骤已有依据，但仍有集成或真实环境验收未完成。状态保留在维护记录和入口文档中，首页不统一加「试用版」标签；不写「开箱即用」「稳定可用」等成熟度承诺。
- **暂缓**：缺少可执行路径、主要能力只有设想、依赖私人环境或无法核对限制，先补齐项目本身。
- **撤下**：主要入口失效、关键能力无法继续使用、维护状态不明、存在更合适的替代项目，或已偏离读者需求时，从首页撤下并记录原因。撤下首页不等于删除或关闭 GitHub 仓库。

较窄的受众和较高的配置门槛会降低首页优先级，但不代表项目没有价值。试用项目优先保留最有代表性的；同时保留多项时，须说明它们各自不同的价值，并在维护记录与使用说明中保留状态和使用条件。会直接影响能否使用的关键限制应在入口文档起步步骤之前说明。

## 4. 文案写法

访客首先看到使用价值，短标签说明用途或使用入口。操作系统、依赖版本和发布状态由入口使用说明承接；首页不把技术条件当作每项的固定标签。

| 字段 | 规范 |
| --- | --- |
| 模块导语 | 1–2 句连接作者的实践方向与读者用途；不复述「使用说明和代码在 GitHub」，不堆能力标签 |
| 展示名称 | 使用直观的产品名，避免直接使用难懂的仓库 slug；沿用已确定的项目命名 |
| 一句话介绍 | 约 35–60 个汉字、1–2 句；按「场景或收益 → 具体能力」组织，一项只讲一个核心价值 |
| 用途标签 | 一行概括场景或使用入口，例如「内容采集 · 资料整理」「ChatGPT 网页接入」「长期协作 · 经验沉淀」；Windows、Python 版本与试用状态放使用说明，不用标签暗示未经验证的全平台兼容 |
| 行动链接 | 默认统一为「了解与使用」，使用项目名补全 `aria-label` |

写法示例：

- 功能描述：「采集文章和视频，保存内容、提取文字，支持本地查阅和 MCP 读取。」
- 面向读者的表达：「把文章和视频变成可复用的资料。保存内容、提取文字，方便自己查阅，也方便 AI 读取。」

文案必须保留项目的主要流程，不能为易懂而改变定位。资料库从用户主动提交链接开始，不写成自动导入收藏夹；文件助手目前面向 ChatGPT，不泛化成任意 AI 即连即用；Harness 提供规则、模板与续接入口，不写成自动记忆、自动执行或同步服务。原型和历史快照保留相应语义，不用「日常在用」「实时」代替实际核对。

有对应博客时，先读正文理解作者为何做它，再用公开仓库核对当前可交付范围。Harness 的介绍应表达长期协作积累与可自定义的起点，不能把个人完整版的全部机制写成公开包已实现的功能。文件助手先说明网页版远程取用本机资料；关于额度，只按实际 Chat / Work 模式与官方规则表述，不把「网页版」等同于「不消耗 Work 额度」。

产品和 PR 视角负责说清值得使用的理由。不能添加没有证据的效率数字、用户规模、排名、收益或成熟度；避免「全平台」「全自动」「万能」「无需配置」等越过实际边界的承诺。「资料保存在本地」也不能推导出「资料永不传给 AI」。

## 5. 链接与展示

- 每项只保留 **一个** 行动链接，默认直达能同时解释用途和起步方式的 README / 使用说明。标题保持普通文本，不再加一组重复仓库链接。
- 优先使用访客能看懂的入口：已有可靠在线产品可直达产品；本地工具和工作流通常指向说明页。仅在确有对应入口时使用「在线体验」「下载」等动作词。
- 原始代码与仓库可通过 GitHub 文档导航继续访问；模块全局保留一个「更多 GitHub 项目」链接。
- 使用稳定的 HTTPS URL，保留有意义的文档锚点；新标签页统一 `target="_blank" rel="noopener"`。
- 延续文字条目、细分隔线和清晰层级，不添加 Stars、下载量、活动热度等自动变化的装饰性指标。
- 条目字号与首页文章、原型及案例共用 `--home-item-*`：标题 18px、简介 16px、用途标签 13px（按 16px 根字号换算）；行高和适用范围见 `CONVENTIONS.md` 的「首页条目字号层级」，不为 GitHub 模块单独放大同级文字。
- 保留深浅主题、可见键盘焦点、至少 44px 点击高度，以及手机端换行与无横向溢出。

## 6. 新项目维护流程

1. 阅读项目当前公开说明，记录核对日期、入口、核心能力和限制。明确哪些来自文档，哪些已实际试用；不能把 README 写有功能当成端到端验收。
2. 按第 2 节逐项给出入选 / 暂缓理由，与当前首页项目比较，决定是新增、替换还是保留在 GitHub。已有授权下按此判断完成本地更新，不额外建立逐项审批流程。
3. 确定「名称、读者场景、核心收益、代表性及依据、使用条件、状态、唯一入口」七项信息，并据此写文案。代表性记入维护文档，页面用具体用途和产品取舍呈现。
4. 只在 `index.html` 的 `.resource-item` 维护公开展示内容；少量精选继续使用静态 HTML，不增加自动拉取 GitHub 仓库的机制。
5. 同步 README 的当前入口说明，将选择理由、证据链接和核对日期记录在本次设计 / 维护文档中。旧验收记录保留其当时的版本含义，不改写历史检查结果。
6. 核对链接和能力表述，运行受影响的回归与公开产物检查。视觉变更按 CONVENTIONS 检查桌面 / 手机、深浅主题和键盘状态；纯文案、数据或链接替换按其截图例外执行，记录实际完成的检查。不要让回归测试固定某一期项目数量。
7. 提交、推送和发布继续按仓库现有规则执行。本规范不自动触发远端修改或发布。

新增候选项目、现有项目用途变化、入口迁移、停止维护或读者反馈无法使用时，触发重新评估。无需为了保持栏目“更新频率”增加项目。

## 7. 维护记录模板

```text
项目 / 仓库：
核对日期与公开入口：
读者场景和核心收益：
作者代表性与对应证据：
使用条件与状态：
主要能力的依据 / 未验证部分：
与当前精选的区别：
决定：入选 / 替换 / 暂缓 / 撤下
决定理由与被替换项目（如有）：
首页名称、介绍和唯一链接：
本地检查 / 提交 / 发布状态：
```
