# 首页 GitHub 工具与工作流模块：调研与设计建议

日期：2026-10-09
状态：已完成首轮本地实施；根据用户截图反馈，第二轮精简为三个项目、每项一个入口，并补充长期精选规范。本文保留前两轮历史记录；2026-10-11 起的当前选择与表达见 [首页项目表达与精选调整](2026-10-11-homepage-project-positioning.md)。尚未提交、推送或部署。

## 1. 建议与目标

建议撤下首页独立的「我的判断」区块，让「思考碎片」继续承载作者观点，由新增的「工具与工作流」接替原区块的位置。

目标：读者浏览完文章后，能快速找到作者公开在 GitHub 上的实用项目，了解它解决什么问题、使用门槛和下一步入口。

不为维持首页模块而额外建立定期写观点的任务。文章有了新的证据、经验或修正，再通过新文章和精选表达；项目用法发生变化时，再更新项目介绍。

## 3. 「我的判断」的取舍

| 方案 | 收益 | 维护成本与取舍 | 建议 |
| --- | --- | --- | --- |
| 撤下独立区块，以文章为观点入口 | 首页精简，观点和论证保留在一起 | 减少一层快速观点摘要 | 推荐 |
| 保留并定期更新 | 访客能快速扫描立场 | 需要持续复核日期、证据、适用边界，以及与文章的一致性 | 仅在作者愿意长期编辑该栏目时采用 |
| 从精选文章自动摘取观点 | 无须重复写内容 | 与紧邻的文章标题和摘要重复，也可能丢失论证条件 | 首版不采用 |

推荐的内容保留方式：

- 四条已有文章支撑的判断，继续保留对应历史文章；撤下模块不触发重写或重新生成文章。
- 「金融 AI 的近期形态」及两组补充内容，在实施前保留带日期的内容快照，作为将来写作素材；发布成新文章前重新核验事实。
- 只有长期稳定、能代表作者方法的表述，才考虑压缩进个人介绍。带期限的预测和行业进度判断不搬进常驻自我介绍。

## 4. 推荐的信息结构

```text
个人介绍
  ↓
思考碎片            阅读我的分析：精选一篇 + 最近三篇
  ↓
工具与工作流        找到能拿去使用的工具、提示词和工作流
  ↓

  ↓

  ↓

```

「原型与研究」是对原「作品 & 工具」标题的改名，帮助区分用途；其现有八个入口保留。

导航建议：文章 / 工具 / 作品 / 案例 / 联系。新模块使用稳定锚点 `#resources`。旧 `#about` 的兼容落点应在实施时保留，避免已有分享链接失效；默认导向个人介绍，而不是无关的资源列表。

博客归档首版仍保持文章列表。可在侧栏的站点返回入口旁补充「工具与工作流」文字链接，并为移动端提供等价入口；该链接属于站点导航，不混进技术、产品、商业、行业、实践这些文章分类。

首批内容的事实边界：

- AI 本地文件助手是公开源码和使用文档入口；README 明确尚非正式 Release，按钮不写「下载正式版」。Windows 图形界面版与 Node 只读版的操作范围不同，主要入口明确进入 Windows 版说明。
- 多平台资料库需要本地环境；平台登录、访问和工具条件会影响具体采集结果，简介不承诺所有平台均可完整保存。
- 两个 AI 工作流仓库提供指令与配置，访客需要在自己的执行平台使用；网页上的链接不代表已经为访客启用自动化。
- 私有或尚无公开使用入口的项目不纳入本轮精选。
- 个人网站源码可放模块末尾「更多 GitHub 项目」或全站页脚；其余历史/试验仓库无需为凑数量进入首页。

## 6. 布局与交互

采用轻量文字项目列表。桌面端左侧为标题、导语及「更多 GitHub 项目」，右侧为四条项目；移动端标题在上，四条项目单列排列。

每条条目的内容顺序：

```text
AI 本地文件助手                         本地运行 · Windows
让 AI 访问你授权的本地资料，默认只读，文件操作可逐项审批。
安装与使用 ↗     GitHub ↗
──────────────────────────────────────────────────────
```

- 项目名称最醒目；一句话说明帮助读者判断是否适用；使用方式提示保持次要层级。
- 主链接直达已核对的使用入口，GitHub 根目录作为次链接。可用性差异通过链接文案表达，不使用统一的「立即体验」。
- 使用已有字体、背景、文字和陶土色变量；用细分隔线、留白和字重建立层级。首版不增加封面图、大图标、星标数量或实时提交统计。
- 每个条目有两个独立链接，不把整条做成包住其他链接的大链接；点击按钮直接打开目标，不弹出额外详情框。
- 鼠标悬停和键盘焦点都能清楚辨认链接。外链新标签页打开并设置 `rel="noopener"`，提供明确的可访问名称。
- 移动端允许名称与使用方式提示换行；说明常驻可见，两个链接可独立点击。
- 4 项直接完整展示，无搜索、筛选、分页、轮播或折叠；项目增多后先重新精选，数量和用途足够多时再讨论独立目录。

首版状态：静态默认内容、链接 hover/focus、移动端换行、浅色/深色。没有远程数据加载，因此不需要加载骨架和 GitHub API 失败状态。若某项目暂不可用，编辑时撤下使用入口或替换为准确的说明入口。

## 8. 实施建议与验收

按已确定的设计方向实施以下工作。

### A. 确定展示内容和旧区块去向

文件：`index.html`、`tools/blog/data/featured-posts.json`、本设计稿。

核对四项介绍与使用入口；保存旧判断及附属内容的带日期快照；确认旧作品区是否改名。现有精选机制保持单一来源，首版无需增加新的文章元数据字段。

验收：每项入口与按钮文案吻合；旧判断有可恢复的内容记录；历史文章正文与元数据保持原样。

### B. 实现首页模块与导航

文件：`index.html`、`assets/css/style.css`；仅在确有相关逻辑时修改 `assets/js/main.js`。

将原判断区块替换为静态项目列表，更新导航顺序及锚点，保留 `#about` 兼容落点。四项只在首页维护一份，不引入运行时 GitHub API、自动仓库抓取或新的后端。若本次只修改既有公开文件，不需要新增 manifest 项；若引入新公共资产，再明确登记。

验收：四项始终可见；所有链接可用键盘访问；320/390/768/1440px 不横向溢出；浅色和深色均符合现有层级。

### C. 可选的博客导航入口

文件：`tools/blog/index.html`。

给归档页补充指向首页 `#resources` 的站点导航，并覆盖移动端。保持文章分类、搜索、精选、分页和历史文章正文的行为。

验收：资源入口不被误认为新的文章分类；返回首页后定位正确。

### D. 文档、检查与视觉复核

核对文件：`README.md`、`CONVENTIONS.md`、`AGENTS.md`、`CLAUDE.md`，以及描述首页结构的共享文档；只修正与最终变更相关的内容。设计确定前不将本草案写成长期规范。

现有 `scripts/equivalence/a0-equivalence.spec.js` 有针对 `#about` 的导航断言；实施时应核对预期与兼容处理。候选架构仍使用冻结输入，需明确真实源码与候选基线的关系，不能为了过检查直接刷新全部基线。

建议验证：

- `git diff --check`、`node scripts/check-repository-policy.js`。
- 从 `scripts/` 执行 `cmd /c npm run check`，确认既有规范、链接和公开内容检查。
- public dist 构建及检查写入项目内 `build/` 的验证目录；验证新增资源入口的实际链接。
- 真实浏览器截图审查首页受影响区域，覆盖桌面/移动、浅色/深色、键盘焦点与导航展开状态。若补充博客入口，同样覆盖其桌面和移动布局。
- 本地检查、提交、远端推送、Pages 部署和线上核验分别报告。发布动作按项目规则和用户授权执行。
