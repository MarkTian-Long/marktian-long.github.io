# 作品与工具内容深化设计

**日期：** 2026-08-30
**状态：** 已批准
**范围：** 首页「作品 & 工具」中的 8 个公开页面，以及必要的证据、测试和发布清单
**实现边界：** 纯前端、零公开密钥、GitHub Pages 可运行；首页保持极简列表

## 1. 背景

现有 8 个页面已经能够独立访问，但成熟度不一致。较新的智能客服和 ASCI 已经包含场景、HITL 与流程状态；较早的信息工具更接近静态资料陈列。部分公开表达还把目标、演示指标和真实结果混在一起，例如：

- ESOP 首页把“≥95%”写成已实现结果，当前证据文件实际将其定义为目标。
- ESOP 页面把“高置信度字段占比”称为“准确率”，两者不是同一个指标。
- ESOP 还会把可能含姓名、薪酬等字段的完整结果自动写入 localStorage；新版本必须默认仅保留在会话内，并让旧数据由用户选择加载或清除。
- A 股助手同时包含网络行情、模拟基本面和静态模型结论，但首次交互前没有形成统一的运行边界说明。
- 热点快照的更新时间是内容事实的一部分；过期时应明确降级为历史快照，不能继续暗示“当前热点”。
- AI 产品拆解和 Agent 认知全景包含会快速变化的产品、框架与数字，但缺少统一的最近复核状态。

本轮不是单纯扩写文案或视觉翻新，而是让每个页面具备可解释的产品任务、会改变结果的交互、失败路径、证据边界与可持续维护方式。

## 2. 目标与非目标

### 2.1 目标

1. 招聘方在 3–5 分钟内能看出作者解决了什么问题、做了哪些产品决策、如何处理风险。
2. 日常访问者能完成一个具体任务，而不是只浏览静态介绍。
3. 八个页面使用一致的可信度语言：真实、Mock、静态内容、目标、代理指标、离线测量和外部研究不得混用。
4. 四个信息工具形成连续工作流：信源发现 → 信号筛选 → 产品分析 → 方法论沉淀。
5. 保持现有静态站架构，不引入浏览器密钥、后端服务或需要账号登录的核心路径。

### 2.2 非目标

- 不把 8 个页面合并或下线。
- 不把首页改成大型作品卡或新增复杂筛选。
- 不新增站点托管的真实 LLM、券商、论文数据库或企业系统；ESOP 仅保留用户主动配置、凭证只存在当前会话的可选自定义 API 路径。
- 不用伪造的实时数据、生产指标或用户结果增强观感。
- 不顺手重构博客、主页其他区块或全站设计系统。

## 3. 双体系信息架构

### 3.1 产品原型体系

四个产品原型统一回答八个问题：

1. 谁在什么场景下遇到什么问题？
2. 为什么需要 AI，规则或普通检索为什么不够？
3. 哪些部分由系统自动完成，哪些必须由人决定？
4. 哪三个产品决策最影响结果？
5. 正常流程如何运行？
6. 失败、冲突、权限不足或低置信度时如何处理？
7. 如何评估输出，而不是只展示输出？
8. 当前演示与生产系统之间还差什么？

### 3.2 信息工具体系

四个信息工具保留独立 URL，但在页面中声明上下游关系：

```text
前沿雷达
  发现和管理信源
       ↓
热点快照
  跨平台筛选信号
       ↓
AI 产品拆解
  建立产品研究档案
       ↓
Agent 认知全景
  沉淀可复用决策框架
```

每页只承担一个核心职责，避免重复建设“又一组链接”“又一组热点”或“又一组框架卡片”。

四页统一使用标签“1 信源 / 2 信号 / 3 分析 / 4 方法”，顺序和相对链接一致；当前页只能有一个 `aria-current="step"`。这是一份跨页语义契约，不引入共享运行时。

## 4. 统一页面契约

每个页面按自身视觉语言实现，但必须提供以下语义层：

### 4.1 首屏任务说明

- 一句话价值。
- 适用对象和主要任务。
- 页面模式：交互式 Mock、静态研究、网络数据可选或离线演示。
- 最近复核或数据更新时间。
- 限制说明在首次交互前可见。

### 4.2 决策与状态

- 至少三个会改变展示结果或流程的用户选择。
- 至少一个失败、冲突、低置信、过期或人工介入状态。
- 状态之间能重新开始或返回，不依赖刷新页面恢复。
- 动态结果必须与当前选择保持同步。

### 4.3 可信度语言

公开数字必须属于以下一种：

| 类型 | 含义 | 页面表达 |
|---|---|---|
| `target` | 产品或验收目标 | “目标”“门槛”，不能写成已达到 |
| `proxy` | 用于观察体验或流程的代理量 | 说明计算方法与局限 |
| `offline-measured` | 在明确的本地样例或评估集上测得 | 显示样本范围、版本与日期 |
| `production-result` | 真实生产结果 | 仅在有可核查证据时使用 |
| `external-research` | 第三方研究或案例 | 显示来源、日期和链接 |

“模型置信度”“高置信字段占比”“字段准确率”“来源覆盖率”必须分别命名，不得互相替代。

### 4.4 降级策略

- 网络失败：保留可解释的本地样例，不把样例标成实时结果。
- 数据过期：显示“历史快照/待复核”，不静默继续使用“最新”。
- JSON 加载失败：显示可读空态和恢复建议，核心页面框架仍可访问。
- 用户输入与演示数据不匹配：明确说明当前数据包范围，提供可选预设。
- 导出失败：页面状态不丢失，按钮恢复可操作状态。
- 可选自定义 API：只接受 HTTPS（显式 loopback 调试除外），拒绝 URL credentials 和非法协议；凭证、endpoint、model、输入与结果都不得写入持久化存储，错误信息必须脱敏。

## 5. 八个页面设计

### 5.1 ESOP 字段提取 Demo

**新定位：** 文档智能抽取与质量评估工作台。

**保留：** 文本/PDF Demo、字段分组、溯源、逻辑校验、Bad Case 标注和 JSON 导出。

**深化：**

- 首屏把“≥95%”改为离线验收目标，不再声明已实现生产准确率。
- 质量看板拆成字段完成率、高置信字段占比、来源覆盖率和规则告警数。
- 增加指标定义抽屉，解释置信度不等于正确率。
- 提供三种本地样例：完整披露、字段缺失、跨章节冲突；选择样例会改变结果和告警。
- 增加“评估模式”：用随仓库保存的合成标注答案计算样例级 exact match、完整率和溯源覆盖率，并明确标记为离线演示测量。
- Bad Case 增加根因分类、修复建议和 Prompt 版本，形成“发现 → 归因 → 修复 → 回归”的闭环。
- PDF 接入只展示真实文件名与大小，不再按文件大小估算页数或暗示默认 Demo 读取了 PDF 内容。
- 新结果仅在当前页面会话保存；检测到旧版 localStorage 结果时，由用户选择加载或清除，不静默读取或删除。

**不做：** 真 PDF 解析、OCR、站点托管的模型请求或生产准确率承诺；可选自定义 API 不计入默认 Demo 的效果证据。

### 5.2 A 股 AI 助手

**新定位：** 证据驱动的金融研究 Copilot 演示。

**保留：** 六个 Tab、可选网络行情、RAG/Reranking、Agent 轨迹、合规说明和反馈闭环。

**深化：**

- 在首屏增加统一运行模式说明：网络行情可用时为外部数据；基本面、新闻和模型结论为 Mock/静态演示。
- 把六个 Tab 串成一条研究任务：问题定义 → 数据收集 → 证据检索 → 结论生成 → Claim 审查 → 合规交付。
- 研报结果增加 claim-evidence 表：每条判断对应引用、数据时间、证据级别和未解决冲突。
- 增加三类失败路径：行情网络失败、本地知识与市场新闻冲突、证据不足时拒绝形成确定结论。
- 把“置信度”改为演示评分或删除；任何评分都说明计算规则。
- 反馈闭环补充“问题类型 → 修复对象 → 回归结果”，而不仅是 localStorage 计数。

**不做：** 交易指令、个性化投资建议、真实券商接口或浏览器内模型调用。

### 5.3 智能客服产品设计沙盘

**新定位：** 多场景客服产品决策与风险实验台。

**保留：** 银行/电商/创业三场景、九张决策卡、L4 链路、四类对话和 HITL。

**深化：**

- 将“真实对话链路”统一改为“完整模拟链路”。
- 为每个场景增加验收卡：首要目标、硬性 guardrail、成本约束和人工接管策略；所有数字标明 target 或 proxy。
- 增加故障注入：过期知识、提示注入、无权限 SQL、低置信意图。故障会改变节点状态和最终处置。
- Demo 结束后生成运行复盘：经过节点、触发规则、HITL 决策、风险检查、是否完成任务和仍待人工处理项。
- 决策卡中的外部数据增加来源类型与日期；无法核实的数字改成定性原则。
- 支持导出当前场景的决策摘要 JSON，不导出敏感或伪造生产数据。

**不做：** 自由文本真实模型对话、真实工单系统和真实订单查询。

### 5.4 ASCI 科研任务执行系统

**新定位：** 可复核、可回退、有人类决策记录的科研任务编排器。

**保留：** 14 节点注册表、三种模板、非线性插入、HITL、降级、回退与最终结果。

**深化：**

- 任务开始前增加研究协议摘要：研究问题、时间范围、来源范围、纳入规则和交付物。
- 明确主题输入不会触发真实检索；若结果数据包固定，则禁止暗示“真实 Agent 适配”。
- 每个人工决策写入审计轨迹，包括节点、动作、理由、时间与受影响的下游节点。
- 最终页增加可复现清单：实际执行管线、动态插入节点、排除文献、矛盾处置、降级路径和人工编辑。
- 现有置信度统一标为模拟流程指标，不表示科研结论正确率。
- 支持导出“研究过程清单”JSON；正文和引用导出继续保持独立。

**不做：** 真实论文库检索、全文授权、真实综述结论或跨任意主题生成一致结果。

### 5.5 前沿雷达

**新定位：** 可维护的个人 AI 信源系统。

**深化：**

- 每个信源包含语言、内容类型、关注主题、更新节奏、优先级、访问方式、最近复核日期和保留理由。
- 提供四个研究意图预设，把各意图映射成有顺序、有目的的阅读路线，而不是平铺链接。
- 支持按语言、主题、类型和优先级筛选。
- 最近复核超过约定周期时显示待复核，不自动声称失效。
- 工具清单改为“任务 → 为什么用它 → 输入 → 输出 → 替代方案”，减少泛泛赞美。
- 页面尾部明确下一步进入热点快照。

**不做：** 自动抓取订阅、登录态聚合或后台链接健康检查。

### 5.6 热点快照

**新定位：** 跨平台信号筛选与趋势研判台。

**深化：**

- 保留五个平台榜单，但默认先展示本期三条核心信号，榜单作为证据层。
- 每条核心信号包含：发生了什么、为什么值得关注、支持证据、不确定性和接下来观察什么。
- 项目点评拆为事实摘要与作者判断，避免混在同一段里。
- 数据过期时进入历史快照状态；显示更新时间、距今天数和更新方式。
- 支持按产品、技术、商业和行业筛选，并标记跨平台重复出现的信号。
- 与 AI 产品拆解建立明确下游入口；只有存在真实对应档案时才显示链接。

**不做：** 浏览器端实时抓榜、虚构投票/Stars 或用主观总分伪装客观排序。

### 5.7 AI 产品拆解

**新定位：** 有证据、有版本、有竞争判断的 AI 产品研究档案库。

**深化：**

- 每个产品增加最近复核日期、档案状态、核心研究问题和“上次复核后发生了什么”。
- 将现有七个 Tab 收束为“决策摘要、产品机制、竞争取舍、证据账本、演化与边界”五类；原字段可以继续复用。
- 支持按类别和决策主题筛选，并显示个人判断、复核日期与证据数；本轮不扩张为评分或跨产品排行。
- 推荐星级和趋势必须解释标准；无法维护则移除，避免成为无依据排名。
- 数据过期、来源缺失和无链接来源在卡片和详情中都可见。
- 支持 URL 参数或 hash 打开指定产品，承接热点快照的下游链接。

**不做：** 自动爬取产品、自动生成结论或伪实时 MAU/收入数据。

### 5.8 Agent 认知全景

**新定位：** 从业务约束出发的 Agent 设计决策手册。

**深化：**

- 框架选型先问约束，再给建议；框架清单显示最近复核日期和官方来源。
- 过时、实验性或被替代的框架保留历史说明或更新，不继续以当前推荐呈现。
- 增加“是否需要 Agent”前置判断：任务重复度、可验证性、外部影响、错误成本和人工接管。
- 架构页增加故障传播、权限边界和可观测性检查，不只展示拓扑。
- 企业场景中的 ROI 数字标为目标、外部研究或示例；没有依据时改成待验证指标。
- 最终输出一张决策摘要：推荐形态、不推荐原因、必需 guardrail、验证计划和下一步。

**不做：** 以静态页面替代真实框架 benchmark，或给出无日期的“最佳框架”结论。

## 6. 首页调整

首页只做以下修改：

- 统一名称与页面内部标题。
- 一句话描述使用“任务 + 差异点”，不写未验证成果。
- ESOP 移除“≥95% 已实现”表达。
- ASCI 描述从“5 步”改为能反映 14 节点、HITL 与回退的准确表述。
- 所有新窗口链接补齐 `rel="noopener"`。
- 不增加标签、展开详情、封面图或复杂卡片。

首页修改属于本轮批准的有意变化，以首页集成测试和新截图验收；不修改候选冻结页或旧 A0 baseline，也不把“与旧页面零差异”的 candidate 检查当成本轮门禁。

## 7. 数据与状态

### 7.1 本地数据

- 结构化内容优先由现有 JSON/JS 数据源驱动。
- 需要用户本地保存的筛选或反馈继续使用 `qiuzhi_<module>_v<version>`。
- 不把 API key、个人股票、自定义文档原文或敏感标注写入持久化存储。

### 7.2 时间状态

信息工具至少保存 `reviewedAt` 或 `updated_at`。前端可根据当前日期显示：

- 当前：在维护周期内。
- 待复核：超过维护周期，但内容仍可浏览。
- 历史快照：数据本质上只代表某个日期。

状态只描述维护时间，不推断内容真假或链接是否失效。

## 8. 测试与视觉验收

### 8.1 自动检查

每个工具增加独立 Node 测试，至少覆盖：

- 必要的 Mock/真实边界文本存在。
- 关键数据对象字段完整。
- 用户选择会映射到不同输出或状态。
- 指标类型、来源和日期满足页面约定。
- JSON 可解析，URL 和相对资源路径安全。
- 新增公开资源进入 public-dist manifest。

全局继续运行：

```powershell
cd scripts
cmd /c npm test
node check-repository-policy.js
node check-search-foundation.js
cmd /c npm run build:public
cmd /c npm run check:public-dist
```

### 8.2 视觉检查

每个页面至少检查：

- 桌面 1440×900 默认状态。
- 桌面核心交互完成状态。
- 移动端 390×844 默认状态。
- 一个失败、过期或 HITL 状态。

重点确认首屏限制可见、文本不溢出、筛选和折叠可键盘操作、状态颜色不是唯一信息来源。

所有 `*.browser.test.js` 统一使用现有的 `node:test + Playwright chromium + createStaticServer` 模式，由 `node --test <file>` 执行；测试自己管理服务器与浏览器生命周期，不混用 Playwright runner 的 `*.spec.js` 契约。

## 9. 执行与集成

采用一份总设计、八份独立实施计划、八个隔离 worktree 实现任务和一个主集成任务。八个任务一次派发，由运行环境并发调度；共享文件只由当前总控任务串行处理。

每个工具任务必须返回：

- 修改文件。
- 测试命令与结果。
- 截图页面、视口和状态。
- 剩余限制。
- 提交 SHA 或可审查差异。

主任务负责最终规格审查、代码质量审查、全量测试、公开白名单、证据文件、首页文案和本地提交。候选冻结页与旧 A0 baseline 保持不变；`git push` 保持 HITL。

## 10. 完成定义

只有以下条件全部成立时，才能声称本轮完成：

1. 八个页面均实现各自规划，而不是只有文档。
2. 首页没有未证实结果或错误能力描述。
