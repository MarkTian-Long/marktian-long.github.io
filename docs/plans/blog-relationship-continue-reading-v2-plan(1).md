# Blog Relationship & Continue Reading v2｜实施计划手册

## 一、任务背景

当前博客文章底部的“相关文章”主要依赖 metadata 相似度进行推荐。随着历史文章动态关联检索已经进入博客写作流程，这套机制出现了明显断层：

- 写作阶段已经能够判断文章之间是前提承接、观点延伸、观点修正，还是只有主题/关键词相似；
- 网站端仍把不同类型的关系压缩成统一的“相关文章”；
- 正文历史内链与底部推荐容易重复；
- 新文章发布以后，旧文章无法自然展示后来出现的后续观点。

本次改造的目标不是建设推荐系统、知识图谱或系列中心，而是把写作阶段已经确认的真实文章关系沉淀到网站导航中，同时保留轻量的自动同主题推荐。

任务名称统一为：

**Blog Relationship & Continue Reading v2**

---

## 二、核心产品目标

把文章底部从：

**相关文章 = 按 metadata 猜测相似文章**

升级为：

**继续阅读 = 强关系优先 + 同主题发现兜底**

最终让读者能够理解四类问题：

1. 当前文章建立在哪篇旧文章的认知基础上；
2. 后来哪篇文章继续推进了当前问题；
3. 后续文章是否修正或重新限定了当前判断；
4. 除正文已经出现的文章之外，还有什么同主题内容值得发现。

同时保留“上一篇 / 下一篇”，继续作为单纯的发布时间导航。

---

## 三、已经锁定的产品原则

### 3.1 历史正文保持发布时状态

历史文章正文不因为未来文章出现而自动修改。

正文回答：

**“作者在这篇文章发布时，是怎么判断的？”**

“继续阅读”回答：

**“站在今天，读完这篇以后最值得往哪里继续？”**

这两个时间视角必须刻意区分。

因此：

- 不自动给旧文章正文补“后来我又写了……”；
- 不因为关系系统上线而批量重写历史正文；
- 新文章可以改变旧文章底部“继续阅读”的结果；
- 旧文章本身仍保留原始公开判断。

### 3.2 继续阅读最多 3 篇，不强制填满

- 最多显示 3 篇；
- 可以显示 0、1、2 篇；
- 不为了凑满三个推荐位降低关系门槛；
- 强关系优先，弱关系只补剩余位置。

### 3.3 强关系与自动同主题分层

强关系必须经过内容判断确认，不能由 metadata 相似度自动猜测。**显式关系是写作与发布评审的输出，不是反过来塑造新文章主线的输入。** 对未来新文章，应以 Blog SOP 中已经完成的历史独立性与增量评审结果为依据再沉淀 relation；网站推荐算法或历史关系网络本身不得成为“应该把文章写成续篇”的理由。

建议发布 metadata 只维护三种显式关系：

- `builds_on`
- `revises`
- `companion`

读者展示：

| metadata 关系 | 新文看旧文 | 旧文看新文 |
|---|---|---|
| `builds_on` | 承接前文 | 后续延展 |
| `revises` | 修正前文 | 后续修正 |
| `companion` | 并列阅读 | 并列阅读 |

没有显式强关系、但满足自动推荐条件的文章统一显示：

**同主题**

自动算法不得生成 `builds_on / revises / companion`。

### 3.4 一条关系只维护一次

显式关系原则上由较新的文章指向较早的文章。

例如：

B 在 A 基础上继续推进。

只维护：

`B -> A / builds_on`

不再在 A 中人工维护：

`A -> B / follow_up`

旧文章 A 打开时，从当前最新的中央 metadata 反向扫描，即可自动得到：

**后续延展 → B**

同理：

`C -> A / revises`

可以让 A 自动得到：

**后续修正 → C**

这样未来新增文章只维护新文章，不需要反复回改历史 metadata。

### 3.5 正文历史内链不等于显式关系

正文历史链接仍然服务论证。

以下情况可能需要正文链接，但不一定形成强关系：

- 引用旧文章中的案例；
- 补充背景材料；
- 使用一个旧定义但不是当前核心前提；
- 说明此前写过相近问题；
- 参考资料或扩展说明。

只有明确存在以下关系时才考虑显式 relation：

- 当前文章建立在旧文章的核心判断、框架或必要前提上；
- 当前文章明显把旧问题继续推进到新的问题；
- 当前文章对旧判断进行了实质修正、挑战或重新限定；
- 两篇文章回答直接互补的问题，共同阅读价值显著高于普通同主题。

普通关键词、同模型、同公司、同大类和宽泛主题相似都不构成强关系。

### 3.6 concepts、topics、tags、category 的职责保持分离

#### concepts

继续服务 AI 历史文章语义召回。

目标偏向高召回：

**“以前是不是写过这个概念、机制或判断？”**

不得直接参与前端显式关系判断，也不直接进入自动同主题推荐。

#### topics

作为自动“同主题”推荐的基本资格。

两篇文章至少共享一个 topic，才允许进入自动同主题候选。

#### tags

只用于满足 topic 门槛后的辅助排序。

#### category

只作为更弱的辅助排序。

仅 category 相同不构成推荐资格。

#### relations

只表达经过正文精读确认的强文章关系。

## 四、继续阅读的最终选文规则

推荐结果最多 3 篇。

### 第一层：显式强关系

从中央 metadata 中获取：

- 当前文章主动声明的 `builds_on / revises / companion`；
- 其他更新文章指向当前文章后形成的反向关系。

强关系优先于所有自动同主题。

### 第二层：控制正文重复

识别当前正文中已经出现的站内历史文章链接。

继续阅读允许与正文重复的历史文章最多 **1 篇**，且必须是最重要的显式强关系。

其余正文已经出现的站内历史文章：

- 不进入自动同主题候选；
- 不为了填满坑位再次展示。

为什么允许最多重复 1 篇：

正文链接回答“理解这里需要什么前提”；底部最核心的承接关系回答“读完以后如果要补齐这条认知链，最值得去哪里”。

两者使用场景不同，因此最重要的一篇重复可以接受；大量重复则失去发现价值。

### 第三层：自动同主题补位

只有满足以下条件才进入自动候选：

- 至少共享一个 topic；
- 不是当前文章；
- 未经强关系已经入选；
- 不属于正文已经出现的其他站内文章。

排序优先级：

1. 共享 topic 更多；
2. 共享 tag 更多；
3. category 相同作为弱辅助；
4. 使用稳定的发布时间顺序解决最终同分。

取消旧的：

- topic +3
- tag +2
- category +1
- category 相同即可入选

这种固定魔法分数机制。

### 第四层：不凑数

如果候选不足：

只展示实际有价值的候选。

## 五、动态反向更新

这是本次必须实现的核心能力。

### 场景 A：旧文章出现新的后续延展

历史已有 A。

后来发布 B，并声明：

`B builds_on A`

A 的正文和 metadata 不需要人工添加 B。

以后读者打开 A：

系统读取当前最新中央 metadata，发现 B 指向 A，于是自动展示：

**后续延展 → B**

### 场景 B：旧文章出现后续修正

后来发布 C：

`C revises A`

A 自动增加：

**后续修正 → C**

### 场景 C：自动同主题随新文章变化

若新文章 D 与 A 共享 topic，并且比 A 原来的某篇同主题候选更合适：

A 的自动同主题推荐允许更新。

因此继续阅读是一个“当前视角”的动态导航，而正文仍是“发布时视角”的历史记录。

## 六、历史文章处理原则

### 6.1 不批量重生成正文

禁止使用旧 Markdown 批量重新生成历史发布 HTML。

原因：

历史 HTML 可能已经包含发布后的修正，而 Markdown 不一定同步。

本次只能修改：

- 公共运行时；
- 公共样式；
- 推荐导航 mount point；
- 与旧相关文章脚本直接相关的重复逻辑；
- 必要的模板 shell。

不得修改：

- post-body 正文；
- 标题和摘要实际文本；
- 表格正文；
- 参考资料；
- 人工正文站内链接；
- 已发布观点内容。

### 6.2 历史关系只做高置信初始化

可扫描现有发布 HTML 的站内博客正文链接，作为候选召回。

历史初始化只对**已经发布的事实关系做事后分类**，不得为了补关系网改写旧文、调整旧 metadata 语义，或把本来只是同主题的文章解释成承接关系。

但：

**“存在站内链接”不等于“存在显式 relation”。**

优先补：

- 正文明说“延续此前……”
- 正文明说“在上一篇基础上……”
- 正文明说“此前我认为……现在……”
- 明确直接互补、并且共同阅读价值明显的文章

不确定关系：

- 不猜；
- 不强行写入；
- 继续交给自动同主题；
- 最终报告可以列为待人工复核候选。

本次不追求让所有旧文章都形成关系网络。

## 七、页面结构与体验

文章底部建议保持两个清楚分工的区域。

### 7.1 继续阅读

标题：

**继续阅读**

最多 3 篇。

每项包含：

- 轻量关系标签；
- 文章标题；
- 日期可作为弱辅助。

支持标签：

- 承接前文
- 后续延展
- 修正前文
- 后续修正
- 并列阅读
- 同主题

视觉原则：

- 继续保持当前博客克制的文字导航风格；
- 不做大型推荐卡片；
- 不给 6 种关系分别设计强颜色；
- “修正”可以略强调，但不能像错误/警告状态；
- 深色模式正常；
- 长标题折行清楚；
- 手机布局可读；
- hover / keyboard focus 清楚。

### 7.2 上一篇 / 下一篇

继续保留。

它只回答：

**“按发布时间，作者前后发布了什么？”**

不要把时间导航和认知关系混为一套。

## 八、metadata 方案

`posts-meta.json` 增加可选 `relations`。

推荐语义结构：

```json
{
  "relations": [
    {
      "slug": "older-article-slug",
      "type": "builds_on"
    }
  ]
}
```

允许 type：

- `builds_on`
- `revises`
- `companion`

要求：

- target slug 必须存在；
- 不能指向自己；
- 同一 target 不重复；
- 没有关系时允许省略；
- 不要求所有文章都有 relations；
- 不人工维护反向边。

如果仓库当前 schema 设计存在更合适的等价表示方式，可以调整具体 JSON 结构，但不能改变这些语义规则。

## 九、公共运行时与生成流程

目标不是重构博客生成系统，而是消除文章级重复推荐逻辑。

本次应让：

- metadata 读取；
- 继续阅读计算；
- 反向强关系推导；
- 上一篇 / 下一篇；
- 必要的推荐 Analytics

尽量进入共享运行时或统一公共能力。

仍然保持：

- GitHub Pages；
- 静态 HTML；
- JSON；
- Vanilla JS。

不引入：

- React / Vue；
- 服务端；
- 数据库；
- embedding；
- 向量检索；
- 运行时 LLM；
- 用户个性化推荐。

如果当前新文章生成器仍使用某一篇真实已发布文章作为模板，应建立独立文章模板或等价单一模板来源，避免以后继续复制旧相关文章逻辑。

但不要借此重写整个 Markdown parser 或博客生成流程。

## 十、Analytics

本次一并解决内部文章跳转来源不可区分的问题。

至少区分：

- `body`
- `continue_reading`
- `post_nav`
- `archive`
- `homepage`

继续阅读额外记录关系类型，例如内部值可以是：

- `builds_on`
- `follow_up`
- `revises`
- `revised_by`
- `companion`
- `same_topic`

具体事件名称和字段保持现有 GA4 风格即可。

限制：

- 不发送正文内容；
- 不发送个人信息；
- 尽量保持现有文章打开/阅读深度事件连续；
- 不为了本次导航改造重构整套 Analytics。

目的：

未来可以比较“有明确关系解释的继续阅读”与普通同主题推荐是否真的提高站内阅读深度。

不要把完整推荐算法复制进 memory。

## 十二、网页版 Blog 项目规范同步

这次需要同步：

- `1_blog-sop_v25.md`
- `3_blog-review-checklist_v18.md`

### SOP 职责

只规定：

- 历史召回 ≠ 正文内链 ≠ 发布显式关系；
- 正文历史内链不自动形成 relation；
- 只有强关系才沉淀；
- 大纲确认同时判断“正文应不应该引用”和“是否值得公开成为显式关系”；
- 历史正文不因为未来文章出现而自动回改。

不保存网站运行算法。

### Checklist 职责

增加显式关系真实性终审：

- 承接是否真实；
- 修正是否真实；
- companion 是否真的直接互补；
- 是否把普通同主题/案例引用越级成强关系；
- 是否为了 SEO 或填满推荐位强行建立关系；
- 没有关系时允许不写。

## 十三、静态校验与自动测试

至少覆盖：

### metadata

- relation type 合法；
- target slug 存在；
- 无自引用；
- 无重复 relation；
- JSON 可解析。

### 推荐逻辑

- 最多 3 篇；
- 自动同主题必须至少共享一个 topic；
- category-only 不会入选；
- concepts 不参与前端自动推荐；
- 正文历史链接不会再次进入 same-topic；
- 正文重复显式强关系最多 1 篇；
- 强关系优先于 same-topic；
- 候选不足时不凑数。

### 动态关系

必须测试：

B `builds_on` A 后：

- B 显示“承接前文 → A”；
- A 自动显示“后续延展 → B”；
- 不要求修改 A metadata。

C `revises` A 后：

- C 显示“修正前文 → A”；
- A 自动显示“后续修正 → C”。

### 回归

- 上一篇 / 下一篇正常；
- metadata 请求失败时正文仍可读；
- 旧文章正文内容没有因迁移改变。

## 十四、浏览器与视觉 QA

本次是明显用户可见改动，必须实际启动页面检查。

至少检查：

1. 有 builds_on 的新文章；
2. 被 builds_on 的旧文章，确认自动出现后续延展；
3. 有 revises 的文章及反向后续修正；
4. 无显式关系、只有同主题的文章；
5. 正文已有多个站内链接的文章；
6. 推荐不足 3 篇的文章；
7. 最新文章和最旧文章的上一篇/下一篇；
8. 手机；
9. 深色模式；
10. 长标题、hover、focus。

关键状态建议截图留在 Codex 最终报告或临时 QA 目录中；不要把无必要截图提交到正式网站资产。

## 十六、实施顺序

### 第一阶段：先保护现场

- 检查 git status；
- 确认未提交修改；
- 读取仓库长期规范；
- 找出相关文章、生成器、runtime、Analytics、测试的实际当前实现；
- 明确哪些历史 HTML 可安全只迁移 shell。

### 第二阶段：建立数据与校验

- 增加 relations；
- 建 validator；
- 添加核心逻辑测试；
- 暂不大规模初始化历史关系。

### 第三阶段：实现共享“继续阅读”

- 替换旧推荐算法；
- 加入反向关系；
- 加正文去重；
- 保留上一篇/下一篇；
- 做统一 UI。

### 第四阶段：安全迁移历史文章

- 只调整公共导航 shell；
- 不重生成正文；
- 验证正文区域未变化。

### 第五阶段：高置信历史关系初始化

- 扫描站内正文历史链接；
- 语义复核；
- 只写高置信关系；
- 模糊项列入报告，不猜。

### 第六阶段：Analytics

- 区分 body / continue_reading / post_nav / archive / homepage；
- 记录 relation_type。

### 第七阶段：文档同步

更新：

- WRITING_GUIDE
- CONVENTIONS
- BLOG_DESIGN
- README
- memory

### 第八阶段：全量 QA

- 静态检查；
- relation tests；
- 浏览器测试；
- 手机；
- 深色；
- 新文影响旧文；
- git diff；
- 历史正文保护验证。

## 十七、完成标准

任务完成必须同时满足：

- 全站旧“相关文章”逻辑被新的“继续阅读”替代；
- 显式强关系和自动同主题清楚分层；
- 新文章能自动反向影响旧文章；
- 历史正文保持不变；
- 继续阅读最多 3 篇，允许不足；
- 正文内链不会在底部大面积重复；
- 自动同主题必须共享 topic；
- category-only 不再构成推荐；
- concepts 不参与前端推荐；
- 上一篇 / 下一篇正常；
- Analytics 能区分阅读入口；
- 自动检查通过；
- 浏览器 QA 通过；
- 长期规范同步；
- 未增加 Series / 知识图谱等超范围能力；
- 未制造内容相同的 v2/v3 仓库副本；
- 未执行 git push，除非用户另行明确授权。
