# 文档同步

变更内容：$ARGUMENTS（描述刚刚做了什么改动）

## 执行步骤

### 第一步：梳理变更范围

先读取当前任务、已有授权和实际 diff，确认新增、删除、重命名及行为或规则变化。参数未填写但上下文已经明确时直接继续；只有无法从现有信息判断、且会改变范围或作者立场的问题才集中询问。文档同步不扩大原任务授权。

### 第二步：定位唯一责任文件

检查 `AGENTS.md`、`CLAUDE.md` 与根 `README.md` 的目录、模块表和入口是否受影响，只修改实际过时处。新增工具时检查该工具 README 是否说明功能、数据来源、文件结构和维护入口；命名或目录规范变化时定位 `CONVENTIONS.md` 对应规则。

博客文章、工程或规范变化先读 `tools/blog/governance/README.md`，再按当前阶段检查：

- **草稿或预览**：核对唯一源稿、候选构建与公开分发隔离。不得因“新增文章”就追加正式 `posts-meta.json`、搜索、RSS 或 sitemap；公开预览授权不包含正式发布。
- **正式发布**：按 Writing Guide 与当前 `publish-blog` Skill 核验最终 Markdown、派生 metadata、HTML、图源和发现资产；不在本 Skill 维护另一条发布顺序。
- **字段与语义**：frontmatter、分享文案和同步契约归 `tools/blog/WRITING_GUIDE.md`；taxonomy 词义与合法值归 `tools/blog/data/blog-taxonomy.json`，变更决策归 SOP。文档同步不能自行造词、重新分类历史文章或选择分享句。
- **流程与质量**：SOP 负责阶段及作者关口，认知规范负责反馈方法，Checklist 负责结果验收；预览规范、图表规范和 Visual Guide 各维护自身契约。修复 `CONVENTIONS.md`“博客内容规范”和共享 memory 中已过时的竞争性描述，优先改为当前责任文件的引用。
- **网页版项目指令**：仅当长期硬约束、授权或默认交付方式变化时更新 `tools/blog/governance/chatgpt-project-instructions.md`；普通 CLI、规格或测试变化不复制进去。仓库文本更新与网页版实际设置更新分别报告，不假称同步完成。

### 第三步：执行最小更新与验证

在已授权范围内直接修复确定性差异，保持单一当前文件；不把同一细则复制到多个入口。只对实际影响的路径、命令和链接做核验，不顺手重写无关文档。

项目 Skill 以 `.agents/skills/` 为唯一编辑源，按 `docs/agent-context/skills.md` 单向同步 `.claude` 兼容层并执行现有兼容与仓库政策检查；不创建同义 Skill 或改动个人安装副本。

### 第四步：报告实际结果

说明修改了哪些责任文件、修正了什么冲突，以及实际验证和剩余事项。已有授权覆盖的同步工作完成后直接报告，不增加默认的文档确认关口；作者立场、范围或尚未授权的公开操作仍回到对应确认节点。

## 注意事项

- 文档简洁说明职责与使用边界，实现细节留在代码及所属技术文档。
- `AGENTS.md`、`CLAUDE.md` 中受影响的共同入口保持一致；无变化时不机械改写。
- 实现描述以实际代码和运行证据为准；代码违背有效规范或授权边界时修复实现，不能靠改文档让未完成事项变成通过。
