# Blog 标签巡检与历史问题台账

本文件是分类与标签维护的**单一运行入口和问题台账**，不另建词典。适用于 ChatGPT 定时任务及读取仓库的 Claude/Codex；它本身不会执行任务或发送通知。实际周期执行由 ChatGPT「Blog 标签巡检」任务承担。没有修改 GitHub Actions 配置，也没有扩大为整个网站的内容事实审计。

## 真源与职责

- [taxonomy](data/blog-taxonomy.json)：字段职责、合法值、词义、边界和数量要求的唯一真源。
- [SOP](governance/blog-sop.md) 的 Taxonomy change：新增、改名、定义调整、保留或退役的决策流程。
- [Checklist](governance/blog-review-checklist.md) 第六类：正文与标注、误标与漏标的终审。
- [发布指南](WRITING_GUIDE.md)：严格 frontmatter、运行索引和历史源稿例外。
- [前次治理复核](../../docs/plans/2026-10-15-blog-taxonomy-review.md)：2026-10-15 首次清理、缺口补齐与逐篇依据的历史记录；后续未结事项及复发记录统一回到本台账。

这里只维护检查节奏、操作步骤、提醒去重、问题状态和实际证据。不得把旧台账的标签结论置于当前正文与最新词典之上，也不得为维护旧标签而改写历史文章。

## 检查节奏

**每周一进行轻量巡检**：先读取本文件最新版本及上次成功检查的 ref，再读取完整当前词典和运行索引。核查新增、修改文章及未结事项；没有内容变化时不重复声称重新审过全部正文。第一轮失败必须记录覆盖缺口，不得用缓存结果冒充本次成功。

**每月第一次周检增加语义复核**：查看高占比、与栏目高度重合、反复误标、空值、未启用词及过期处理事项；先看完整 metadata，再精读真正相关的新旧文章、边界例和反例。不要每月强行重贴所有文章，也不按数量配额削减标签。

**事件触发**：词义/数量/状态变更时按 SOP 做全量 metadata 初筛与相关正文复核；读者指出错误、同一问题复发或源稿/索引不一致时立即进入当前问题，不等下次定时。

实际提醒节奏以已创建任务为准；任务每次读取这里的现行规则，不把创建时的词表和统计结果冻结。已有项目级月度维护可以读取此台账，但本次标签巡检不能重置 `docs/agent-context/maintenance.md` 的全站月度完成日期。

## 每次执行

1. **确认输入**：记录日期、默认分支 ref、taxonomy 语义版本、metadata SHA、可访问的发布产物和最新 CI 结论。比较上次检查 ref 以来的文章与标注变化；未读到或未验证的部分明确列出。
2. **跑只读检查**：在仓库根目录运行下面命令。健康脚本只统计和报信号，不写入文章、标签或台账；源码不完整时可以依据真实读取的完整数据做等价统计，但必须注明哪些原脚本未执行。
3. **检查语义而非仅数量**：单看高占比不能判错；对有实质变化和边界问题的条目读取当前线上正式页，无法加载时用最新成功部署产物/仓库发布 HTML，再看 Markdown。检查同标签是否共享有意义的主问题、有没有漏标，以及第二/第三个标签是否提供独立区分。
4. **回看已解决问题**：将当前证据与本台账旧判断比较。相同问题复用原 ID；新反证或范围变化时重开，保留原修复和这次变化原因，不能反复生成同名新问题。
5. **处置与验证**：确定性同步修复也要先确认真源；语义调整须有正文依据，并按授权边界操作。写入后回读 SHA、执行现有一致性检查，再核对对应提交的完整 CI/部署。只运行统计不能关闭源稿、语义或发布问题。
6. **原位回写**：更新本文件最近检查与相关问题卡。只保留当前状态和有意义的变更历史，不新建内容相同的周报/月报；失败或无变化时不要伪造新完成项。

```bash
node tools/blog/check-taxonomy-health.js --json
node tools/blog/check-blog-taxonomy.js
node --test scripts/taxonomy-health.test.js
```

词典发生语义变化时，再运行 `audit-taxonomy-impact.js`，参数使用实际变更前 Git ref，按 [发布指南](WRITING_GUIDE.md) 的命令契约执行。需要写入发布内容时继续执行完整仓库校验及构建；健康脚本不能替代这些步骤。

### 健康脚本能证明与不能证明的内容

`check-taxonomy-health.js` 复用现有词表校验，输出字段错误、标签总量、空话题、退役词误用、未使用有效词、全库及栏目内集中度。数值筛查阈值以脚本的 `REVIEW_THRESHOLDS` 为单一实现来源，仅用于选择复核对象，不是语义正确性的标准，不用于自动删除标签或自动退役词。

脚本返回 `complete-metadata-only` 只证明已检查完整元数据；正文语义、严格 frontmatter 一致性、推荐质量和线上部署仍须分别检查。错误记录不计入有效样本分母且标明覆盖不完整。`reviewSignals` 没有信号，不等于文章绝无误标/漏标。

## 提醒与授权

仅提醒首次发现、证据/范围/状态变化、到期仍未解决的事项，以及检查或回写阻塞。已接受且没有变化的集中度不每周报警；未结问题没有新增证据时最多每 14 天提醒一次。首次发现、最后核验、最后通知、计划复核日期分别记录。

信号 fingerprint 用于同一规则/标签/文章集合去重；同时检查 ref 差异和信号 details，避免成员不变而分母、词义、正文或规则已变时漏报。复发沿用原问题 ID，并保留旧 fingerprint。没有实际发送通知，不更新最后通知日期。

定时任务可以读仓库、运行只读检查、原位维护本文件、提出修复建议。**它不得仅凭统计信号自动修改 taxonomy、文章分类/标签/关系、正文、UI 或 CI。** 明确且已有授权的修复按最小改动执行；词义或作者立场等变化集中请用户决定。读取、测试、写入失败应通知阻塞，不宣称“无问题”或“已经处理”。

## 状态与关闭条件

状态使用 `open`（新发现）、`reviewing`（正在核验）、`pending_decision`（等待实质决策）、`resolved`（已落实修复、待最终验收）、`closed`（已核验关闭）、`accepted`（有依据保留现状）。`accepted` 必须附重开条件，不是永久免检。

每条问题至少保留：ID、首次发现/最后核验日期、对象与证据、当前判断、已做操作、验收依据、下一步或重开条件。需要延期才填写目标日期；没有人实际承诺的日期只称计划，不冒充业务承诺。修复必须能说明改了什么，以及原问题如何不再成立；合并提交或统计变少本身不算关闭依据。
