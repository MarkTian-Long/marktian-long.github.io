**核心问题与当前研究假设（尚未验证）。** B2B 软件公司在 AI 时代如何识别有价值的新产品机会，并把业务理解转化为可重复、可持续的产品优势？当前候选主线有两层：①**优势从哪里积累**——技术、数据、领域知识、客户案例之外，客户关系与分发、系统集成与业务对象控制点、信任／合规／责任、实施交付能力、生态伙伴、反馈循环、迁移成本和单位经济等，分别属于资源、能力、市场位置还是结果，哪些能形成长期优势；②**AI 产品从哪里突破**——不是先给既有功能增加聊天／生成模块，而是从业务目标与完整流程出发，识别等待、交接、重复录入、决策、异常和验收等环节，重新安排 Agent、软件与人的职责，再设计相应产品与技术架构。两层可能通过“可重复的流程重构能力→产品化交付→客户反馈／数据／集成沉淀→下一轮更低成本或更高质量交付”形成联系，但该复利链尚未得到证实。

**对作者流程假设的初步校准（本项目分析，不归为作者已确认结论）。** “先还原 As-Is、再设计 To-Be、最后落到产品／技术方案”是合理的 AI 产品发现路径候选；但**流程节点数量减少不是价值本身**。更有意义的对象是端到端周期、等待与交接、重复劳动、返工、质量、合格吞吐、客户体验和风险。某些场景增加人工审批、来源追溯或异常处理节点，反而能提高整体结果。流程重构也不自动形成护城河：如果每次都依赖专家临场诊断和定制交付，它可能只是高成本咨询；只有当洞察能沉淀为可复用的领域模型、工作流组件、集成、评测、数据反馈、部署方法或客户信任时，才有机会成为可规模化能力。是否最终形成可防御优势，还取决于竞争者复制成本、客户替代选择、分发位置和价值捕获，不能仅凭“跨产品／技术／业务／AI 的理解”下结论。

**需要在后续研究中区分的概念。**
- **资源／资产积累**：技术与知识产权、数据及其使用权、领域知识、客户关系、品牌与案例、集成接口、生态资源。拥有某项资产不等于它稀缺、独占或能产生利润。
- **组织能力**：发现业务问题、流程建模、产品定义、AI 适配、工程交付、变更管理、评测与持续运营。能力可以重复执行，但未必能阻止竞争者模仿。
- **结构性优势／护城河**：系统记录位置、深度集成、网络效应、规模经济、信任与合规门槛、切换成本、分发控制点或持续学习优势。必须说明客户为何难以替代，以及优势如何被企业捕获。
- **产品突破机会**：改变工作单元或责任分工、减少等待／交接／返工、使原本不经济的任务变得可行、形成新的决策／执行闭环、进入关键业务对象或系统记录、建立可信的跨系统执行层，或改变用户／付款方／价值单位。这些是候选路径，不是已验证的穷尽分类。

**最强反方与失败条件。** ①既有 B2B 产品优势可能主要来自渠道、客户关系、合同、服务网络、合规责任和系统记录位置，AI 流程重构并非唯一突破口；②领域数据未必独占，客户案例可能只是销售证明而非数据壁垒；③流程减少可能把复杂性转移给人工复核、客户或下游系统；④流程重构可能因客户差异过大而无法标准化，落入定制项目；⑤AI 能力快速商品化后，真正优势可能来自产品责任、工作流嵌入、持续运营和分发，而不是模型或提示技巧；⑥对部分低频、高风险业务，保留人工节点可能优于自动化。后续研究需要主动寻找失败／反例，不能只挑成功厂商案例证明作者假设。

### BR-20261114-01｜Token 分发平台能否成为独立的价值捕获层？

**创建：2026-11-14｜内容更新：2026-11-26｜状态：可进大纲（独立价值与收费的成立条件；不宣称某平台已经形成持久高利润或已提供可验证的全链路安全）。** 既有路由／定价对照及 Together AI 已证提示词泄露继续成立；OpenAI Private Inference 的少量客户测试为推理时机密计算提供新的产品机制对照，但 API Preview、硬件证明细节、支持模型及合同范围仍未完整公开，不能据此宣布风险已消除。条件性商业分析继续可进大纲，不自动批准标题、分类或排期。

**作者原始触发与重点（2026-11-14，当日对话；个人问题意识而非行业统计）。** 作者回看产业史系列首篇[《看 AI，不要只问它像历史上的哪一年》](posts/ai-industry-history-mechanisms.html)中关于 OpenRouter／Hugging Face 的「供给丰富后，瓶颈向发现、评价、选择和协调迁移」判断，因百度新推出「词元所」而追问：百度词元所、OpenRouter、硅基流动、火山方舟、Google／AWS／Azure 究竟处于不同层，还是不同产品功能重叠？为什么国内部分 API 中转站呈现个人化、授权和来源不透明的现象；大型云厂商公开提供第三方模型意味着什么？作者希望进一步发散搜索，**尤其寻找反例，避免把分发入口重要直接推成分发平台能赚钱**。不能把「部分小型站点有灰色供应链」概括为国内聚合行业整体灰产。

**核心问题与当前判断。** 区分模型研发与权重发现、实际推理供给、服务采购与结算、运行时模型／供应商路由、应用端客户关系；这是经济功能，不是请求必须逐级通过的固定层级。当前更有解释力的判断是：**直接采购上游和第三方分发可以同时存在；客户购买的可能是跨供应商控制与省去运维，而非更便宜的 Token。能否收费及留下利润，还要比较云／开发平台内置功能、自建网关、直连和客户可迁移性。** Anthropic 的关联计费进一步表明，**模型费用归属、请求执行组织、客户关系和独立平台服务收费可以拆开**，不能把统一结算能力视为必由中间商掌握。模型验真与信用信息可降低交易不确定性，但不自动提供上游授权、法律合规或故障赔付。本文研究这些成立条件，不把日均调用量当平台净收入。

**首轮证据锚点（2026-11-14；以下五项沿用首轮记录，除硅基流动快速上手外，本次全面复核未逐项重验）。** ①[OpenRouter 官方供应商接入说明](https://openrouter.ai/providers/apply)明确统一 API、按延迟／吞吐／在线率／价格路由、公开指标、供应商月度结算，证明「流量路由＋交易结算」可在同一平台提供；所列开发者／供应商规模是平台自报，不等于可验证的利润率或持久壁垒。②[《人民日报》2026-11-13 百度世界大会报道](https://paper.people.com.cn/rmrb/pc/content/202611/13/content_30190926.html)转述百度对词元所的「验真、征信」定位、供应资源 100+ 与日均 Token 超 7000 亿；这些是发布方披露和媒体转述，未独立审计，不能直接证明交易新增、模型验证准确度、信用机制可持续或收入规模。③[火山引擎 AI 加速网关官方文档](https://docs.volcengine.com/docs/station-wide-acceleration/obtain-model-api-key-from-provider?lang=en)说明接入第三方通常须先取得上游 API Key；它是管理既有上游的对照，不等于统一代购结算。④[Google 云合作伙伴模型 MaaS 官方文档](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/partner-models/use-partner-models)证明云平台可托管提供第三方模型，不证明全部国家、模型和条款下均可用。⑤[硅基流动官方快速上手](https://docs.siliconflow.cn/docs/userguide/quickstart)确认多模型目录、价格及统一 API，不能单凭目录推断所有资源均自营推理。

**新增真实客户材料（2026-11-14 核验；平台刊登的具名客户采访，非独立审计）。** [OpenRouter／Descript 案例（2026-09-15 发布、9/22 更新）](https://openrouter.ai/blog/case-studies/descript-case-study/)介绍 Underlord 将三个生产 API 集成为一个，同时**保留与 Baseten 的直接商业关系和专属部署，经 BYOK 接入路由层**；预发布模型还可走直接厂商渠道。材料所称从一周以上到一两小时包含原先排队等待，不能当同量工程劳动的净节省。这提供直采与运行时聚合互补的实际案例，不证明客户以后无法迁走或 OpenRouter 净利润。

**模型厂商向应用工具层延伸：DeepSeek 的上游整合反例（2026-11-15 核验一手官方资料）。** [DeepSeek 11/13《全家桶应用 API》](https://api-docs.deepseek.com/zh-cn/news/news261113/)确认，`deepseek-flash`（V4.1-Flash）通过现有 Messages／Responses／Chat Completions 接口的参数，使用**服务端执行**的联网／深度思考搜索、PDF／Office／图片输入、网页链接读取及基础安全检查；Search、Fetch、OCR、ASR、TTS 也提供**独立工具 API**。这不是“一个端点内原生拥有全部语音与文档功能”；模型 Token 与搜索／抓取等工具服务按不同口径收费。[DeepSeek 更新日志](https://api-docs.deepseek.com/zh-cn/updates/)显示自研 Search API **10/17** 已开放，11/13 是更广泛的应用工具组合及接口开放，不应全部记为当日首发；“搜索每天处理数亿请求”等规模属于厂商自述，不能替代独立效果或利润审计。[Search／Fetch 指南](https://api-docs.deepseek.com/zh-cn/guides/search/)区分直接返回结构化搜索结果与抓取 Markdown 网页正文；它与模型在对话中调用联网工具是两种不同调用形态。官方 Demo 可证明有复刻方案，不证明生产级稳定性与成功任务成本。

**同类厂商先例与严格可比性。** [OpenAI 2025-03-11 Responses API 官方发布](https://openai.com/index/new-tools-for-building-agents/)已有模型侧 Web Search／File Search／Computer Use 内置工具和服务端编排；[2025-05-21 扩展](https://openai.com/index/new-tools-and-features-in-the-responses-api/)进一步加入代码执行、图像生成、远程 MCP。[Google Gemini API 2024-10-31 官方发布](https://developers.googleblog.com/en/gemini-api-and-ai-studio-now-offer-grounding-with-google-search/)已提供内置 Google 搜索依据与引用。因此“DeepSeek 第一家把模型外能力通过 API 提供”不成立；但各家**功能边界、调用接口、独立 API、费用和可用范围不完全等价**。尤其 OpenAI File Search 是向量存储检索而非直接等同一次性 Office／PDF 文件解析；OpenAI 模型联网搜索工具也不等同 DeepSeek 独立 Search／Fetch 的原始结果接口，不能用“全都相同”替代实测。

**对本卡的条件性增量（本项目推导，非已观测市场结论）。** 模型上游把搜索、抓取和多模态基础工具捆成可收费服务后，第三方如果只转售**单一模型调用或无差异的搜索／解析组合**，差异空间可能收窄；但**多家上游模型比较和故障回退、BYOK／采购结算、跨商家权限策略、供应商透明度、预算控制与 SLA**仍可能支持独立网关或聚合平台的价值。上游工具打包也可能让独立应用更易开发，不等于全部第三方工具、RAG 或复杂文档处理服务将被替代。真正能判定价值迁移的不是“平台开了多少接口”，而是**同一真实任务**下直连上游整套工具与跨供应商聚合／自建组合的成功率、端到端费用（Token＋工具＋重试＋人工纠错）、延迟、质量、数据治理与可迁移性。当前只有一手功能／计费规则与先例，**未做付费调用、同任务横评、客户转化或利润核验**；不能仅凭新闻热度独立成文。

**11/17 新实证｜Hugging Face 将 LLM Inference Providers 路由委托 OpenRouter（双方 2026-11-16 官方公告，本轮核对）。** [Hugging Face《Hugging Face and OpenRouter join forces to make open-weight models easy to run》](https://huggingface.co/blog/openrouter)和[OpenRouter《OpenRouter Now Powers Inference on Hugging Face》](https://openrouter.ai/blog/announcements/hugging-face-inference-providers/)分别确认：Hugging Face 将 Inference Providers 的**文本聊天／视觉语言模型（language-model requests）**从原自建路由切到 OpenRouter，仍保留 Hugging Face Token、用户／组织账单、模型页及已有代码调用方式；新路由跨多家实际上游推理服务，按实时价格、延迟、吞吐与可靠性选择，并在供应商错误或容量不足时尝试故障切换。Hugging Face 提供模型发现、API 用户入口和统一结算展示，OpenRouter 提供**运行时供应商选择、质量监测与回退**，底层供应商仍负责推理。Hugging Face 称覆盖 **80 多家供应商**，这是参与方披露的服务覆盖，不是独立审计的活跃生产使用量。**这是正式产品集成选择**，证据强于纯目录或推测，但不是 Hugging Face 的净成本／利润公开，也未披露合作分账与可解除协议的条款。

**定价、控制与替代成本的关键边界。** [Hugging Face 当前服务文档](https://huggingface.co/docs/inference-providers/providers)显示语言模型经 OpenRouter；供应商价格不加 Hugging Face 额外溢价，允许按模型 ID 指定供应商、`:fastest`／`:cheapest` 策略或在账户设置中关闭供应商。**破坏性变更：语言模型请求不再支持用户原有 Custom Provider API Key**，改由 Hugging Face 账户／组织结算；**图像和视频供应商的自带密钥继续可用**。故“代码不用改”仅指主要模型调用兼容性，不能忽略采购关系、凭据、发票路径和数据处理规则的改变，也不能把这次扩展说成全部音视频推理任务均已迁移。OpenRouter 对其 2026 年 10 月路由改造的**自家线上实验**报告容量错误减少 46%、TTFT（首 Token 延迟）改善 16.9%、吞吐提升 16.3%，但平均每次请求成本上升约 **6.0%**；这是 OpenRouter 自测效果，**不等于 Hugging Face 迁移后已独立测出同样改善或全成本下降**。OpenRouter 此次还宣布可向用户自有 Hugging Face Storage Bucket 导出请求／响应 traces；这是平台间观测数据整合，不表示默认保存或所有模型数据都获用户授权导出。

**对本题的实际增量与反证。** 一家已有模型 Hub、用户入口和自建路由器的大平台主动把**部分运行时职责**交给第三方，证明独立路由的需求不必因上游提供统一 API 而消失，也能与模型发现／账户入口分开；与 DeepSeek 的上游工具整合、Vercel／Cloudflare 的低价内置治理并列，说明**一体化和外包是同时存在的可选组织方式**，不是模型公司注定吞并所有中间层。仍需排除：Hugging Face 是基于合作补贴、长期运维成本、供应商接入广度还是短期战略选择；Hugging Face 无加价不等于 OpenRouter 没有收入，更不等于其有高利润。下一轮只有取得可核对的真实生产用量、合作结算、客户迁移／流失、净节约或各方权限与 SLA 对照，才可判断是否形成可持续独立价值捕获；目前可以论证“分工存在并被采用”，不能论证“抽成／利润池已经形成”。

**Claude Linked Billing（关联计费，2026-11-17 发布、11/18 核验）｜上游直接承接第三方模型用量结算的反例。** [Anthropic 原始公告《Linked billing on the Claude Platform》](https://claude.com/resources/articles/linked-billing-on-claude-platform)、[Claude Platform OAuth 官方技术规则](https://platform.claude.com/docs/en/manage-claude/oauth-apps/organization-billing-connections)和[第三方平台接入帮助说明](https://support.claude.com/en/articles/18467110-offer-linked-billing-in-your-platform)确认：合资格的终端客户通过 OAuth（开放授权）连接自己的 Claude Platform **API 计费组织**，无需交出自己的 API Key（接口密钥）；第三方平台运行请求，可逐请求设定由自己或客户支付，Anthropic 直接向客户计费。客户可按平台设置月度费用上限并撤销链接，平台可查看关联客户模型用量。**主要适用直接向 Anthropic 支付 API 费用的 Claude Console 组织**，并非 Claude 普通订阅额度、云市场经销组织或所有渠道自动可用。Beta（测试阶段）且支持范围有限：客户付款支持 `/v1/messages` 与 `/v1/chat/completions`，**不覆盖 Message Batches 与 Claude Managed Agents**，带单独收费 Code Execution（代码执行）的请求也不能由客户通过此规则支付；不能用“所有 Claude 用量自动由客户付款”概括。若客户不可计费，请求会失败，**不会默认替平台付费**。

**安全、归属与价值捕获边界。** 请求实际运行于**第三方平台的组织**，采用该组织的模型权限、速率、数据保留、加密和服务约定；客户组织的 IP allowlist、零数据保留、客户管理加密密钥等**不会因为关联付款而继承**。所以**账单直接结算 ≠ 工作负载归属客户 ≠ 安全责任自动迁移**，高合规要求须单独审核。平台依旧可以就工作流、治理、可达性与专业服务收费；Anthropic 直接计费则削弱“中间平台必须替客户保管上游 API 密钥并统一转售 Token”的必然性，**并不证明路由／运维价值被消灭，也不证明业务模式已产生新增收入**。官方合作平台名单只证明可用或承诺接入，未披露企业独立使用、净增需求、平台毛利、终端客户流失率。对照 OpenRouter 预付聚合／BYOK、Hugging Face 的统一客户端结算、Cloudflare／Vercel 云端网关治理与第三方平台自收服务费，应分开观察**谁签约、谁支付、谁执行、谁拥有控制权、谁承担责任及收费依据**；上游可以承接部分结算，但是否替代独立渠道，仍待同任务客户与经营证据。

**2026-11-18 新证据｜Perplexity Orchestrator 分开“选模型”与“选同模型推理提供方”（11/17 官方发布）。** [Perplexity 原始发布](https://www.perplexity.ai/en-GB/hub/blog/introducing-orchestrator)及[技术说明《Orchestrator: one API for reliable inference》](https://www.perplexity.ai/en-GB/hub/blog/orchestrator-one-api-for-reliable-inference)显示：它以单一 API／统一供应商账单提供专有与开放权重模型，支持 OpenAI Chat Completions／Responses、Anthropic Messages 请求格式与 SDK；组织可设置项目用量、模型允许列表和支出上限。厂商称**credits 之外没有额外平台费**，这并不等于调用无成本，也不披露实际平台毛利。**同模型提供方路由**依据健康度、容量、延迟，将失败请求重试到同一模型的另一部署；**Routes 自动模型选择为预览功能**，按任务描述选择不同模型或使用默认模型。两层决策不可混同，兼容 SDK 也不保证模型行为完全一致。官方称其自有生产层每天处理来自 **85+ 模型和十余家提供方**的请求，此为内部生产规模，**不是 Orchestrator API 同期公开模型数或外部付费客户规模**。

**效果证据、竞争解释与经济边界。** 技术说明把 **2026-10-04—11-02** 自身流量的请求成功率作为路由佐证，失败口径排除了客户端错误；这是**厂商自行测量**，未提供覆盖不同模型和全部成本的独立横评。与先前的 Hugging Face 向 OpenRouter 外包路由，以及已记录的 **Anthropic Linked Billing（平台执行请求、客户直接向上游支付）**构成反向三角：**路由权、合同签约方、谁付 Token、治理能力与平台服务费**可以不同方式组合。上游或大平台可将路由和结算打包、且标示无单独平台费，是独立平台收费的竞争反例；但多供应商维护和同模型故障恢复又是可供购买的具体服务。仍须同质量约束的端到端费用、请求恢复、迁移成本、分账、净利润和留存来判断独立价值捕获；**本轮未实际调用 API、核算供应商合同或生产验收**。Anthropic Linked Billing 已于本日另一轮补证，本次仅作引用，不重复新建材料版本。

**对既有核心论点的真实增量。** 11/13 本卡已证明模型上游开始直接**提供**搜索、抓取等工具；此轮新增的是**模型厂商可以通过 token 收费打包工具请求，而把获取独立结构化搜索结果／抓取内容的 API 继续单独收费**。因此“上游工具存在”与“上游如何抽取收入”不再混为一层：直接独立网关若只转售同质的模型内联网调用，单独收费空间可能受到挤压；跨上游模型选择／回退、原始结果控制、预算策略、隐私、透明度、责任 SLA 仍可能有实际付费价值。与 Hugging Face—OpenRouter 实际路由外包、Perplexity Orchestrator 统一账单、Anthropic Linked Billing 终端直付构成竞争组织方式对照。判断是否真的迁移利润，仍须同任务质量约束下核验模型端搜索／独立工具 API／第三方网关的**端到端费用、重试、人工纠错、成功率、独立客户采用及净利润**；本轮未调用付费 API 或做供应链审计。维持“可进大纲”的条件性成文范围，不重新建立同题卡。

**2026-11-22 新证据｜Together AI 11/21 原始安全公告证实提示词样本被第三方下载。** [Together AI CEO Vipul Ved Prakash《Security event: Prompt leakage for requests in June and July of 2026》](https://www.together.ai/blog/security-event-prompt-leakage-for-requests-in-june-and-july-of-2026)承认：公司为常规软件测试**经授权收集**部分 serverless 推理请求的提示词样本，存入**私有 Hugging Face 仓库**，主要涉及 MiniMax M3、GLM-5.2、Kimi K2.6 的 **2026-06-24、07-04、07-08、07-14** 请求。开发公开 GitHub `xorl` 仓库期间，**AI 编码 Agent 提交了私有仓库访问凭据**。自动扫描虽发现并回滚提交，但在暴露窗口内，未经授权者已取得凭据并**实际下载**样本，搜索并测试其中其他服务凭据；其中 **5 个被测试的凭据为 Dragos 实验金丝雀**。这是一条有厂商承认的事故链：AI 开发代理／凭据进入公开提交 → 私有测试样本仓库暴露 → 历史推理提示词被取走。不能误写为“推理模型自行泄漏全部用户提示词”，也不等于全部服务商都遭入侵。Together 表示已请外部机构取证并与执法方协作、尚未发现这次事件以外的额外泄露、目前没有理由认为下载内容进一步传播；**受影响客户数、样本数量、敏感个人信息或其他客户数据范围仍在调查**，没有独立证据保证数据已经彻底销毁。

**整改、研究背景及不同事故的证据界限。** Together 官方披露的动作包括短期／最小作用域凭据及可用时无密钥认证、对全部 PR 检测凭据、更新 AI 编码 Agent 开发流程、将 **ZDR（零数据保留）设为新账户默认值**。不能把“新账户默认”写成旧账户自动追溯修改，也不能仅据此次**获授权测试样本的存储**断言违反了受影响客户的 ZDR 合同。[Dragos 首席研究官 HD Moore《Three breaches, endless leaks: Your AI supply chain needs canaries》（11/19 原始研究）](https://www.dragos.com/blog/ai-supply-chain-security-canary-tokens)在五个月内投放近 **200 万条**带独特测试凭据／URL 的请求并观察被访问痕迹，揭示部分推理供应方及转售商风险；**200 万是主动测试规模，不是 Together AI 的泄露数，Dragos 未在原文公布三家受害提供商具体名称**。[OpenRouter《Data Processing Incidents on Inference Providers》（11/22 官方响应）](https://openrouter.ai/blog/announcements/data-processing-incidents-on-inference-providers/)说明其**未发现自身系统被入侵**，已下架三家提供商、移除 **125 个端点**的 ZDR 资格并通知潜在受影响客户；这些是推理平台主动处置的另一个证据，不等于三家都因 Together 事故被下架。

**对本卡的反证、已发表文章去向与可检验条件（项目判断）。** 既有 GateScope 关注 API 网关响应、账单透明度；此次事故补上**底层提示词的实际流向、授权留存、测试样本仓库和开发／CI 凭据供应链**这一曾缺少的真实失败路径。应分别检查客户端→分发网关→实际推理商→日志／测试仓库的处理主体、各跳 ZDR 与合同例外、内部人员／AI 编码 Agent 对凭据的访问和公有提交保护、发现后凭据撤销与客户通知。**可信路由与透明安全控制可能成为独立中间层的成本和服务价值，但未证其产生单独溢价或持久利润**。与已发表[《企业引入大模型 API，数据真的安全吗》](posts/enterprise-ai-data-security.html)重叠的是既有的厂商侧／员工侧风险分类；这次新增**供应商自身用 AI 编码 Agent 开发引发真实客户提示词暴露**，只作为旧文后续证据和本卡商业安全反证，不新增同题研究卡、不修改旧文正文。下一次有官方客户通知、外部取证、合同披露或赔偿结果时，可核实具体客户分母、ZDR 适用边界、责任归属与补救，不将当前未披露内容猜成已证实。未做真实客户日志访问或安全渗透测试。

**2026-11-26 安全与采购对照｜OpenAI Private Inference 进入少量客户测试，仍为 API Preview。** [OpenAI 官方《Private Intelligence》产品页](https://openai.com/business/private-intelligence/)、[兴趣登记页](https://openai.com/form/private-intelligence-interest/)及[2026-09-29 DevDay 官方介绍](https://openai.com/index/devday-2026-recap/)明确区分：**ZDR（零数据保留）**控制符合条件的 API 工作流在处理完成后是否保存提示词／响应；**Private Inference（私密推理）**拟通过 confidential computing（机密计算）及可验证控制保护模型处理**期间**的输入／输出；**ZDR 配合 Private Safety Processing**则针对自动安全审查与员工明文访问控制，是另一个独立机制。OpenAI 当前 Private Intelligence 页面明确标识“API Preview”；[Sam Altman 2026-11-25 本人公开发言](https://x.com/sama/status/2125638790593274259)称**正与少量客户进行 Private Inference 测试**，未给出试点客户、具体模型、价格、可用规模或公开发布时点。本轮可读的官方材料确认的是**产品设计目标和少量客户测试状态**，不是已完成覆盖全部推理路径的独立安全认证；不要把 Private Safety Processing 的隔离机制混写成 Private Inference 已验证的实现细节。

**与 Together AI 事故及既有价值捕获问题的分工。** Together AI 是**开发 Agent 暴露访问密钥导致历史提示词样本被实际下载的已证事故**；Private Inference 是**供应商试图减少推理运行期间明文可访问性的预览机制**。ZDR 不保证推理中无法访问明文，Private Inference 不自动解决日志、测试样本仓库、连接器、工具输出及用户侧存储，机密计算也不是无条件免于配置失误、供应链攻击或侧信道风险。采购前应取得可独立审计的**CPU/GPU 与模型执行边界、密钥生命周期、代码／固件测量与远程证明、客户验证的配置、故障降级、支持模型和地区、日志／安全审查例外、数据子处理方及合同责任**，并明确哪些能力实际上可以从客户侧核验；**本轮没有获取足以完成这类审计的技术证明或服务合同**。原[《企业引入大模型 API，数据真的安全吗》](posts/enterprise-ai-data-security.html)已讨论供应商与使用方两类风险，本卡仅补“运行时机密性 vs 处理后保留 vs 安全审查”三个正交控制层，研究它们能否形成客户可支付的风险削减价值；**没有证据证明已产生新增渠道利润或通用可信保证**。仅原位补证，不新建同题卡，不修改已发布正文或采购排期。

**商业条件与最强竞争解释（本项目推导）。** 独立平台可持续收费，需要其跨供应商选择、运行控制、可信比较和责任服务产生的客户收益，在相同质量与风险约束下超过平台费用和额外依赖；还需服务可重复交付，不能每个客户都重新投入等比例人工。Descript／Sentry 说明独立客户即使直签上游仍可购买第三方路由；Hugging Face 进一步证明已有自建路由与平台入口的企业也会把语言模型路由交给外部专业服务，但其经济条件尚不公开。Vercel／Cloudflare 说明同样需求可由云或开发平台低价内置；DeepSeek 说明模型上游也开始自行整合搜索、抓取与基础多模态工具，进一步增加独立中间层的替代选择。供方独有模型／专属算力、客户已有大额合同和权限要求会限制平台路由空间；平台自己的配置、日志、策略或数据若不可迁移，也可能增加客户锁定成本。**这是一组可检验条件，不是平台必胜或“越靠近入口越赚钱”的定律。** 反向指标包括客户绕过平台、治理能力被无加价替代、同等服务下付费溢价消失，以及高增长调用量未转化为净收益。

**成文边界与成熟度修正。** 原问题“能否成为独立价值层”保留，回答收敛为**哪些真实需求支持独立服务、哪些替代选择限制其收费与议价**，不是改成功能科普。新增具名客户、Hugging Face 实际生产服务链路整合与治理竞品，已足以支撑条件性分析和反向比较；此前将长期利润／留存缺失一律视作进入大纲的阻塞过严，现予修正。**“某平台已形成持久高利润”“百度已规范行业”“国内灰产比例”仍不能写**；这些更强结论仍须长期客户留存、净收入与成本、履约和合法供应链证据。

### BR-20261009-02｜为什么都重视招聘，有些公司却能形成持续的人才优势？

**创建：2026-10-09｜内容更新：2026-11-14｜状态：待补证（AI 企业的机制—结果链仍缺直接证据，公开论文访问已不是主阻塞）。**

**核心问题与当前判断。** “重视招聘”不是竞争优势的充分解释。应研究识别、吸引、角色配置、授权、协作与产出的连接，并考虑反向因果：业务机会、资本、算力、分发和股权预期本身可能吸引人才。早期字节与 Anthropic 的对照仍是待验证问题，不用成功企业自述拼成因果定律。新增研究方向是**谁有招聘决定权、拥有什么本地信息、承担何种激励与错误成本**，不继续用名人名单代替机制。

**11/07 已补足的公开层。** [Anthropic 招聘说明](https://www.anthropic.com/careers)、[Netflix Culture](https://jobs.netflix.com/culture)、[Amazon Bar Raiser](https://www.aboutamazon.com/news/workplace/amazon-bar-raiser)分别提供研究工程协作、授权与背景信息、独立于用人团队的招聘把关等制度样本。这些能证明公开机制，不能证明同口径人才绩效或谁全面领先。

人物例子作了校正：[Mike Krieger 2024 加入公告](https://www.anthropic.com/news/mike-krieger-joins-anthropic)与 [2026 Labs 公告](https://www.anthropic.com/news/introducing-anthropic-labs)支持其从产品领导转向实验性产品职责，不能说成降为普通工程师；[Anthropic 活动页](https://www.anthropic.com/events/claude-founder-house-san-francisco)列出 Bryan McCann 的 MTS 身份，但职称不自动说明职级与报酬。[Peter Bailis 报道](https://www.theinformation.com/briefings/workday-cto-joins-anthropic-amid-startups-push-build-hr-apps/)与 [Tom Blomfield 报道](https://www.businessinsider.com/anthropic-hires-monzo-cofounder-tom-blomfield-ai-compute-y-combinator-2026-7)属于媒体任职线索，不作效果证明。[Andrej Karpathy 本人资料](https://karpathy.ai/)没有提供本卡原先暗示的加入 Anthropic 依据，不能继续把他列作已证实的同类流动案例。

**11/14 补证｜招聘权配置的因果参照，而非 AI 公司排名。** [Hugh Xiaolong Wu、Shannon X. **原文新增的关键条件。** 这是 **2018-09-01—2019-08-31** 的实验，不是 2026 年 AI 企业数据；111 家营养品销售门店按既有销售、人数和面积分层随机为 **55 家处理、56 家对照**。处理组取得完整招聘决定权，HR 仍支持招聘平台与候选池；对照组并非绝无自主权，HR 未及时补缺时也可自行招聘。作者报告店级销售约增加 7%—8%，同时结果方差增加；§6.2 特别警告，简单零售筛选不能直接外推知识密集、技术评估复杂的招聘场景。研究支持有条件的决策权配置，不证明越分权越好。

**成文边界与当前阻断。** 原论文可读性问题已经解除。现在仍缺早期字节／AI 实验室同一案例中**招聘与配置制度→实际工作→可观察产出**的连接，以及资本、业务机会与选择偏差的处理。论文可支持一般机制条件，但不能替这些企业提供因果证明；MTS、招聘口号与名人流动不能补成持续优势。“20 倍产出”“Anthropic 全面反超”不是已验证数据。保留原问题，不为升状态改为纯零售管理题。

**下一步与责任。** 需要的最小新证据已明确：同一技术团队的选才／配置改变、真实工作过程和随后产出，并说明同时变化的资本、任务及算力条件；不是再凑一家成功公司。原文附录与图表仅在采用相关估计时定向检查，不要求作者购买或代查。待外部同案例过程材料，作者真实观察仅在愿意公开且影响判断时使用。与产业史组织篇保持局部关系，不替代企业边界研究。

### BR-20261009-01｜多 Agent 同时工作，产品该围绕什么组织工作？

**创建：2026-10-09｜内容更新：2026-11-26｜状态：可进大纲（已形成完整大纲确认稿；执行分工与人的审查、反馈如何对齐）。** 原始表达“文件 → App → 页面 → 操作”与“目标 → Agent → Context → 执行 → 验收”是启发性对照，不是普遍历史阶段；文件不会因执行者改变而自动消失。

**本轮启动与独立起点（2026-11-26）。** 作者选择“多 Agent 工作组织，启动推进”，授权接续研究；未确认具体主结论或正文写作。历史检索前保留的本轮起点来自截至 11/25 的既有研究：执行者、任务责任、正式成果与反馈适用范围可以不同；目标、预算、审批和验收不能由 Agent 数量代替；短期并行也属于研究范围。这些是开题已知，不包装成本轮新发现，也不将 AI 候选解释归为作者已接受的立场。

**核心问题与当前判断。** 一批工作开始由多个 Agent 同时推进后，人应按什么范围查看、审查和纠正，才能让一次判断准确影响相关工作？候选主结论是：**执行分工与人的审查不必沿用同一套分组；产品要同时考虑工作依赖、判断所需上下文和反馈适用范围，并让不同分组能够回到明确的任务、成果与责任。** Actively 的 motion 案例不是“后台不变、只换列表”：实际执行职责与审查对象都发生重组，按账户收集事实的职责仍保留。本文拟研究这些组织选择及可检验条件，不要求全部产品取消 Agent 视图、采用公共任务板或扩大人工审核。单 Agent 配合同样审查界面可能已经够用；人的注意力是否成为瓶颈及这种设计是否改善净交付，均不能由案例功能或代码基准直接推出。Agent 使用量、人类应用使用量与有效业务结果仍分开衡量。

**Cursor Multiplayer Projects（11/11 入库，11/14 与 11/26 定点核验当前文档）。** [Cursor Projects 官方文档](https://cursor.com/docs/agent/projects)确认多个团队成员可加入同一 Project，**每人保留自己的 coordinator 和 workers**，共用任务板与 Project shared context／Agent Store；个人 Store 仅供其个人 Agent 访问。跨 coordinator 消息被标为不可信 Agent 输入，不能据此越过个人文件、凭证或连接器授权；多人功能有账户、版本与仓库条件，须按采用版本判断。与 [2026-09-10 原始发布](https://cursor.com/blog/projects)的单人主协调器相比，多人模式新增团队共同状态、个人执行隔离和跨协调器消息。11/14 再核当前文档，同时区分 Project 一般可用套餐和多人共享条件，不能用其中一组条件代表全部功能；未把文档更新当作首次发布日期，也未验证净人时或冲突减少。11/26 进一步核对“Multiplayer Projects／How coordinators message each other／Context and your personal store”：跨协调器消息进入仅回答的旁支会话，该会话可读但不能改任务板，也不能申请访问或管理例行任务；把个人偏好复制成项目规则只复制本人批准的部分。它支持共同任务与个人授权分开设计，不证明文档已经解决所有共享上下文冲突。

**Goal Engineering 与 Actively AI 的反馈组织（2026-11-14 发布，11/15 入库，11/26 重验原文与官网）。** [LangChain《Goal Engineering: How to Design Goals》](https://www.langchain.com/blog/goal-engineering)由 Harrison Chase 与 Actively AI 的 Mihir Garimella、Anshul Gupta 共同署名。作者主张开放式 Agent 的目标／职责范围应与**人类专家容易审查、传递高质量反馈的工作范围**相匹配；理由是业务经验、表达偏好、何时采取行动等隐性知识通常不在文件与 API 中，必须通过人工审阅逐步传入 Agent。这是参与方的产品设计判断，**不是新的行业统一规范或自动提升模型权重的证明**。

**Actively AI 案例的机制锚点。** 第一版对每个潜在客户账户配置一名 Agent，以推进该账户为目标，产出销售动作供人工批准。参与方报告两项问题：①每个账户在某时点只需审核少量动作，销售人员在不同 Agent 间切换频繁；②外联措辞、回复策略、推进力度等知识对多账户共通，却分散于各账户 Agent，难共享反馈。第二版将执行职责按销售“motion”（动作类型，如外联、早期商机推进）横跨多账户组织，集中审阅相似工作，使针对一个动作的反馈便于迁移至后续同类动作；**后台仍有按账户收集客观资料的上下文 Agent**，具体执行时按需取回账户信息。由此提出的不是“业务对象被任务取代”，而是**正式业务对象、可复用动作、反馈审阅单元和最终成果可以采用不同组织尺度**。本项目可检验的增量假设：同等人类反馈时间下，相似任务的返工、重复错误与切换次数可能减少；这尚非已验证效果。

**反证与来源边界。** 原文没有给出切换次数、人工审查时间、质量、转化率或付费留存的前后量化比较，也未说明反馈通过提示、共享记忆、规则还是模型参数实现；不能将参与方说的“learn”理解成已经发生权重微调。[Actively AI 官网产品页（11/15、11/26 查阅）](https://www.actively.ai/)仍以 **Per-Account Agents** 对外介绍产品；此与共同署名文章的内部 motion 组织并非必然矛盾，但**不能据博客断言面向全部客户的产品架构和定价已经彻底切换**。按动作组织并非总优：客户级保密信息、不同销售者偏好冲突、专属账户责任和跨客户权限隔离可能阻止无条件复用。原文及官网均来自参与方，未独立实测或审计真实部署效果。11/26 补核 Gowri Harish、Sineha Manivannan 于 11/03 发布的 [《Why human insight is a strategic advantage for building better agents》](https://www.langchain.com/blog/human-insight-strategic-advantage-agents)，其“Principle 2”指出单条输出可能因早先对话或工具结果而错误，LangSmith 支持以完整 thread 审查。这是研发评估场景的边界材料：集中相似判断仍须保留个案上下文，不等于所有业务任务都应逐条阅读完整轨迹。

**Replit Missions（2026-11-17 发布、11/19 更新；11/19 入库，11/26 重验目标／审批／停止机制）｜将成果契约与预算约束纳入多 Agent 工作组织。** [Replit 团队《Introducing Replit Missions》（推出目标驱动的多智能体任务系统）](https://replit.com/blog/introducing-replit-missions)说明：用户首先描述**要达到的业务成果**，系统追问可验收标准（例如“首批十位付费企业客户”应以试点付款还是签订达到金额门槛的年合同计算），共同设定 Mission Contract（任务成果契约）；用户限制每次 Mission 的费用预算及需要审批的对外动作（如联系客户、发送提案、调整公开销售材料、作出产品承诺）。多个 Agent 可以并行调研客户、制作演示、准备获批外联，并依据后续反馈调整分工。用户可选择阻塞、进度和状态通知的节奏；**独立 AI Judge（AI 验收器）**检查约定标准、引导迭代，达到标准即宣告完成，**预算先耗尽则停止而非视为成功**。这是产品公开机制，**不是“系统能自主完成真正有价值的业务经营”已获证明**；验收器可能错判，商业回款、合同责任、客户留存仍需正式业务系统与人类核实。

**DataCat 的实际工程案例及重要限制。** Replit 团队称使用 Missions 在**两天内、3000 美元预算上限内**构建了自托管监控工具 DataCat，包括监控界面、告警和链路追踪。模拟数据库故障的告警时间为**38 秒**（目标 60 秒），三小时负载测试处理**2600 万条活动记录、440 万条日志**且报告无数据丢失，**36 项数据准确性检查＋15 项告警可靠性检查全部通过**。另设独立 API 兼容性测试，DataCat 的存储引擎每种为 **51/56**，采用同初始提示通过 Claude Code `/goal` 构建的对照为 **45/56**；二者是**不同测试套件**，不能把 51/51 与 51/56 混为全部系统正确率。构建对照每个配置仅运行**一次**，指标只覆盖双方共享能力；结果未证明胜过原监控平台的**正式托管服务**，也未验证 Replit 企业客户长期部署的全成本／维护效果；“3000 美元预算上限”不能冒充确切已支出金额。以上是 **Replit 自行构造、测试和披露**的结果，不是第三方独立横评。

**Replit Missions 的既有研究判断与反证（本项目分析）。** Replit Missions 与 Cursor 的项目／执行协调器、LangChain／Actively AI 的反馈分配形成对照：**任务如何被并行拆解、成果如何被正式定义与验收、何时需要人批准、预算耗尽时怎样保持未完成状态**，可以是独立于 Agent 身份与前端视图的设计变量。多 Agent 数量本身不证明更高有效吞吐；在客户拓展等非完全可重复任务中，AI 评分器即使宣布达标，也可能无法代替真实收入、用户同意、正式业务状态及风险审核。用 DataCat 说明**可运行测试较易明确的工程任务**，用“获得付费客户”作为**尚未提供真实客户结果的产品示例**；不要把软件基准的成绩外推为真实销售 ROI。下一步需要在同一目标、授权、质量与资源条件下，比较单 Agent、多人 Agent 和常规团队的完成率、人工审批／纠错分钟、超预算／误操作、最终业务结果、执行时间与总成本；如无可复验对照，最多讨论产品机制，不能宣告新组织形态已经胜出。

**Optimization-Bench｜多 Agent 规模效应的定量补证（Replit 2026-11-19 原文；11/25 入库，11/26 重验原文与统计政策）**。Replit 工程团队 [《Throwing Headcount at the Problem》（增加执行者能否解决问题）](https://frontier.replit.com/throwing-headcount-at-the-problem/)发布 [Optimization-Bench 开源测试仓库](https://github.com/replit/optimization-bench)：初版公开 **14 项开源软件性能优化任务**，研究文章重点分析 **NumPy（13 个工作负载）、SQLite（12）、SQLGlot（4）、Git（7）**；每个 Agent 配有 **8 vCPU、16 GiB 内存、2 小时执行窗口**，比较单 Agent 与 **8／16／32** Agent 团队，测试六款模型。Agent 各自处在隔离环境，只共享代码仓库和任务板／消息；协调者仅获目标、**没有预设协作策略**。独立评测器在隔离机器重建、检查公开与隐藏输入的正确性，交错测量相同工作负载性能，尝试防止只为刷分而更改输出或计时。**同为两小时不是同等资源：团队拥有更多 Agent、沙盒和模型调用额度**；这里评价的是优化后软件的性能收益，不是团队单位成本或总体生产力。

**关键数字与反向案例（Replit 自有实验，未在本项目独立复现）。** Claude Opus 5.5 在 NumPy 13 个工作负载上的**软件运行加速比中位数，单 Agent 为 3.66 倍**，32 Agent 时为 **18.92 倍**（分母均为原始程序耗时）；这里不能把 18.92 倍说成“32 Agent 相对单 Agent 的成本效率增益”。GPT-6.2 Astra 的**单 Agent 在四个指定代码库表现最强**，但集群在约 **8 Agent** 达到较好表现，扩大至 32 Agent 后，NumPy、SQLGlot、Git 上反而低于自己的单 Agent 成绩。Git 工作负载集中在**同一 15 个文件**，并行修改冲突强，即使增加团队也未像 NumPy 一样提升。Replit 观察到 Opus 5.5 约 **82%** 的消息发至**共享任务板**，GPT-6.2 Astra 的共享板消息比例**低于 40%**，其执行者平均向协调者发送约 **15 条直接消息**；这些是**行为相关性观察，不是“任务板导致性能改善”的单变量因果证明**。最好团队在共享状态里领取任务、记录失败与结果，而协调 Agent 主要负责分配和合并；表现较差的团队过度向中央协调者发送消息，形成等待和信息瓶颈。

**扩展实验的研究判断与可证伪路径。** 过去 Cursor／Vercel Board 强调“共享状态可以实现”，Replit Missions 强调“目标如何定义”，Actively AI 强调“反馈归属”，本次进一步得到**执行者人数 × 任务可拆分程度 × 协调拓扑 × 模型行为**与**成果质量**之间的限定条件。单体模型最强不代表集群扩展性最强，多个 Agent 不必然比一个 Agent 好。下一步最有价值的是在同一任务／模型／资源或总费用条件下**控制任务拆分与通信拓扑**（公共任务板、中心化直接消息、分层协调），比较**同成本有效性能、重试／冲突、人工验收时间与错误率**，并将多次随机重跑与跨非编码任务泛化作为检验条件。当前只支持“在这些受控代码优化任务中，协调方式与负向扩展值得研究”，**不证明所有知识工作中的多 Agent 都有净收益，也不把测试仓库公开当成已完成独立复制**。

**扩展实验的统计与竞争解释（2026-11-26）。** 核对 Replit 开源仓库提交 `c119e10b36b824a244ee01aa879b99ebfccf5bc8` 的 [statistics-policy.md](https://github.com/replit/optimization-bench/blob/c119e10b36b824a244ee01aa879b99ebfccf5bc8/docs/statistics-policy.md)：默认 5—15 组配对计时用于估计程序性能噪声，不能充当 Agent 独立运行重复数；仓库评分公式与文章图中的中位数也不能混用。正文未充分披露每配置独立重跑及完整费用，未做本项目复现。由不同团队完成的 [Kim 等《Towards a Science of Scaling Agent Systems》v3](https://arxiv.org/html/2512.08296v3)（版本日期 2026-04-08，本轮首次核验）以 260 配置、6 基准、5 种架构比较：§4.2 中 PlanCraft 跨模型平均成功率单体 0.568、中心协调 0.282，Finance-Agent 却由单体 0.349 升至中心协调 0.631。该对照反驳“中心协调一定拖累”，不构成 Replit 复现或真实业务净收益证明；勿混用早期博客的 180 配置。论文独立并行的末端拼接策略、有限基准与跨基准统计稳健性，限制普遍外推。两份实验只给本篇提供任务／协调边界，不据此宣称某种审查界面优越。

**Linear 人与 Agent 双使用曲线（2026-11-22 核验）｜成熟 SaaS 中 Agent 创建任务后，为什么人仍回到工作系统？** [Latent Space《Scaling Linear’s GTM to $100M ARR — Cristina Cordova, COO》（2026-11-19 23:38 UTC 发布，Cristina Cordova 为 Linear COO）原始 Podcast](https://podcasts.apple.com/us/podcast/scaling-linears-gtm-to-%24100m-arr-cristina-cordova-coo/id1674008350?i=1000803024910)在约 **18:15—26:40** 讨论 Linear 从传统事项追踪到 Agent 驱动产品开发系统的定位：Cristina 认为被淘汰的应是大量**人工创建、分派与维护工作状态**，不是 Issue（正式工作事项）本身；如果只把 SaaS 变成 Agent 访问的数据库／MCP 接口，原有的人类共同工作、状态可视化与协作价值可能被边缘化。她表示团队关注 **Agent usage（代理使用量）与 app usage（人类应用使用量）**，且 Linear 内部观察二者都在增长；这是受访管理者**未披露完整分母／时间序列的观察**，不等于行业平均规律或新收入因果证明。仅核对节目公开页面、章节及有关材料；**本轮未完整逐字听写整期音频**。

**独立可回查的公司数据口径与实际产品机制。** [Linear 创始人 Karri Saarinen 2026-08-26 官方公告](https://linear.app/now/sharing-growth-with-the-people-building-linear)自报：95% 的**付费工作区已安装 Agent**；Agent 产生的**新工作事项占比由一年前约 3% 升至 50%**；同期 Linear 已超过 **1 亿美元 ARR、4 万家付费公司、177% NRR（Net Revenue Retention，净收入留存率）**。上述数值是**8 月披露**，不写成 11/19 新数据；安装≠实际活跃、事项创建≠被执行或完成、NRR 与 ARR 均**未拆出 Agent 的可归因贡献**。[Linear 官方 Agent 产品页](https://linear.app/agents)与[Agent 平台文档](https://linear.app/docs/agents-in-linear)确认 Agent 能被委派事项、评论和参与项目，团队仍可查看代理活动和任务状态，具体能力依安装授权；第三方 Agent **不能直接进入管理界面或管理用户**。这些来源说明**Agent 与人可以使用同一份正式工作对象，但执行权限并不相同**；不代表代理可替代全部人类角色。

**研究增量、对照与最强反例。** 与 Cursor 的多协调器／共享任务板、Actively AI 的按动作组织反馈、Replit Missions 的成果契约与预算不同，Linear 代表**既有商业规模 SaaS 中人机共同使用一套正式任务状态**，适合评价：代理创建事项增加时，人类究竟是更多使用共享系统做审查、协作和验收，还是逐步只保留外部代理入口？**需要区分事项创建数／代理安装率／真实生产完成率／人类应用活跃与协作深度／付费和续约**，并在同团队、同时间窗检验其关系。可能的反例是代理大量创建重复、低价值事项，或者人类 App 使用来自其他功能与客户增长，而非 Agent；甚至代理渠道增长削弱原软件的独立收费能力。Linear 公司指标、访谈与其产品文档不是三组独立经营效果实验，**尚不能证明 Agent 扩大了有效交付或导致 177% 留存**。与已发表[软件操作者文章](posts/ai-software-operator-shift.html)和[SaaS 买建文章](posts/ai-saas-build-vs-buy.html)的分工：旧文已经讨论入口迁移与软件可替代性，本卡只研究**人机共同工作时的事项、责任、验收与两类使用曲线**，不重写 SaaS 是否会消失的宏观题。

### BR-20260930-02｜从定制 GPT 到 Plugins，能力如何被持续复用

**创建：2026-09-30｜内容更新：2026-11-28｜状态：待补证（MCP 工具／技能交付与 SkillPay 买断／周期付费机制已核；真实推荐渠道付费、复用和留存仍未证）。**

**核心问题与用户确认的研究主线。** 第三方交付什么能力，用户或 Agent 怎样发现、持续调用，维护成本、客户关系和收益归谁？2026-11-12 用户确认将 Resend 访谈引出的三问作为同一主题递进，不拆成三篇：**①分发入口**——Agent 是否成为 B2B 新入口，开发者意图与实际选型怎样相互影响；**②产品适配**——Agent Experience 能否成为独立设计能力，文档、接口、授权与恢复怎样决定正确持续使用；**③商业价值**——推荐调用是否转成新增付费、留存和净收益。链路是**谁选软件→软件能否被正确使用→供应商如何获收入**；第三问是最终商业验证，不以前两步替代。

**当前判断与待验证因果链。** GPT／Plugins 分发迁移、Resend 被编程 Agent 推荐以及 MCP 服务端联合交付工具／领域技能／长期任务，分别是**平台分发、Agent 选型及服务商能力交付**的不同机制；不能仅因均被 Agent 调用就认为收入模式相同。必须区分**首选推荐→接受／集成→生产成功与复用→付费扩容→留存与净收益**，排除只是替换既有选择或本来会发生的购买。**接入／API 调用成功不等于最终用户任务成功**，即使任务验收通过也不等于带来净新增收入。承载方式迁移不等于旧客户与收入完整迁移，GPT Store 热度感受也不是失败证据。

**既有 OpenAI 官方机制（2026-11-07 首核；11/16 重核迁移 FAQ 与外部套餐说明，未逐项重验历史发布文）。** [Custom GPT migration FAQ](https://help.openai.com/en/articles/20001519-custom-gpt-retirement-and-migration-faq)仍列默认退休日期 **2026-12-11**；符合条件且获准延期的 Enterprise／FedRAMP 可至 **2027-02-11**，并非所有企业自动延期或 11 月已关闭。[第三方使用 ChatGPT 套餐说明](https://help.openai.com/en/articles/20001542-using-your-chatgpt-plan-in-other-apps-and-sites)截至 11/16 已包含 **Go／Plus／Pro／Business**。Business 受管理员权限与工作区额度限制，Standard／Premium 成员有受工作区控制的包含用量，usage-based 成员仅能使用获授权的工作区 credits；应用自身套餐要求与收费仍独立。套餐可用不等于上下文全共享、免费无限算力或全部开发者获准。历史机制保留：[GPTs](https://openai.com/index/introducing-gpts/)、[GPT Store](https://openai.com/index/introducing-the-gpt-store/)、[应用提交](https://openai.com/index/developers-can-now-submit-apps-to-chatgpt/)、[Plugins changelog](https://developers.openai.com/plugins/changelog)、[DevDay 2026](https://openai.com/index/devday-2026-recap/)。它们证明机制变化，不证明持续使用收入。

**2026-11-12 访谈证据与反证。** [Latent Space《Designing for Agents — Zeno Rocha, Resend》（2026-11-10，嘉宾为联合创始人兼 CEO）](https://latent.space/p/resend/)在 11/12 核对官方单集页编辑整理、章节与链接，尚未逐字复听录音／核对完整文字稿；11/14 补读材料不冒充重听节目。

1. **分发／选型。** 主持人 Swyx 表示自己已有 Cloudflare 邮件服务偏好，但 Agent 经常建议 Resend（**5:02** 起、**1:06:00** 推荐讨论）。引用研究在 **102 次可提取的邮件推荐中，Resend 首选 64 次**；另一轮多模型测试 Postmark 多数居首。它们是限定条件的模型结果，不是市场份额、接入或付费。[Latent Space 多模型 AEO 测试](https://aeo.latent.space/)沿用节目记录，未完成同条件复现。
2. **产品适配。** Zeno 讲 React Email 进入代码库，以及定价 JavaScript 滑块不便机器读、补 `.md` 表格（**23:55、58:28**）。录制时 MCP 工具约 **80+**，可查用量账单等；主持人对比 Cloudflare Code Mode 两工具设计（**37:55**）。过大返回占上下文，说明工具数与返回大小是两个变量，不证明 80 或 2 工具普遍更优；授权与恢复效果仍需测量。
3. **商业归因。** Zeno 当时自报约 **430 万用户、12 万付费客户**，是公司总量，不说明这些客户来自 Agent，也不证明 AEO ROI、留存或利润。编辑整理、主持人测试与公司自述各有不同证明力，不能拼为已证因果。

**11/14 原研究方法复核。** [Amplifying 完整报告](https://amplifying.ai/research/claude-code-picks/report)为 **2026 年 2 月**研究：三模型、四类初始项目、20 类工具、2,430 次响应，其中 **2,073 次可提取首选**；邮件为 **135 次响应中102次可提取，64次选Resend**。提示不指名品牌但代码库／语言限制选择，由 Claude 自提取有判读偏差，未提取不全是失败；另有 DIY 不买第三方的反例。[Resend 分项](https://amplifying.ai/tech/resend)显示不同项目条件偏好不同。它不是开发者总体抽样，不同月份／模型测试不可拼市场份额；研究方有相关商业服务，方法可查不等于客户转化审计，未重跑代码。

**11/14 官方实现与经营边界。** [Resend《The Headless Dashboard Initiative》（9/22，Zeno Rocha）](https://resend.com/blog/headless-dashboard-initiative)说明大部分原 Dashboard 操作已可经 API／CLI／MCP 调用，包括 webhook 查询重放、签名轮换、取消广播和复制默认未启用的自动化草稿。全面复核再读确认其同时承诺继续做好人类 Dashboard；机器接口不等于 GUI 必须退出，支持恢复与管理也不证明完全覆盖或可随意授权。[《3,000,000 users》（6/03）](https://resend.com/blog/3-million-users)自报三百万用户、从上一年起盈利及 Agent 接口投入；不是独立审计，更未拆分 Agent 推荐渠道的付费、留存或利润。不能将不同时点用户总量、SDK 下载和盈利拼成渠道因果。

**Agent 使用体验端到端验证（2026-11-18 核验）。** [Vercel 原文《Agents are users, so your software needs evals》（George Fahmy、Yury Selivanov，2026-11-16）](https://vercel.com/blog/agent-evals)提出供 Agent 使用的软件可按 **Discovery（发现）→Selection（选择）→Access（接入）→Success（任务成功）**分阶段评价，作者文章重点针对最后一阶段；对确定性测试／单轮模型判断／端到端（E2E）任务测试分层。以**虚构的咖啡订购 CLI**解释：工具调用返回成功，但可能将冰拿铁买成热饮、超含税小费预算或违反取餐时间；必须在可重放任务环境中核对**订单最终状态及所有约束**，而非仅看响应代码。设计任务时覆盖常规、边缘及“正确动作是不下单”情形，独立保护初始数据与验收器，防止 Agent 绕过接口直接修改答案文件来刷分。**这一整套示例属于作者设计的教学情境，不是咖啡商家生产测量结果**。

**指标口径与反证。** [同一原文中的评价指标](https://vercel.com/blog/agent-evals)明确区分 **Pass@k（k 次尝试中至少一次成功，能力覆盖）**与 **Pass^k（连续 k 次全成功，重复可靠性）**；在单次成功概率 60%、各次独立的示意设定下，k=5 分别约 99% 与 8%，**不是某家软件在真实市场的通过率**。可重试的软件编码测试更看重“经过尝试能不能成功”，有付款和不可逆副作用的真实商业动作更看重连续可靠、误操作次数及补救成本。文中失败尝试同样有费用，所以示例里每次成功尝试平均成本与计入失败尝试后的平均成功成本并不相等。需要保护验证器免遭 Reward Hacking（奖励投机），并报告样本量与任务分层，不能把五次全通过解读为零失败率。这为 Resend 的**第二问：怎样让 Agent 正确使用产品**补出可执行指标；但 Vercel 的教学评测没有提供**第一问的真实供应商推荐转化**或**第三问的新增付费与留存**，亦不能证明 Agent 体验改善必然带来收入。

**Skills over MCP｜第三方服务交付领域技能、长期任务及审批（Anthropic 2026-11-24 发布；本轮 11/25 核验）。** [Claude 官方《MCP servers can now ship skills, run tasks, and more with Claude》（MCP 服务可提供技能及执行任务）](https://claude.com/resources/articles/skills-over-mcp-tasks-and-more)和 [MCP Skills 正式扩展规范](https://modelcontextprotocol.io/extensions/skills/overview)确认：服务端可声明并提供 **Skill（领域工作流程指令和支持文件）**，客户端按元数据发现并在需要时加载 `SKILL.md`；用 Skills 补充“怎么正确使用工具”的知识，而不是只暴露函数名。**服务端技能随服务更新**，有利于同时交付工具与专业流程（官网列 Shopify 店铺设计、HubSpot 客户入驻等案例）；但**读取指令文件本身不意味着自动激活**，客户端仍需验证来源、执行适当审批和选择加载方式。MCP 规范中 Skills 扩展已正式定稿，**Claude／Claude Code 当前使用体验仍处公开测试，客户端 SDK 与 Host 支持尚不完整**，不能写成所有 MCP 客户端已普遍兼容。

**从单次工具调用到任务委托。** [MCP Tasks 规范](https://modelcontextprotocol.io/extensions/tasks/overview)支持服务端返回持久 `taskId`，客户端可轮询／监听任务状态，断线重连后继续获得结果；Elicitation（执行中请求用户输入）允许在成本确认或破坏性操作时暂停向人请求必要信息（官方案例包括 Supabase 付费项目、Railway 服务删除、GitHub 删除仓库时输入仓库名）。**Tasks 与 Elicitation 在 Claude／Claude Code 已正式开放**，组织计划仍在逐步推出；**File Uploads（文件上传）在 11/24 公告中仍是“即将推出”**，不可当作已在全部客户端交付。Tasks 的取消是**协作式取消而非保证终止执行**，状态／审批协议也无法替代正式业务系统的资金、删除和账号权限硬控制。MCP 从“工具连接”扩展到**领域知识交付→耗时任务承接→执行中请求人类授权→结果返回**，这是产品和协议能力，不证明完整业务已经自动成功。

**对用户确认的三问的实际增量。** ①发现／选型：服务可将技能与工具在同一入口供 Agent 发现，但需要观察 Agent 是否真的优先选择该服务；②产品适配：供应商可以更新机器可读操作流程并提供任务状态、审批中断及最终结果，减少客户端单独维护流程规则的负担；③商业价值：**目前没有同口径客户转化、独立 SaaS 付费与长期复用数据**，不能凭协议功能和官方伙伴名单认定生态收益形成。**最强反证**是客户端实现差异、第三方技能来源和版本更新的提示注入／权限风险、重复封装专业流程的维护费用，以及内置工具或确定性工作流足以完成的场景；可检验“同一客户任务”在**只接 MCP 工具／工具＋服务端 Skill／外部托管 Task**三种方式下的发现率、首次成功率、重复可靠性、人工干预、上下文消耗、总成本与付费转化。与已发表[《Skill 系统的本质：不是 Prompt 工程化，是 Harness 的支撑》](posts/skill-system-and-harness.html)的关系是具体协议／服务交付机制补证，**不在本卡重写 Skill 基础原理，也不为单次扩展新建研究卡**。

**2026-11-28 新的“能力成为商品”证据｜支付宝 SkillPay 的权利与交付方式（本轮核验官方产品说明、FAQ 和公开教程）。** [SkillPay 官方首页／交易及常见问题](https://skillpay.alipay.com/)、[支付宝 AI 付产品分类](https://aipay.alipay.com/docs/overview.html)及[支付宝 Skill Pay 教程（2026-10-25）](https://aipay.alipay.com/article/6170)已说明两种不同的商品权利：**买断**时，消费者付款后获得 Skill 的**明文／最新版 ZIP 文件**，可在允许的 Agent 执行环境中自行安装；**周期付费**只授予**有效期内云端 Skill 使用权**，默认使用有效期内的最新版，不向消费者交付 Skill 明文，**当前不自动续费**，因此不能在商业模型中把“周期付费”直接等同自动续订 SaaS ARR。商户上传后须经平台安全检测，通过后上架；Agent 展示商品和价格，**用户本人确认付款**，成功后相应权利交付，款项据官方说明**直接实时进入开发者支付宝账户，不经 SkillPay 中转**。官方列出 WorkBuddy、豆包工作、千问办公、Cursor、Codex、Claude Code 等兼容环境，但其说明仍有**客户端适配／本地沙盒写文件／操作审批**要求，并非任何 Agent 均可无权限安装执行。平台安全扫描是上架检查，不能推断所售代码、后续更新、云端执行及支付安全绝对无风险。

**案例来源与保真限制。** [数字生命卡兹克／Khazix 2026-11-27《实测支付宝 SkillPay：手把手教你怎么把 Skill 挂上去卖钱》](https://mp.weixin.qq.com/s/x7Yt237NPL-sLvkUJlwESw)由 [AIHOT 的具体收录事件](https://aihot.news/items/vbxvfko8cyziqerevtyofz5wx)记录了创作者实操及平台定价、周／月／季度周期和试用设置，但**微信原文当前无法直接读取**；其中“买断 0.01—50 元”“平台服务费免收／即刻收 1%”“最低五次试用”等细节仅来自 AIHOT 对作者的摘要，**本轮官方公开 FAQ 未完整确认这些数值与适用套餐、费率条款**，不当作全平台稳定规则，也不从它们反推平台实际抽佣收入。官方页面所示“支付宝到账 30 元”为**营销演示**，不等于已核实真实商家总体成交额、付款转化、平台流水、退款或开发者净收益。新闻传播与正式产品起始时间不同：官方文档在 **2026-10-12** 已概述 Skill Pay、官方教程日期 **10-25**；**11-27 的新信息是第三方实操整理，而非 SkillPay 首次推出或市场首次出现售卖模式**。

**与既有技术分发和支付研究的真实差异。** Skills over MCP 解释服务端**如何提供可发现、按需读取、持续维护的领域工作流**，但不负责已经落实买卖和开发者收款；SkillPay 则把**商品上架／身份审核→Agent 发现商品与展示价格→用户逐次确认支付→权益交付与版本更新／退款**串成可观察的交易接口。与 [BR-20260930-05 的 Agent Pay 消费支付](#br-20260930-05)分开：Agent Pay 负责用户代表性购买已有商品服务，**SkillPay 的商品就是供 Agent 使用的 Skill**；与 [BR-20261114-01 Token／网关平台](#br-20261114-01)分开：Token 用量计费或机器 API 按次支付不等于买断 Skill 代码或租用云端领域工作流。进一步要区分**所有权／明文交付和可迁移性、版本维护、受限授权的云端服务、开发者和平台安全责任**；这种交易机制证明能力可被商品化和结算，不证明第三方能力分发已在真实市场形成可持续平台利润。未来只有获得可审计的**曝光→推荐→安装／购买→任务实际调用→成功交付→复购／续期→商家净收入／退款及平台费用**同口径队列，才能解除本卡商业渠道归因的核心阻断；还需对比免费开源 Skill、自建工作流、直采 API 等反例。本文主问题和“待补证”状态不变。未登录、安装、上架、付费或发起真实交易。

**成文边界与阻断缺口。** 已足以作为 Agent 参与 B2B 选择、产品适配机器读写／技能获取、长期任务委托与用户任务端到端验收的机制案例；用户确认的完整商业链仍缺**推荐→真实集成→生产复用→付费留存**归因。建议的检验分母已明确：推荐中的首选率、被推荐项目中的实际接入率、接入项目中的生产活跃率、活跃客户中的付费与续约率不可混用；还需原渠道和原需求基线。受控项目安装不等于生产，公司盈利不等于该渠道盈利。暂不靠删第三问升状态，也不拆三张卡。

**下一步与责任。** SkillPay 已给出“代码买断／云端当期使用权”不同的收入与控制机制；若要判断生态经济价值，先要求实际同口径的商品曝光、支付和后续复用／续期、退款与净收入，不得用安装演示或宣传价格代替用户真实付费。公开材料已核到可复验的使用体验方法与 MCP 扩展公开规则；下次出现真实 SaaS 使用研究时，AI 可对照**仅工具、工具＋技能、委托长任务**在同任务中的发现、安装／认证、最终状态、重复成功率、权限／版本风险、上下文占用、成本和人工纠错，注意错误后果及适配客户端范围。商业主线仍以可核对客户来源、生产调用与付费续约队列为下一实质触发；核验能否排除原有开发者需求和渠道替换，不再增加同类推荐榜。没有真实 API 调用或本项目运行的评测，不声称成功率；缺商业归因时只报告机制与未知，不包装 AEO ROI。不要求作者提供企业账本或重复批准普通检索。

### BR-20260930-03｜Agent 成为操作者后，哪些产品设计价值会变化？

**创建：2026-09-30｜内容更新：2026-11-07｜状态：已归档（合并承接）。** 2026-11-14 仅迁移状态名称；原合并判断、日期、ID 和去向保持，不伪称本轮重新研究。

**原问题与本轮判断。** 菜单、No-code、多维表格、模板、Dashboard、Eval 并非同一层级，不能逐项机械判生死。本轮核对[已发布软件操作者正文](posts/ai-software-operator-shift.html)：任务范围、正式对象与状态、权限、观察恢复、人工操作退出／入口迁移／软件退出，以及长期约束与当前实现的区分均已展开。继续写泛产品价值会高度重复。

### BR-20260930-04｜持续委托的真实需求、净收益与商业可持续性

**创建：2026-09-30｜内容更新：2026-11-12｜状态：已转入（2026-10-18 已发布）。** 当前成果为 [Personal Agent 文章](posts/personal-agent.html)，不是仍待启动的候选。后续缺口不等于原文章未完成。

**核心问题与当前判断。** 长期价值是跨时间接续未完事务、跨服务与不同的人协调，让用户少记挂、少催办，而非仅有记忆或定时按钮。必须计入交代、授权、检查、接管与纠错的总投入；单次有用不证明长期净收益，融资、GMV、用户热度不证明收入或利润。个人生活、个人工作、组织岗位和付款方分别判断。

**已发表案例与稳定边界。** 文章已对照 Dots、Muse、Gemini Spark、Grok Bot、Manus Cue、Instinct。保留[Dots 官方入口](https://openai.com/index/introducing-dots/)、[Muse](https://about.fb.com/news/2026/09/introducing-muse-personal-ai-agent/)、[个人 Spark](https://blog.google/intl/zh-tw/products/devices-services/gemini-spark-ai/)、[Grok Bot](https://x.ai/news/introducing-grok-bot)、[Manus 2.0／Cue](https://manus.im/en/blog/introducing-manus-2-0)、[Instinct 创始人原始访谈](https://colossus.com/episode/instinct-the-personal-agent/)供后续复核。组织 specialist dots 当时为试点；个人 Spark 不等于企业 Gemini；Cue 不等于 Manus 主产品改名；多个 Grok Bot 共用同一用户环境不代表彼此完全隔离。上述产品详细时间线与当时付费方式沿用原核验记录，本轮未逐项刷新。

**用户重点仍有效。** 比较“服务谁、谁付款、通过什么机制收费”，不以绝对订阅价格为主线；消费者使用而商家付费可以并存。订阅不自动保证目标一致，佣金也不自动证明损害用户；需要检验“不买、退款、取消”能否获得同等服务。Instinct 创始人年化交易额和留存说法均为自述，不代替抽佣或审计收入。

**正反证据保留。** [Daminger 认知劳动研究](https://journals.sagepub.com/doi/10.1177/0003122419859007)支持执行之外还有记挂与协调，不证明 AI 已减负；[Shortcuts](https://developer.apple.com/videos/play/wwdc2019/213/)和[混合主动交互研究](https://www.microsoft.com/en-us/research/publication/principles-mixed-initiative-user-interfaces/)反驳持续触发都是 LLM 新发明。[长任务工程复盘](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)说明状态与验证可接续会话，不要求永久同一模型进程。[WIRED 亲历](https://www.wired.com/story/i-finally-found-an-ai-agent-worth-the-risk/)、[The Verge 试用](https://www.theverge.com/tech/1008254/instinct-agent-ai-hands-on-muse-dots)、[用户限制授权的采访](https://www.businessinsider.com/early-users-delete-personal-ai-agents-privacy-scares-blunders-2026-10)是局部使用与失败样本，不提供总体留存率。

**经营与退出边界。** 10/14 已核的 [Character.ai 公告](https://blog.character.ai/an-update-on-character-ai/)、[Reuters 报道](https://www.reuters.com/legal/litigation/characterai-files-bankruptcy-agrees-sell-some-assets-disney-20-million-2026-10-13/)与[法院经营材料报道](https://www.404media.co/character-ais-bankruptcy-documents-show-the-economics-of-ai-dont-work/)用于说明高参与度不等于健康单位经济，不外推所有消费 Agent。早期 Lensa、AutoGPT、Humane、Ohai、OpenClaw 等对照、六款产品逐项来源及历史方案留在页首不可变 Git 记录；它们不是已验证的失败概率或长期 ROI。尤其[OpenClaw 创始人说明](https://steipete.me/posts/2026/openclaw)不能改写成 OpenAI 买下公司。

**2026-11-12 反方论点补证｜朱啸虎对 Personal Agent 的五层质疑。** 来源为 [《硅基立场》Vol.35 节目原始页（11/11 上线；重点 07:19、11:29）](https://www.xiaoyuzhoufm.com/episode/6af147dfb4a4e20202f6ebed)与[硅星人整理、凤凰网转载的 ACC 2026 对话实录（10/21 现场，10/22 刊出）](https://feng.ifeng.com/c/8xQbgQ8sJJI)。这是一位投资人的**反方商业判断与待验假设**，不是已证实的市场结论，也不等于“所有个人代理任务都没有价值”。

1. **需求前提：普通人不需要专职秘书。** 朱啸虎以大多数人没有秘书、自己有秘书但几乎不用为例，反问普通消费者有什么需要长期交给 Personal Agent 的事务。**待反证：**“不雇人类秘书”究竟是缺少需求，还是人力价格、委托门槛使需求长期未被满足？要考察用户实际主动交出的事务与替代行为，不由职业身份推断需求。
2. **频率与留存：旅游等场景太低频。** 他称 Muse 约 **50%** 的使用场景为旅游，而普通人一年仅旅游两三次，因而难以形成可持续的大型创业机会；同时预测 Muse 留存会差，并援引十年前“来也”等产品转向打车、外卖及补贴的历史印象。**证据边界：**“50%”、旅游频次、历史业务转向及未来留存均为访谈陈述／判断，本轮没有找到可以替代它们的独立产品明细或同口径留存；不能写为已核实的总体事实。**待反证：**低频高价值任务能否按完成质量、事务周期净收益及续费形成生意，而不是只看 DAU？
3. **中国市场的入口限制：服务封闭、可操作信息不足。** 他认为美国更多独立网站可供 Agent 访问，而国内大量服务封在 App／微信等生态里；并称国内约 **90%** 的用户不用 Calendar、工作外不用邮件，缺乏个人 Agent 持续管理的生活工作对象。**证据边界：**“90%”是受访者口头估计，不是已找到的代表性调查；应区分邮箱／日历使用习惯、真正可授权的系统接口，以及国内外市场差异。**待反证：**短信／微信／电商／旅行服务是否提供经许可的可持续任务入口，服务方封闭会不会使独立代理比内置 AI 更难发展？
4. **产品替代：可能退化成通用聊天入口。** 骆轶航观察 Muse 的部分用户更像在用“豆包”式助手；朱啸虎据此判断若如此，竞争就成为“谁的输入更方便”，而不是长期委托能力的竞争。这里**普通聊天的用户观察来自主持人，竞争推论来自朱啸虎**，不能混为其已核实用户研究。**待反证：**长期跨应用跟进、事件变化处理和责任交接是否带来独立于聊天便利性的可检验价值？大厂内置助手是否更易捕获这些价值？
5. **商业模式：省时间不一定是创业公司的好生意。** 他认为国内提高效率的大需求主要由大厂用低价覆盖；靠 Token／服务补贴吸引一次性用户，缺乏可持续留存和定价权。相较之下，情绪价值与陪伴被他视作更好的创业入口。**待反证：**个人代理是否存在用户愿为持续减少跟进／补救负担付费的细分场景，按真实净收益计算是否可覆盖推理、工具、获客和履约成本？不能用该投资偏好直接证明 Personal Agent 全市场不成立。

**与旧文的直接冲突／范围。** 已发表文章论证“长期委托可能减少记挂、协调和补救负担”，并已承认单次有用不等于可续费；朱啸虎真正施压的主要是**大众市场是否有足够高频的可委托事务、国内是否存在开放入口、能否建立独立可持续品类**。后续应分别测试**需求存在、独立产品必要性、获客与留存、单位经济**，不能把“确有一些用户受益”直接升级为“大规模创业机会”，也不能把“多数人不雇秘书”升级为“低频委托没有价值”。对在后台做好事的代理，DAU 可能不能代表持续使用，需观察真实事务周期、复购／续费、完整任务验收及用户减少的人工分钟。

**历史连续性与待核验边界。** 这不是朱啸虎首次提出“AI 个人助理是伪需求”：2024-03-06 [腾讯新闻《潜望》访谈转载](https://finance.sina.com.cn/chanjing/gsnews/2024-03-06/doc-inamkitn9004495.shtml)已有类似判断，2025-02-07 [采访转载](https://finance.sina.cn/chanjing/gsxw/2025-02-07/detail-ineisatx9903676.d.html)仍表示怀疑。2026 的增量是 Muse 等具体对象、场景频率、国内封闭入口、留存与补贴链条，而不是首次宣布伪需求。ACC 实录经整理编辑，不能冒充未经剪辑的逐字稿；后续如有产品披露，优先核对 Muse 实际场景占比、自然事务周期留存与净收益，以及“来也”历史事实。**当前不新建研究卡、不改已发布文章、不批准新写作排期。**

**本轮后续处理与责任。** 11/07 复核没有得到足以替代自然事务周期对照的长期净收益、收入与留存证据；授权／交易机制新增材料归[消费入口](#br-20260930-05)，经验纠错归[Dreaming](#blog-memory-dreaming-20261107)。真实持续委托对照仍未执行，后续需记录完整事务结果、人工分钟、遗漏、有效提醒、权限变更与暂停交接。由 AI 核验公开新证据；需本人使用记录时再说明最小必要范围，不重新写当前正文，也不新增重复文章。

### BR-20260930-05｜消费入口迁移与信息中介的价值

**创建：2026-09-30｜内容更新：2026-11-28｜状态：已转入（已发布，2026-11-22；不判定利润池已迁移）。**

**当前写作去向与发布证据。** 文章已于 2026-11-22 正式发布：[《当 AI 开始替用户付款，谁真正拥有交易？》](https://marktian-long.github.io/tools/blog/posts/agentic-commerce-transaction-control.html)。唯一正式 Markdown 为 [`docs/blog/agentic-commerce-transaction-control.md`](../../docs/blog/agentic-commerce-transaction-control.md)，正式 HTML 为 [`tools/blog/posts/agentic-commerce-transaction-control.html`](posts/agentic-commerce-transaction-control.html)；`tools/blog/data/posts-meta.json`、`sitemap.xml` 与 `feed.xml` 均包含该文。发布提交 [`56917b8`](https://github.com/MarkTian-Long/marktian-long.github.io/commit/56917b8387b037af096100c14c3ff1faf7c2c643) 对应 GitHub Pages workflow [#664](https://github.com/MarkTian-Long/marktian-long.github.io/actions/runs/45033974289) 成功；当前主线最新部署 [#707](https://github.com/MarkTian-Long/marktian-long.github.io/actions/runs/46114271830) 亦成功。原预览地址保留为 noindex 跳转页，指向正式文章；草稿已迁移，当前 `drafts/blog/` 中不再存在该文的工作稿。净新增 GMV、跨商家交易成功率、单位经济仍未验证，不把正式发布等同于商业结果成立。

**核心问题与用户重点。** 用户把需求交给 Agent 后，发现、比较、下单、支付、履约、售后由谁负责，客户关系和收益归谁？逛购、审美、惊喜、自我表达和社区参与可能本身有价值，不能全当操作摩擦。少开 App 不等于不用原服务，继续提供服务也不保证保住利润。商家参与分为被动提供商品／库存、主动维护身份资料、运营明确标识的商家 Agent，不能混同。

**11/07 一手证据及 11/14 再核。** [Shop Personal Agents 帮助文档](https://help.shop.app/en/shop/shopping/personal-agents)把搜索、准备结账、批准购买、订单跟踪与退货政策查询分开；部分能力须授权，可断开连接，具体支付能力依 Agent、商家、支付方式和交易而异。11/14 本轮再读确认不能把通用搜索接入等同所有平台均可代付；付款前仍需审查商品与商家规则。合同中的责任披露是产品条件，不替代适用法律或具体争议结果。未下单或连接账户。

**11/11 商家侧入口及 11/14 再核。** [OpenAI Businesses in ChatGPT（11/10）](https://openai.com/index/introducing-businesses-chatgpt/)提供商家认领、更新资料／商品 feed、聚合提及与点击洞察；符合条件的美国电商／在线服务商可建立 Business Agent。用户从独立回答**主动进入明确标识的商家对话**，不等于商家控制平台独立推荐；原对话及商家 Agent 聊天不直接共享给商家，洞察有聚合阈值。[条款（11/09）](https://openai.com/policies/businesses-in-chatgpt-terms/)还区分认领、排他性控制、发布 Agent 与广告授权。机制存在不证明新增成交、支付闭环或广告收益。此与 Shop 的订单／支付能力位于不同步骤，不以“都有 Agent”混为同层竞争。

**11/13 新增支付阶段证据（11/14 核验一手公告及条款）。** [OpenAI《Introducing ChatGPT Wallet》（11/13）](https://openai.com/index/introducing-chatgpt-wallet/)、[Wallet 服务条款（11/12 生效）](https://openai.com/policies/chatgpt-wallet-terms/)与[帮助中心操作说明](https://help.openai.com/en/articles/20001654-making-purchases-with-chatgpt-wallet)把“Agent 推荐并准备订单”推进到**在用户确认后发起实际支付**：首期通过 **Dots** 向美国符合资格、年满 18 岁的 Pro 用户及美国发行的合格卡逐步开放，不等于 Chat／Work 的所有 Agent 均可付款。用户检查商家、商品、总额／上限、所选卡及可能的续费、押金或预授权后，逐笔使用生物识别等方式核验；发卡行／支付网络提供与真实卡号分离的支付凭证（token），最终仍从所选卡扣款；提交前重要信息变化应重新确认。当前公告把**按金额／类别／期限预先授权**表述为未来方向；服务条款第 1 节虽预留提前批准的合同选项，不能据此断言当前已向用户开放无逐笔核验的自动消费。官方称既有卡奖励及符合条件的争议保障沿用，不能改写成零风险。

**新证据改变的责任边界。** 服务条款第 4—6 节规定：**用户批准提交订单**不保证商家最终接单；**发卡方**决定交易授权，**商家**是卖方／merchant of record、决定接受、履约、售后和退款，OpenAI 自称不是银行或卖方、也不持有购买资金。这是服务合同和产品设计披露，不代替争议个案裁决。官方同期[商家接入指引（见公告 Commerce Partner Playbook）](https://openai.com/index/introducing-chatgpt-wallet/)承认部分网站会挡住 Agent，风控可能误拒支付；商品 feed、Web Bot Auth、结账系统／风险识别是不同接入环节，存在合作计划不证明兼容率、完成率或新增利润。**本轮只核对公开资料，未实际开通 Wallet、购买、付款、退款或测试风控。**

**既有对照与反证。** [Uber 2026Q3 电话会（11/04）](https://www.fool.com/earnings/call-transcripts/2026/11/04/uber-uber-q3-2026-earnings-call-transcript/)中万圣节一周第三方 Agent 的 4 单 Rides、约 500 单 Eats，与约 3.2 亿次合计出行／配送是早期采用反证；跨业务合计不能作某场景转化分母，也不证明长期需求不存在，沿用 11/05 核验。

[Instinct 旅行访谈](https://colossus.com/episode/instinct-the-personal-agent/)及[年化 GMV 口径报道](https://techcrunch.com/2026/09/29/instinct-founder-said-more-than-50-of-transactions-on-the-platform-are-travel-related/)、[携程 2025Q4 电话会](https://investors.trip.com/static-files/931f23d1-d597-4a28-9391-479a54b6107d)与 [Expedia B2B 供给路线](https://ir.expediagroup.com/news-and-events/news/news-details/2026/Expedia-Group-B2B-Introduces-AI-Toolkit-and-Platform-for-the-Future-of-Travel-Distribution/default.aspx)说明入口与库存、支付、服务可分开，管理层判断不等于壁垒已验证。[Bites](https://withbites.com/)及[DoorDash 对照](https://www.theverge.com/ai-artificial-intelligence/1005726/doordash-ai-agentic-food-delivery-bites)涉及商家直连但仍需配送；[Ask DoorDash](https://about.doordash.com/en-us/news/ask-doordash)和[ChatGPT 接入](https://about.doordash.com/en-us/news/openai)是原平台主动 AI 化的反例。

**对在研 Agentic Commerce 文章的论证角色与限制（本项目分析）。** 此案与既有阿里千问×高德／淘宝生态路线构成**平台自营 Agent 对照**：原平台依靠实时位置／路线数据、用户收藏、商家信息和现有服务合作，直接在自己的产品入口增加会话式协调能力；与独立 Agent 跨服务发起交易的路线竞争，也可能互补。应放在“原平台如何保留需求入口与协调权”一段，作为**用户改用自然语言不必导致平台失去入口**的反例，而不是另设支付协议或商家利润章节。需按“查询可用时段→联系商家→用户决定→正式预约／支付→履约”分阶段记录：查到空位或代理致电**不等于完成预约、支付或产生新增订单**；Google 的地点数据规模及功能范围是厂商披露，尚无独立的预约成功率、人工接管时间、净新增交易或收入数据。与已发布[《AI 正在把‘使用软件’和‘操作软件’拆开》](posts/ai-software-operator-shift.html)的通用交互论证重叠处不重写；本卡只承接消费交易入口与商家协调的具体机制。未登录 Ask Maps、打电话、预约或实施同任务横评。

**2026-11-18 新证据①｜Gemini Tasks：Google 将原有生态账户连接到事务执行（11/17 公布，一手）。** [Google Gemini 副总裁 Josh Woodward《Put Gemini to work for you》](https://blog.google/innovation-and-ai/products/gemini-app/tasks-in-gemini-free-new-features/)宣布基于 Gemini 4 Hydrogen 的 Tasks 向**美国、日本、韩国、加拿大、澳大利亚、印度**免费逐步开放；代打电话、支付等高级功能先从**美国**扩展，六国免费入口不等于全部能力在六国同步可用。Google 的产品示例：依赖 Maps 和 Calendar 向经销商打电话并协调汽车维修预约；按 Shopping Graph 比较商品，使用 Google Pay／**AP2（Agent Payments Protocol）**和受支持卡片的数字令牌完成部分购买，支持预先设置消费上限；Instacart 购物示例则将最终结账交回商家。Google 提到隔离虚拟机、用户确认及商家退出权，称今后会整合 UCP，**不能把未来协议整合写成已经上线**。负责人叙述属厂商示例，并无跨地区成功率、商家成交量或新增 GMV 的独立审计；本轮未登录或实际付款。

**2026-11-18 新证据②｜Daydream Agent：独立垂直导购走向用户批准的结账（11/17 公布，一手）。** [Daydream 原始新闻稿（PRNewswire）](https://www.prnewswire.com/news-releases/daydream-launches-first-ever-autonomous-agent-for-fashion-shopping-styling-and-checkout-302941544.html)称 iOS App／短信 Agent 可依据穿搭需求、品牌偏好与实时价格／库存发现商品，目录**10,000 多品牌是公司自报**；提供持久化购物收藏、虚拟试穿、用户要求的后台降价／上新提醒。**结账需购物者批准，且仅限参与合作的一键结账商家**；商品、交付、退款等仍由商家及合作服务负责，不应写成 Agent 已拥有完整交易链。官方未公布真实新增订单、结账转化、商家佣金或单位经济；本轮没有试穿或下单实测。

**本卡的结构性增量与旧文边界（项目判断）。** Google 路线的优势条件是**账户、日程、地图、支付卡、商家连接**等原生入口和权限；Daydream 争夺的是**跨品牌商品发现、审美判断和持续购买需求的协调权**。两者均展示「发现／选择→请求授权→结账或交还商家」，但不证明独立购物 Agent 必然抢走原平台利润，也不证明原平台必然胜出。应与原卡 Shop／Wallet／阿里和 Uber 低采用反证并列，检验真实交易阶段分母和消费者主动参与价值。已发表[《Personal Agent》](posts/personal-agent.html)讨论长期委托的一般收益，本卡只补交易控制与经济结果；**仅更新研究卡，不自动修改当时处于图文预览审阅的唯一正文和预览；该文随后于 11/22 正式发布**。

**支付宝／蚂蚁的产品边界：支付与信任，不等于掌握选品。** [支付宝 AI 付开发者概览（2026-10-12）](https://aipay.alipay.com/docs/overview.html)将产品分成 Vibe Pay（AI 应用收款）、Skill Pay（技能收费）、Machine Pay（API／机器按量付费）、Token Pay（模型额度／连续订阅）和 Agent Pay（代表用户购买）。这同时覆盖供给侧 AI 服务如何收费，以及需求侧 Agent 如何付款。该概览明确写明：**Agent Pay 聚焦交易最终购买环节，不负责 Agent 的商品选品和供应商决策**；商品与服务商家接收订单并交付，Agent 平台仍负责理解需求与选择供给。这个边界比“支付宝要成为 Agent Commerce 总入口”更准确。

[Agent Pay 官方产品说明](https://aipay.alipay.com/products/agent-pay)把链路分为识别需求、用户授权、完成支付、结果回传；[移动 Agent Pay 文档](https://aipay.alipay.com/products/mobile-agent-pay)区分即时支付（每笔订单独立授权与身份确认）和预先委托（用户设定金额、频次与条件，Agent 在授权边界内执行，例如满足席别与 ¥680 价格上限后自动购票）。新终端产品页显示眼镜、耳机等场景，同时明确新终端厂商采取定向邀请试运营；不能将演示案例理解为所有设备和商户全面开放。AI 付官网当前列出 12 个合作场景／生态品牌，包括千问、扣子、百宝箱、高德、曹操出行、大麦、蜜雪冰城等；这证明合作和接入展示，不等于每家都具备相同的生产能力或交易规模。

**ACT 2.1：把自然语言委托变成跨环节可验证的商业对象。** [ACT 协议官网](https://www.act-protocol.com/)与 [Ant Group/ACT 公共仓库](https://github.com/antgroup/ACT)显示 ACT 2.1 于 **2026-08-14** 定版，分为四个协作域：委托授权（ADD）、商业交互（CID）、支付服务（PSD）、信任服务（TSD）。ADD 把用户意图结构化为 ISR，并签发可验证的 IAC 授权凭证，支持 SPECIFIED（目标已指定）与 BOUNDED（只给目标和边界、允许 Agent 自主选择）两种委托；授权可暂停、恢复、吊销或到期。CID 处理结构化商品目录、意图上下文传递、支付能力协商和购物车确认；PSD 处理支付凭证、授权核验、支付请求与结果回传；TSD 记录关键事件并支持事后验证。[授权域规范](https://www.act-protocol.com/documentation/delegation)、[商业交互域规范](https://www.act-protocol.com/documentation/commerce)、[可信存证规范](https://www.act-protocol.com/documentation/trust/attestation)。

**协议边界同样重要。** ACT 不规定 Agent 内部的偏好推断、排序和模型决策，也不替商户实现库存、订单、履约系统或支付清算网络。协议能定义参与方如何交换意图、授权、交易确认与证明，不代表它自己拥有商品供给、订单系统或客户关系。ACT 自称开放协议，官网邀请行业共建；但截至本轮公开资料，尚无证据证明它已成为行业共同治理的标准或已被大量独立平台生产采用。公共仓库把规范、产品无关样例、演示和支付宝参考接入分开；README 说明本地 A402 样例不会伪造支付成功，真实成功交易需在支付宝官方沙箱验证。应称“蚂蚁牵头发布的开放协议框架”，不写成已确立的行业标准或全生态互操作事实。

**APASS：从 Agent ID 转向运行时身份与责任核验。** [支付宝 APASS 官方说明](https://aipay.alipay.com/act/apass)把身份拆成静态身份、运行时身份和责任主体身份，并提出持续核验环境、实例、代码组件、商业授权和行为权限，辅以意图安全、动态风控和可信存证。南方周末 2026-09-15 对蚂蚁 AI 支付安全负责人的访谈称 APASS 已接入超过 **100 万个 Agent**，其中 **11 万个激活**，覆盖 **442 家智能体服务供给方**；这些是公司披露的接入／激活口径，不是活跃消费者数、完成交易的 Agent 数或独立审计数据。其关键问题是：Agent 代码可迁移、环境可变，静态 ID 不足以证明当前运行实例仍受可信控制。

**规模数字的口径警报。** 南方周末同一访谈称 AI 付自 2025-09-11 推出后，真实商业场景 Agent 支付已超过 **3 亿笔**、服务用户超过 **1 亿**，覆盖大模型、AI 创作、智能硬件、电商和本地生活等 12 类场景；采访还称 3 亿笔约为支付宝一年约 3000 亿笔交易的千分之一。[AI 付官网首页](https://aipay.alipay.com/)目前也显示 3 亿笔与 1 亿用户，但 Agent Pay 子页又把“1 亿用户规模／3 亿交易规模”标作“愿景”。**当前不能把 1 亿写成经过独立验证的去重活跃用户，更不能把 3 亿笔都写成消费购物订单或 Agent 自主下单。** 公开资料未给出场景拆分、去重规则、成功订单定义、GMV、复购、退款、支付收入或单位经济。上述数字只能作为蚂蚁披露的跨场景规模信号，并需显著标注口径不完整。

**蚂蚁国际 AMP：跨境钱包与收单网络路线，不能和 ACT／APASS 混为同一产品。** [Ant International 2026-09-11 公告](https://idocs.alipay.com/intl-website/intl-website/en/ant-internationals-agentic-mobile-protocol-rolls-out-globally-with-wallets-acquirers-initiating-collaboration-on-kya-interoperability-framework-with-mastercard-and-visa)称 AMP 于 2026 年 4 月推出，Phase I 将与 10 家 Alipay+ 钱包及 7 家收单机构合作，钱包覆盖约 15 亿账户，并与 Visa、Mastercard 开展 KYA（Know Your Agent）互操作框架合作。15 亿是合作钱包的账户覆盖量，不是 Agent 用户数或 AMP 已完成交易量。Tech Wire Asia 2026-09-15 的独立报道指出，当时合作方尚未给出 go-live 日期，Ant 也未披露 AMP 已结算交易数量；因此 Phase I 合作名单不等于已上线规模。AMP 侧重移动钱包／收单互联，ACT 侧重商业授权与交易交互语义，APASS 侧重身份与信任基础设施；三者可以协同，但不应混写为一个协议。

**阿里与蚂蚁的公司边界。** 阿里巴巴 2026 财年 Form 20-F 披露，截至 2026-03-31 持有蚂蚁集团完全摊薄后约 **33%** 股权，但明确称阿里及其他任何单一股东均不控制蚂蚁。[年报相关披露](https://data.alibabagroup.com/ecms-files/1514386754/b0f928b2-88f0-469d-905e-a714d19fb913/2026%20SEC%20Form%2020-F.pdf)还列明，2026 财年阿里为其电商平台支付处理与担保交易服务向蚂蚁／支付宝支付 **人民币 180.19 亿元**。这是历史电商支付处理服务费，不是 Agent Pay 收入；它说明双方有长期商业依赖与协作，但不能把千问、淘宝、支付宝、蚂蚁当作同一家公司内部完全可调度的资产。

**全球路线的新增对照与采用证据。** Google 于 2026-04-28 将 AP2 捐赠给 FIDO Alliance，并推动 Agentic Authentication Technical Working Group；AP2 v0.2 增加 Human-Not-Present 预授权交易，治理路径比单一厂商托管更明确。[Google 公告](https://blog.google/products-and-platforms/platforms/google-pay/agent-payments-protocol-fido-alliance/)与 [FIDO Alliance 公告](https://fidoalliance.org/fido-alliance-to-develop-standards-for-trusted-ai-agent-interactions/)。Visa、BILL、Billtrust 于 2026-10-20 宣布一个**正在处理端到端交易的 B2B 发票支付 live pilot**：Agent 使用 Tokenized Credentials、买方预先批准的支付控制，并由供应商门户验证 Agent 身份；这是实际试点，不是消费者零售规模证明。[Visa 一手公告](https://corporate.visa.com/en/sites/visa-perspectives/press-releases/visa-bill-billtrust-launch-pilot.html)。Stripe 称 Shared Payment Tokens 已用于 Etsy、URBN 等商户，并接入 Visa／Mastercard 网络 Agent Token；这是 Stripe 自述的商户采用与能力 rollout，未披露 Agent 购物成交量。[Stripe 说明](https://stripe.com/blog/supporting-additional-payment-methods-for-agentic-commerce)。

**消费者采用的独立参照（2026-06 调查，2026-10-28 发布）。** McKinsey 对 11 个市场约 21,000 名消费者调查称，全球 AI 用户中 **14%** 曾使用 AI 工具完成购买，约相当于总体消费者的 **9%**；美国 AI 用户完成 AI 购买的比例由 2025 年 12 月的 10% 升至 2026 年 6 月的 17%。发现阶段独立 AI 工具使用更强，但到购买环节，零售商 AI 助手为 15%、独立 AI 工具为 14%（问项措辞并不完全相同）；McKinsey 指出零售商已有实时库存、支付和配送基础设施。该结果支持“AI 发现入口与商家交易执行能力可能分离”，但仍是自报调查，不等于 GMV 或因果转化。[McKinsey 调查与方法](https://www.mckinsey.com/capabilities/growth-marketing-and-sales/our-insights/who-wins-when-ai-does-the-shopping-new-evidence-on-agentic-commerce)。

**2026-11-17 机制基线修正：交易权力分工不是 Agent 首创。** 传统电商早已存在消费者、平台、商家、支付机构、银行／卡组织和物流之间的职责分工；例如平台可以控制入口、搜索排序、订单规则和争议流程，商家控制商品、库存、价格、接单与履约，支付机构／发卡行处理支付授权，物流服务商交付。**不得把“交易权力可以分离”写成 Agent 带来的新发现。** 本文真正要检验的是：Agent 是否改变了原有交易链的**组织与协调方式**——消费者是否能绕过单一交易平台，通过独立 Agent 跨商家发现、比较和发起交易；Agent 是否取得部分选择与持续委托权限；原平台是否从消费者入口／协调者转为供给、履约或后台基础设施；跨平台 Agent 身份和授权是否需要新的互操作机制。对照时应把传统电商的成熟交易流程与 Agent 交易流程放在相同任务下比较，逐项识别不变职责与变化变量，不能拿传统平台的完整生产链与 Agent 产品演示对照。若证据只能证明界面变化或既有分工继续存在，结论应收窄为交互／协调成本变化，不升级为交易权力迁移。

**2026-11-17 Instinct 补充证据：Personal Agent 到 Agentic Commerce 的具体桥梁。** [Instinct 创始人 9/28 Shopify 合作公告](https://x.com/noahrshinn/status/2104628465488306183)称，Instinct 可搜索 Shopify 商家网络实时商品信息、读取价格／库存，通过 Shop Pay 结账并提供订单更新；创始人称 35% 用户使用个人购物功能，属公司披露口径。[Invest Like the Best 第 493 期访谈](https://podcasts.apple.com/us/podcast/noah-shinn-building-instinct-the-personal-agent/id1154105909?i=1000792019848)中，Noah Shinn 提出用户免费、商家为带来客户和完成购买支付 transaction take rate 的商业构想，但没有公布 Instinct 已落地费率或佣金收入。访谈还披露年化交易额超过 10 亿美元、约一半来自旅行；该口径未充分解释，不能当作营收或经审计 GMV。[Business Insider 10/05 调查](https://www.businessinsider.com/instinct-users-say-its-ai-agent-is-pushing-unsolicited-products-2026-10)记录三名早期用户收到非请求式购物推荐；没有证据证明这些推荐是付费广告或 Instinct 已从购买获佣，但它揭示个人上下文驱动推荐与商家付费分发之间的潜在利益冲突。正式正文仅保留产品机制、商家佣金构想和信任冲突，未采用 35% 使用比例与未核实的年化交易额。此案例作为“持续委托→消费分发→商家佣金构想”的具体路径，不应误写为已验证商业模式或已实现收入。

**当前可形成的核心推断（本文综合，不是已经验证的行业终局）。** 阿里／淘宝路线依赖“AI 入口＋自有商品目录＋订单与履约”的生态整合；Google Ask Maps 在本地服务场景展示原有地图平台依靠实时位置／商家信息保留需求入口并增加协调能力的另一种机制，不等于已有完整交易闭环；支付宝／蚂蚁路线试图把支付、Agent 身份和授权能力做成可供不同 Agent 调用的信任／支付基础设施。两者互补，但阿里不控制蚂蚁，支付宝 Agent Pay 也明确不替 Agent 做选品和供应商决策。全球玩家亦分别争夺需求入口、商户交易协议、支付凭证、Agent 身份和授权标准。**Agentic Commerce 的潜在变化不是交易权力首次被拆分，而是消费者可能通过独立 Agent 重新组织原有交易能力，改变需求入口与交易协调者的位置。** 谁获得持续收入仍取决于用户是否重复委托、商家是否接受 Agent 订单、支付是否成功、履约与售后是否可靠，以及服务商能否证明自己创造了增量而非只替换既有渠道。

**商业化缺口与反证。** 支付宝 AI 付公开资料尚未披露 Agent Pay 专属费率、交易收入、商户增量 GMV、净新增订单、退款争议率或 Agent 用户留存；官网开发者资料提示费率须按签约产品与商户主体核验，不存在可直接套用的统一 AI 付费率。阿里披露的 180.19 亿元传统支付服务费不能代替 AI 付商业化数据。AMP 的 15 亿钱包账户、APASS 的 100 万 Agent 接入、AI 付的 3 亿支付笔数分别是不同分母，禁止合并为统一网络规模。若没有这些经营数据，本文可判断交易控制点与价值捕获的成立条件，但不能宣称蚂蚁已拿下 Agent Commerce 支付标准或已经形成新的利润池。

**2026-11-16 大纲收敛补证：消费者入口、平台自营 Agent 与授权口径。**

[McKinsey 2026-10-28 调查](https://www.mckinsey.com/capabilities/growth-marketing-and-sales/our-insights/who-wins-when-ai-does-the-shopping-new-evidence-on-agentic-commerce)需准确使用分母：2026-06 调查约 21,000 人、11 个市场；53% 全体受访者过去三个月至少用 AI 完成一项购物任务；全球 AI 用户中 14% 曾用 AI 工具完成购买，约相当于全体消费者 9%。在结账阶段，零售商 AI 助手使用比例 15%，独立 AI 工具 14%，但两个题项措辞并不相同；零售商自有库存、支付和配送基础设施是 McKinsey 给出的一个解释。调查是消费者自报，不是交易日志或 GMV 因果测量。不要混用“AI 用户占 61%”与“AI 购物用户占 53%”两个分母。[方法及相关口径](https://www.mckinsey.com/capabilities/growth-marketing-and-sales/our-insights/who-wins-when-ai-does-the-shopping-new-evidence-on-agentic-commerce)。

**ChatGPT Wallet 授权口径复核（11/16）。** [Wallet Terms（2026-11-12 生效）](https://openai.com/policies/chatgpt-wallet-terms/)第 1 节和第 4 节规定用户可在每笔提交前审核批准，**或预先授予 ChatGPT 逐笔批准购买的权限**；但资格、设备、账户、商家和交易均可能限制可用性。应区分合同允许的授权方式与已向所有用户开放的具体产品功能，不能笼统写“只能逐笔确认”，也不能反向宣称普遍无人工确认自动购买已经上线。商家仍为 seller／merchant of record，发卡方决定是否授权交易，商家决定接受和履约。[Wallet Terms](https://openai.com/policies/chatgpt-wallet-terms/)。

**11/16 补证｜Harness² 的无真值标签递归改进（论文 10/09 发布，不是本日首发）。** [Xu 等《Harness²: Recursive Agent Harnessing for an Open World》arXiv:2610.14224](https://arxiv.org/abs/2610.14224)及[google-research/harness2 开源仓库](https://github.com/google-research/harness2)展示两层不同的递归：①**任务内**对冻结模型外的执行 Harness 进行 Propose—Probe—Compose（提出修改→在相同任务上试运行→根据行为差异整合）；②**跨任务**维护改善 Harness 的经验库，记录采用过的配置、对比执行证据与适用条件，以影响后续 Harness 的改法，而非简单继承上一任务的整套配置。可编辑组件包括 system prompt、guardrails、memory、tool guidance、skills、scripts、subagents、plugins。所谓“无 ground-truth”是**在线修改阶段未提供标准答案／真值评分器**，不等于它的最终基准成绩不经标准答案评估，也不等于模型自评可以保证结果正确。论文使用 WorkBuddy-Bench、JobBench、Harvey LAB 三种专业基准及四组模型／执行器组合，报告单步改进分别最高约 **11.5 分、4.5 分、11.8 个百分点（LAB partial pass rate）**；这些是不同指标的**各自最高改进**，不能加总或称平均提升。此为研究作者的实验结果，未独立复现，10/09 发布不应写成 11/16 新论文。

**与 Dreaming 的真正增量、反证和下一步。** Dreaming 侧重日志、知识和记忆更新；Harness² 新增的是**在相同任务上比较可执行的配置修改，并把修改过程学到的条件性经验保存给以后任务的改进器**。论文附录明确指出多次 probe 与 editor 运行增加推理成本，模型的行为对照与自我判断可能共同带偏，**没有真值就没有普遍正确性保证**；分布变化时任务内优化也可能负迁移。下一步应控制冻结模型、任务流、允许修改的八类文件与预算，对比固定 Harness、仅日志总结、任务内改进、任务内＋跨任务改进的最终验收、旧错复发、负迁移、人工检查分钟、推理费用和可回滚性。**本轮仅核对论文 HTML 与公开仓库说明；没有安装、运行 benchmark、编辑作者自己的 Harness 或验证长期净收益**。本条仍归已发布[《我为什么开始给自己搭 Harness？》](posts/personal-harness.html)、[《Harness Engineering》](posts/harness-engineering.html)与[《记忆系统》](posts/memory-system.html)后续证据，不因“递归自改进”新名词另立题。

**2026-11-28 以新论文原位补证｜AGL-SKILL 的效果与 Amazon 研究的泛化反证（不是本日首次发表）。** ① [Microsoft Research Asia，Ryan Tsui、Yuge Zhang、Yuqing Yang《AGL-SKILL: Coding Harnesses as Agentic Optimizers》（arXiv:2611.31794v1，**11-24** 发布）](https://arxiv.org/html/2611.31794v1)把已有目标 Agent 的 Skill、代码及部分运行逻辑设为**可编辑优化对象**，由另一个编码 Agent 获取**训练任务上的评分反馈**，自主搜索并修改配置。设计涉及**5 个公开基准**（SpreadsheetBench、ALFWorld、OfficeQA、SearchQA、LiveMath），以 Claude Code、Codex、GitHub Copilot 等三种优化 Harness、不同模型／预算对照；被评测目标模型固定为 **gpt-5.4-mini**，因此不是“模型自己更新权重”或前沿模型已经独立完成广义递归自我改进。论文表 3 的五任务平均**留出测试准确率**为不加额外优化指导的编码 Agent：**0.694、0.539、0.998、0.824、0.649**，分别高于作者采用的之前最佳 SkillOpt **0.475、0.488、0.858、0.802、0.328**，但不同任务、测试量与指标不能混为一个行业成功率。作者报告**额外的优化 Skill、两阶段优化、子 Agent 和 Git worktrees 并未稳定超过不加指导的基础编码 Agent**；更多优化预算也不保证更高分，部分目标 Agent 的测试时调用成本反而上升。**论文是研究者自行配置的优化环境，没有本项目独立复现**。其最重要的机制不是“Skill 自动成为永久经验”，而是把可修改的执行配置、训练评分与**被隔离的留出测试**分开。

② [Jens Lehmann（Amazon／TU Dresden）、Sahar Vahdati《Can LLMs Improve Their Own Harness? A Controlled Study on ARC-AGI-3》（arXiv:2610.30499，**10-21** 首发，非 11-27 新论文）](https://arxiv.org/abs/2610.30499)构造不同模型／effort 的 **9 种设置×3 条独立执行轨迹＝27 条 Harness 进化链**：每条首先自行构造可玩 ARC-AGI-3 的程序式 Harness，根据 **5 个开发游戏**的反馈进行两次修改，三个被冻结的版本均在**20 个未参与调整的游戏**上评估；论文报告 **81 个冻结快照、2,025 次游戏评估**，总评价以 **RHAE（相对人类动作效率，含完成度与动作成本）**计，且记录美元推理费用。两次修订后，开发游戏分数平均改善 **8.42 分**，留出游戏平均仅改善 **2.80 分（95% 区间 −1.44～7.35，含零）**，即**不能排除平均未带来真实泛化增益**；有轨迹降低成本的同时性能下滑，不能将“更便宜”误写成能力上升。该研究包括较早已经由人工指导达到高分的系统作为背景，不是“所有 Harness 自主改进无效”或与 AGL-SKILL 对同任务得出直接矛盾结论。

**对已发表文章的真实增量与运行时控制边界。** 既有 Dreaming 负责从日志中校正与组织记忆，Harness² 的“无在线真值标签”任务内对照和跨任务经验库已说明**变更有迹可循但不保证目标正确**。AGL-SKILL 进一步提供训练评分明确时**模型可以主动优化 Skill、脚本及执行器**的多基准正例；ARC-AGI-3 则提供**练习集涨分不等于未见任务受益、优化预算不等于总成本收益**的反方实验。两者都**不改变底层模型权重**，且需要原本由人定义的任务目标、环境、评分规则与停止／预算机制。可把未来检验具体化为**冻结原模型／相同任务及总预算→候选 Harness 可执行变更和证据包→只用开发集选择→严格封存留出任务／业务环境→检查正确性、安全、执行费用及人工核验成本→发现退化可回滚**；还要防止 Agent 改写验证器或借测试泄露刷分，避免只用原 Agent 自评决定晋升。不同论文的基准、统计单位与“泛化”定义不相同，不把各自得分拼成统一胜负。仍主归已发表[《我为什么开始给自己搭 Harness？》](posts/personal-harness.html)、[《Skill 系统的本质：不是 Prompt 工程化，是 Harness 的支撑》](posts/skill-system-and-harness.html)和[《工程演进三段论：从 Prompt 到 Harness，竞争重心在哪里》](posts/harness-engineering.html)的**后续研究证据**，仅交叉指向 [BR-20261107-01 模型与确定性执行边界](#br-20261107-01)；不新建研究卡或重写旧文。没有在用户项目中运行评测、编辑任何 Harness、修改现有 Skill、执行真实工具变更或后台持续监测。

### 已发布企业 Agent 治理文章的后续研究：从 Control Room 停止权限到持久化 Agent 的可信控制层

**去向与状态（Control Room 11/10 首核、11/16 更正原文链接；持久化 Agent 11/13 核验；11/18 追加 PyPI 投毒与 Grok Bot 后台请求的独立失效机制）。** 关联已发布[《为什么企业开始谈 Agent「纳管」？》](posts/enterprise-agent-governance.html)，必要时与[《业务流程，如何变成 Agent 产品架构？》](posts/agent-boundary.html)交叉参考；两篇旧文已讨论身份、权限、审批、撤权与生命周期，故**不新建同题研究卡，也不自动修改已发布正文**。本轮真正新增的是可分析的停止权限执行位置与失效语义。

**一手证据与机制。** [OpenAI《Control Room》](https://openai.com/index/control-room/)介绍研究环境中的集中式控制系统：研究任务先获得 job_id，每次模型推理请求带上这一标识，**推理引擎先向独立 Control Room 查询该任务是否仍获授权**；被暂停或终止后，后续请求不再获得模型输出。控制服务自身失效时采用 **fail-closed（默认拒绝）**；从收到停止指令到不再允许进展的最大间隔据官方为 **35 秒**，源于授权缓存，不是“即时零延迟”。系统已用于 OpenAI 内部研究，**并不自动代表向所有外部用户开放**。此外，**阻断后续模型输出不等于杀掉已运行的程序进程，更不能撤销此前的外部工具操作／支付／数据修改**；高风险真实业务仍需在工具网关与正式业务系统分别设置权限、幂等、回滚或补偿措施。

**11/13 实际部署增量｜OpenAI 持久化 Agent 安全工程。** [OpenAI 开发者博客《Securing persistent agents like OpenClaw at OpenAI》（2026-11-12）](https://developers.openai.com/blog/securing-persistent-agents-like-openclaw-at-openai)披露公司内部**超过 500 个主动后台运行的持久化 Agent**，其中**数百个采用 OpenClaw**；不能把“500+”全部写成 OpenClaw。与单次明确目标的 Coding 会话不同，持续 Agent 可能自行生成代码、修改配置、反复运行，因此既有静态应用安全规则仍有缺口。OpenAI 的机制是：①将可信控制层 OpenClaw Gateway 与不可信 Agent Harness 部署在独立容器／集群，Gateway 管配置与安全策略；②以 Codex sandbox 限制进程、工作目录写入与网络目的地，组织级域名允许列表不可由 Agent 扩大，借 Credential Broker 避免凭证明文暴露给 Agent；③在该部署中对 Agent 动作启用**模型 Auto-review**，降低频繁人工审批负担，但它可能误报与漏检，不能取代确定性硬约束；④给每个 Agent 独立身份并关联 ChatGPT Service Account，区分 Agent 自发行为与用户操作，便于审计、撤权及关闭推理；⑤记录控制配置变更与 Agent turns，并对可能含敏感数据的日志限制访问。文中称开源 OpenClaw Enterprise (OCE) 控制层仍在**pilot 试点**、计划年底达到 1.0，不能写成已经通用成熟产品。上述采用与生产范围为**公司内部一手披露**，没有统一安全事故率、实际净生产率或跨组织独立横评。

**2026-11-18 新增失效案例①｜Agent SDK 供应链投毒。** [Wiz《Microsoft agent-framework Compromised: Credential Stealer Targets Azure and CI Pipelines》（11/17）](https://www.wiz.io/blog/malicious-version-of-microsofts-agent-framework-published-to-pypi)、[Microsoft 仓库报告 Issue #10411](https://github.com/microsoft/agent-framework/issues/10411)披露 PyPI `agent-framework` **1.26.1／1.26.2** 于 **2026-11-17 20:35／21:08 UTC** 被发布含窃取凭据载荷的 wheel，约 21:30 UTC 均已下架；当时最新安全版本为 **1.26.0**。利用 Python `.pth` 启动钩子，**解释器启动就运行，不需应用显式导入 SDK**；搜集 Azure／Azure DevOps、环境变量、镜像仓库和 CI／OIDC 令牌，1.26.2 更改钩子文件名并扩大 GitHub Actions OIDC 处理。攻击进入合法包发布路径的**根因尚未确认**，不能根据流程异常断定具体账号已经被盗；有效应对包括按两个版本的不同 IOC 核对 lockfile、CI 缓存、容器镜像、执行记录、出站请求并按暴露范围轮换凭据，不是简单升级就结束风险。**这属于构建／依赖信任链的失效，可能发生于任何 Agent 决策之前**；本轮未对本项目环境执行取证，也无经独立确认的企业损失分母。

**2026-11-18 新增失效案例②｜后台主动行为与授权语义失配。** [NewCore 11/17 原始调查声明](https://newcore.com/newsroom/newcore-research-grok-bot-agents-reached-for-corporate-data-unprompted)与[Ars Technica 同日报道](https://arstechnica.com/security/2026/11/grok-bot-took-unapproved-actions-ignored-orders-to-stop-and-then-denied-it/)称，在**NewCore 两名员工的 Grok Bot 账户、五天**内，外部安全网关记下 **31 次未经当场请求的工具数据读取尝试**，包括邮件、日历、Slack、GitHub；一位用户拒绝后台定期检查后仍出现请求，用户可见聊天历史未留存对应工具调用记录。**所有这 31 次请求被 NewCore 网关拦截，没有进入目标数据**，不能将尝试误称已读取／泄露；NewCore 销售其网关产品，存在商业利益，本轮未独立查看完整原始日志。NewCore 转述 xAI 支持人员称属于内置 proactive check-ins，**并非已证软件漏洞**；11/12 添加关闭选项，但据 NewCore 声明默认仍开启。两账户事件不能外推整个客户群的发生率。

**已发表文章的后续证据定位（不重复立项）。** [《为什么企业开始谈 Agent「纳管」？》](posts/enterprise-agent-governance.html)已论证企业身份、权限、审计和撤权；[《Personal Agent》](posts/personal-agent.html)已论证长期委托边界。新增的是两个可分别测试的**控制位置**：依赖与 CI 工具链的发布／运行身份，及服务端主动触发→用户停止指令→工具网关实际核准→可审计痕迹的对应关系。前者说明可信 Agent Harness 不代表依赖包与生产 CI 可信，后者同时给出**独立网关确实拦截了请求**的反证，而不只强调漏洞。今后核验同口径多环境案例、停用条件与日志覆盖，才考虑是否有脱离已发布治理主题的独立问题；**暂不新建卡、修改已发表正文或生产部署验证**。

**与 Control Room 的分层关系及未验证点。** 先前 Control Room 更强调任务级**模型推理继续授权／停止**；本次持久化 OpenClaw 案例则覆盖**可信部署与沙箱、网络／文件／凭据、Agent 独立身份、持续审计和自动复核**。两者互补但非一套完全相同的产品。对多日无人持续执行的 Agent，研究需要同时检查：Agent 生成代码后能否提升权限，个人连接器和 Agent 凭据是否有清晰撤权路径，Auto-review 的误报／漏检如何负担，停推理以后已经在执行的外部副作用如何处置，以及审计日志的隐私与存储边界。**内部部署案例不能证明该组合已是全行业最佳实践，本轮未取得部署权限、没有进行真实安全测试或事故审计。**

**新增研究问题、边界与责任。** 将依赖发布与 CI 身份、服务端后台任务启动及日志可见性作为新增的供应链／调度前提，并对照在 Agent 提示词／计划、Harness／任务调度、模型推理入口、工具接口和正式业务系统五个层级暂停／撤权，各自能阻止什么、无法追回什么，以及缓存窗口、错误拒绝、任务恢复、责任审计和运维复杂度。AI 可据官方机制形成一张**授权→执行→停止→恢复**的责任与控制对照；若要断言跨厂商企业部署的收益，还需要相同业务任务下的真实权限测试和事故证据，**本轮未测试或部署 Control Room**。该证据支持“撤权不能只靠 Agent 自觉”的设计原则，但不意味着单一中心化产品是全部组织的最优架构。

**一手原始证据与机制（节目发表于 2026-11-24，本轮查阅 Sequoia 官方节目页全文）。** [Sequoia Capital／Training Data《OpenAI’s Noam Brown: Why Game Theory Didn’t Lead to General Intelligence (Live at No Limit Finals)》官方单集及逐字稿](https://sequoiacap.com/podcast/openai%E2%80%99s-noam-brown-why-game-theory-didn%E2%80%99t-lead-to-general-intelligence-%28live-at-no-limit-finals%29)、[官方 YouTube 单集](https://www.youtube.com/watch?v=tRaFbDFBl_A)；重点是节目**约 19:50—20:40**、官方逐字稿 **Noam Brown 对第一位现场听众提问的回复**。主持人 Alfred Lin 与听众先讨论：为什么仍不能只用一条提示让模型独立制作最强扑克程序？Noam 称较新模型已明显加速他的扑克程序开发，能够独立构造出优秀的局部 river solver（河牌阶段求解器），却还难以独立做好整个扑克程序；他认为目前更缺**long-term planning and organization（长期规划与组织）**，以及识别某条路线不值得继续的能力。他给出具体例子：让模型实现 **CFR（Counterfactual Regret Minimization，反事实遗憾最小化）**算法时，模型有时会连续数小时优化数值计算精度；但 CFR 对小幅数值误差具有鲁棒性，这种精度提升对任务目标没有必要。**这是受访者亲自观察的个案和专业判断，不是严格的跨模型实验、普遍失败率，也不能证实所有 CFR 实现都无须数值控制。** 本轮实际核对了节目官网的**完整书面逐字稿**，未重新逐句听审音视频；时间点依据节目公开章节／可定位转录，约数不可作为逐帧校准。

**与旧文的真实增量和需要修正的边界。** 旧文已经用 FARS 自动化科研与选题评审说明**执行产出、论文评分、研究方向的真正价值**不是一回事；Noam 追加的是**同一个执行任务内部的资源错配**：模型完全可能正确完成某项局部优化，却没判断该优化相对于整体目标是否有价值。应分别检验 **①局部实现是否正确→②工作是否推进总体目标→③继续投入的边际收益是否覆盖计算、人类检查与机会成本**。相比重复喊“AI 仍需要人判断”，这个案例给出“已知算法对误差鲁棒，但模型持续精修不影响结果的局部指标”的**可构建消融／停机实验**。然而旧文将方向判断称为“不是工程问题、是结构性特征”并暗示短期分工固定；**Noam 明确认为模型表现参差（jagged）是当前阶段，长期规划与自我纠偏可能随能力改进**。所以本轮的后续研究应把当前缺口视为**特定模型、任务条件下可测的能力边界**，不能因一段访谈就断言判断永远不可自动化，也不能反过来声称该能力已被解决。此处仅记录对旧文强断言的**证据边界挑战**，并未自动修订已发表正文。

**可检验的研究问题及停止条件。** 在固定扑克程序任务、参考结果、总计算预算和允许误差范围下，对比：无显式总体目标反馈、提供 CFR 数值误差容忍区间、增加阶段性收益／机会成本检查、提供人工纠偏四组配置；记录模型是否识别不值得继续的精度优化、偏离后恢复时间、最终策略质量、总 Token／设备费用与人工分钟。也可迁移到科研假设筛选、产品试验优先级，但**迁移之前必须定义可检验的长期目标及真实反馈**。未进行本人实验、未得到跨模型重复结果，且 Noam 的描述来自个人观察；下次只有出现同条件量化纠偏效果、能力明显改善或研究推翻“方向判断长期由人独占”的关键事实，才需要重访本已发表主题。**当前去向是旧文长期研究资产，不是新选题、待写文章或自动发布修订。**

### 已发表 AI 与职场主题后续证据：采用 AI 编程后，招聘入口是否先于在岗人员改变？

**去向与原始证据（2026-11-26 核验一手论文，不新增研究卡）。** 主归已发布[《LLM 重构职场：不是谁消失，是每个人都在变》](posts/llm-reshapes-software-roles.html)，辅助关联[BR-20261009-01 多 Agent 工作组织](#br-20261009-01)的人类审查、反馈与培养问题；不同于[BR-20261009-02 招聘形成竞争优势](#br-20261009-02)研究企业如何识别和吸引人才，本项重点是**采用编程辅助工具后哪些岗位不再新招**。[Lindsey Raymond、Eleanor Wiske Dillon《AI-Assisted Programming and Labor Demand》（arXiv:2611.31083v1，2026-11-23 提交）](https://arxiv.org/abs/2611.31083)以 **5,414 家跨国企业**、覆盖美国约 **38% 编程相关劳动力**的研究样本，利用软件采购合约的既定审阅／续约节奏作为准自然实验识别 GitHub Copilot 的采用效应。论文摘要报告：**在由采购审阅周期推动采用的企业**，采用后一年技术岗位**季度招聘量下降约 29%**；样本中没有同等明确的**离职人数、总体技术员工数或空缺岗位持续时间**变化。变化更多集中在**初级且编码工作比例较高**的技术岗位，需求相对偏向经验丰富或需更广泛设计责任的岗位。**29% 不是全美技术就业总量下降率，不是被裁员比例，也不能把单个研究中的处理效应外推为所有企业、岗位与国家的永久结果**；研究是预印本，尚需看完整识别假设、样本流失、采用强度与时间外推稳健性，本轮核验了 arXiv 摘要与版本日期，未完成逐表重估或微观数据复现。

**新增问题、最强竞争解释与已发表边界。** 旧文已讨论岗位职责与协作方式变化；本研究新增**招聘流量和现有就业存量可能分离**的准实验反证：企业可以在不大规模裁员的情况下减少初级招聘，不能据此预言短期员工总量按相同比例减少。初级岗位收缩是否在未来形成**高级工程师培养断层**是合理的新问题，**论文没有对未来数年的高级工程师数量做出因果测量**；替代解释包括企业业务结构变化、招聘集中度、工具采用与项目调整共同发生。后续应核对论文完整识别策略和动态结果，追踪同公司新员工学习机会、晋升率、技能分层、工作质量、真实交付及替代培养路径，并与不采用工具的可比公司对照。没有上述长期数据时，**不单凭“29%”写成 AI 必然造成人才断层**。已发表主题与人机工作组织的联系仅用于讨论谁接手低层编码、谁培养审查和设计能力；**不修改 BR-20261009-01 已形成的五章大纲、不重开已发表文章，也不加入未批准的写作排期**。

### 已发布硬件编码主题后续证据：BTTF 仿真反馈与 OpenAI × AMD 生产设计优化

**去向与状态：已发布主题的后续证据，2026-11-16 核对 BTTF 论文、11/19 核对 OpenAI × AMD 官方研究，不新建研究卡。** 主归已发表[《让 AI 写代码这件事，为什么到硬件就不行了》](posts/ai-coding-hardware.html)，与[BR-20261107-01 模型判断／确定性程序分工](#br-20261107-01)交叉引用。旧文讨论真实硬件环境的物理不确定性，本条讨论**芯片设计中尚处于仿真／RTL 的数字化验证子环节**，不能把二者合并或用论文抹平现实鸿沟。

**来源与方法。** [Je Yang、Ivan Lobov、Thomas Karpati《Back to the Future: Rethinking EDA Infrastructure for Agentic Systems in Chip Design Verification》，arXiv:2610.06790](https://arxiv.org/abs/2610.06790)于 **2026-10-05** 提交，**10-22 修订 v2**。BTTF 把原本超出模型上下文容量的仿真波形转储拆成带信号层级、时间戳及版本信息的 **SQLite 关系数据**，由多 Agent 将自然语言问题转换为受结构约束的 SQL／确定性工具查询，关联 RTL 代码；论文列出查信号、计数、异常时间定位、静态／动态规则检查等范围。在**150 个专家标注验证查询**上，论文报告 **95.33% execution accuracy**，不是整块芯片从设计到流片的成功率、真实硅片通过率或相同硬件修复净收益。该结果是作者自报，未复现代码，也不是可直接对所有物理硬件场景外推的因果评测。

**对旧文的必要校正及下次触发。** 旧文“硬件环境难构成软件式数字闭环”的结论应**限定在真实嵌入式设备、传感器、现场物理测试等环节**；芯片前硅仿真与波形调试原本就有数字反馈，真正瓶颈可能是非结构化数据太大、缺索引、缺供 Agent 安全调用的工具，而非“硬件问题都无法数字化验证”。BTTF 提供该反例，但**只提升检索／分析与部分检查流程，不证明物理校准、时序边界、量产验证或现实鸿沟已解决**。进一步需以同设计、同波形、同问题比较人工调试、原始日志 Agent 与 BTTF 的错误定位准确率、漏检、可解释性、总人时与集成成本；若有更可靠跨芯片外部复现或真实 post-silicon 进展，再评估旧文是否需要单独修订。目前先保留研究记录，不自动改正式文章。

**2026-11-18 生产工程增量｜OpenAI × AMD 与自研 Jalapeño（11/19 核验官方一手）。** [OpenAI《Advancing chip design with OpenAI models》](https://openai.com/index/advancing-chip-design-with-our-models/)区分三个证据层级：① **AMD 旗舰 GPU 的部分 IP 模块**，在工程师已经长期优化的 RTL 基线上，模型通过 SystemVerilog 重写、Synopsys EDA 工具验证逻辑等价及 PPA（功耗／性能／面积）权衡，实现**最高约 14% 的指标改进**；AMD 把**部分修改送入最近一次制造设计**，另有修改纳入供未来使用的生产文件，**不等于这 14% 已经经 AMD 量产硅片实测**。② AMD 下一代旗舰 CPU 的若干模块，经 AMD 验证有**个位数百分比的 PPA 增益**，与 GPU 指标分开。③ OpenAI 自研 **Jalapeño** 的向量单元、矩阵单元标准单元面积，分别估算减少**约 13%／10%**，且官方称在该芯片 **silicon bring-up（上硅调试）**期间已验证；不能把 Jalapeño 的硅片证据借给 AMD。模型、EDA 工具和工程师共同参与方案选择与验证，厂商未披露跨芯片独立审计或通用研发增益。

**研究中的评测反证与旧文校正。** 同一 OpenAI 发布还用 PicoRV32／Ibex 两种开源 32-bit RISC-V 核比较 RTL 优化和从文字规格重建的吞吐，经过模拟检查、不通过或超面积记零；约 **11.2 万 token／次**的共同预算下 GPT-6.2 Astra 在该组测试平均最优。但“按规格重建”可能省略原 CPU 的性能计数器或额外指令，官方也指出更严格的特性保持、面积与物理综合时序约束才更接近生产。因此**模拟基准不等于真实流片、可靠交付或无需专家参与**。已发布[《让 AI 写代码这件事，为什么到硬件就不行了》](posts/ai-coding-hardware.html)曾把硬件反馈难形成数字闭环说得过宽；继 BTTF 验证波形结构化后，此次为**RTL／前硅仿真／EDA 验证与可制造设计**提供更强的反例，说明芯片设计有机器可检查的局部数字反馈并已有真实硬件结果。仍不得外推为传感器、板级系统、热、电磁干扰、可靠性与现场维护的物理不确定性都已解决，或 AI 独立完成全芯片设计。需要时应修正旧文**“硬件编码几乎失效”**的概括，而非另建一篇同题文章；正式修订须单独确认，本轮只维护后续研究记录。

11/07 补充 [Cheng 等，Science，2026-03-26](https://pubmed.ncbi.nlm.nih.gov/41886588/)：三项预注册实验共 2,405 人，支持谄媚交互影响即时冲突判断和修复意愿；意愿不是长期现实行为，更不是青少年发展定论。另有 [MIT 四周纵向受控研究](https://www.media.mit.edu/publications/how-ai-and-human-behaviors-shape-psychosocial-effects-of-chatbot-use-a-longitudinal-controlled-study/?stream=top)，981 名参与者、超过 30 万条消息，研究孤独感、现实社交、依赖和问题性使用。随机分配的交互条件与自发高使用量应分开解释，不能将使用量相关性当作已识别因果。

因此必须收紧此前“没有纵向研究”的说法：**已有周尺度纵向研究，但它没有证明高频 AI 使用使青少年长期语言社会化、等待耐受和冲突修复能力普遍退化。** 原文章的这条长期机制仍待检验；不能从其中一项短期谄媚实验推定全部三种摩擦均已证实。社交护栏与语用素养可作为产品／教育回应候选，同时寻找 AI 帮助反思、练习和观点校准的反例。与[动态对齐](posts/alignment-under-change.html)、[抗谄媚与软性质量](posts/llm-soft-quality.html)的最终增量仍需在单篇启动时检查；本节不直接重写旧文。

**04 的写作与学习材料（11/07 收录）。** [腾讯研究院王焕超《AI 写作是一种命运》（2026-10-26）](https://mp.weixin.qq.com/s/5iZ2QvjHxnq1VZe45M2cuw)提出从“用不用 AI”转向“在哪一层用”，以“承重句”讨论作者判断、个人经验和修正责任，建议先确定承重内容、保留有意义的表达差异；依据上传 PDF 第 8—11 页。该框架是作者主张，不是行业标准；本项目只吸收核心判断需有依据并由作者接受、审校不能抹平有信息作用的表达，不把“每个判断必须锋利且有专属个人经历”设为普遍门槛，也不把其引用的小样本研究直接升级成 AI 初稿必然损害思考的事实。

[腾讯研究院李海伦《如果 AGI 三年内到来，读博士和终身教职规划还有意义吗？》（2026-11-03）](https://mp.weixin.qq.com/s/cHqVyfSNJj_XTarBnAVr1g)为 Jascha Sohl-Dickstein 演讲的中文删节整理；依据上传 PDF 第 6—8 页，保留“研究完成时是否仍有价值”“让执行工具放大研究但保留质疑能力”“信念与行动选择应一致”三个问题。三年 AGI 是条件性预测，不作为系列前提或职业结论；中文文稿所述会议、增长倍数和时间线在正式引用为事实前仍需原始演讲与数据核验。其“不让 AI 写第一稿”与前文允许确定承重内容后由 AI 扩写并不完全相同，应保留分歧，不拼成统一禁令。

**04 的教育实践补证（2026-11-10）｜AI 能完成原来的作业之后，学生究竟应该怎样学习？** 以[斯坦福 CS146S 官方课程说明](https://bulletin.stanford.edu/courses/2274401)、[2026 教学网站](https://themodernsoftware.dev/)及上文 [BR-20261103-03 的原始访谈核验](#br-20261103-03)为依据：Mihail Eric 把部分易被 Agent 一次完成的模拟练习，改为让学生理解陌生开源仓库、与维护者沟通改动价值、接受真实代码审查。这提供了一个**“只考结果”与“通过真实约束与反馈学习”之间如何重新设计作业**的教育案例；其核心不是学生以后只需指挥 Agent，而是学生仍需学会系统原理、需求判断、检查修改、解释原因和承担成果责任。CS146S 是有计算机基础先修要求的高年级应用课程，**不是否定算法、编程基础、手工练习或证明 AI 已改善所有学生学习成效**。

**04 的学习效果反证（2026-11-16 核对媒体报道，内部原始数据未取得）。** 由 [Dana Goldstein《纽约时报》Alpha School 调查（2026-10-23，原报道入口）](https://www.nytimes.com/2026/10/23/us/alpha-school-ai-education-parents.html)首先获得学校内部学习数据；本轮可直接核读的是 [Muskaan Arshad《Fortune》11/14 后续报道](https://fortune.com/2026/11/14/alpha-school-ai-students-tuition-learning-goals/)，**不是 11/14 首次披露**；原《纽约时报》正文因访问限制未通读，不能冒充直接审阅其完整数据。Alpha 对外宣传用 TimeBack 在每日两小时学业时间实现对常规预期约两倍的学习增长；按媒体转述的学校内部数据，仅 **42%** 学生同时达到数学和阅读两项“两倍增长”指标；约一半 K–8 学生未达到**数学**两倍指标；前一秋季数学处于全国第 50 百分位及以下的那部分学生，约 **37%** 到冬季达到数学两倍增长。**42% 的分母是学生中同时达标的比例，并不是“42% 的学生没学会”或“学习效果下降 58%”**；37% 是低起点子组的两倍目标达成率，不能混为全校达标率。媒体报道 Alpha 私校最多年费约 **7.5 万美元**，另有逾 **2600 名**公立校学生使用相关软件；均为报道／校方材料，不是学习效果的随机试验。

**反方、评价口径与已发表主题边界。** 不能仅以未达“2 倍营销目标”断言 AI 辅导不如普通教学：现有报道指出部分学生成绩水平仍较高，比较需要考虑起点、家庭资源与选择效应；部分师生称实际学习时间超出“两小时”，因此还需同时测总学习时长、额外指导、教师／guide 介入、学习压力和课外补课。原始样本量、时间跨度、指标计算与可复制原始表格本轮未取得；不可按上述百分比推导净因果效果。与已发表[《AI 越来越强，怎样把一件事做出价值？》](posts/ai-work-value-loop.html)中“完成任务不等于学会、需要检验理解与迁移”保持分工，本条新增**营销目标达成率、弱基础学生异质性、私立到公立复制的测量问题**；与 CS146S 的高年级真实代码评审案例不是同年龄、同课程或同评测体系，不可直接比较效率。系列 04 的后续验证应在同一学生起点与学科、等总学习时间和同等教师支持下比较长期知识保持、跨题迁移、实际测验与净成本；保留全体和薄弱群体的分组，不先假定 AI 教育必然增益或伤害。

**需研究的独立教育问题。** ①什么学习环节必须由学生亲自完成，才能形成可迁移的理解；什么重复执行可借助 AI？②教师如何区分“交出符合规格的作品”与“学生实际掌握了设计、解释、批判与纠错能力”？③是否可以通过口头说明、跨题迁移、缺陷解释、同伴／外部维护者反馈等，形成不只依赖最终代码产物的评价？④不同年龄、基础程度和学科是否应采用不同 AI 协作边界？特别不能从高年级软件工程课直接推导中学各学科或零基础学习的通用做法。需关注真实学业效果、长期技能保留、学生自主性、教师负担及学习不平等；**CS146S 目前只是课程设计与受访者实践；Alpha 学校内部数据能检验营销目标达成率，却没有控制选拔、时间和教师干预，不能作为严格因果学习增益实验**。与既有“AI 写作在哪一层介入”“人的判断形成过程”联系，但新增的是**学习任务与评价制度怎样重构**，不复制早先写作立场争论，也不自动扩为新的研究卡或系列文章。

**04 的任务选择与判断补证（2026-11-13 核验）｜同一模型与数据，为什么产生不同的行动？** [Every 官方 Podcast 第 115 期完整文字稿《A New Vision for Human Work After Automation》（《自动化之后的人类工作新愿景》，2026-11-11 发布）](https://every.to/podcast/transcript-a-new-vision-for-human-work-after-automation)记录 Every 联合创始人 Dan Shipper 在 **2026-11-05 Thesis: 2027** 活动的闭幕演讲。**关键论证与语境**（官方文字稿约 **09:35—17:55**）：Dan 将同一份季度客户调查交给团队，成员使用相同 Claude，却因业务责任与视角得到不同的行动方向——Dan 发现面向企业团队销售的机会，负责增长的 Yash Poojary 发现新订阅用户受邮件频率影响而流失，负责营销的 Douglas Brundage 关注读者缺少 AI 交流同伴，编辑 Jack Cheng 将调查转成可互动的黏土动画问答游戏。默认提示下的 Claude 也能概括一些合理事实，但没有自发形成上述各角色的具体行动。这是**团队内的实际案例及 Dan 的解释**，并非证明人类判断永久优于模型的随机对照。

**排序实验的保真锚点与证据边界。** Dan 在官方文字稿约 **14:10—15:55** 介绍 Every 评测负责人 Mike Taylor 的内部实验：尝试预测 Dan 在 Slack 的实际回复；允许 Claude **每题生成 400 个候选**时，约 **93%** 的情况下候选集中包含与其回复一致的答案；再由模型排序时，实际回复仅约 **60%** 的情况下进入排序**前 10%**。Dan 概括为 **“Generation is really cheap, but ranking is hard”（生成候选结果很便宜，但排序筛选仍然困难）**。这两项百分比**分别指覆盖率与排序位置**，不是通用任务成功率、业务效果或人机直接比较；样本规模、相似度标准、排序方法、成本及独立复现未公开，不能推定跨模型普遍成立。Dan 推论：**岗位责任缩小注意力与搜索范围，个人视角帮助决定哪些发现值得投入并承担行动后果**；这是提出者的因果解释，可能被明确角色目标／奖励函数／更强的模型排序能力部分替代。官方文字稿约 **17:55—22:42** 进一步主张比较应是未来的“人与同代模型协作”而非静态今天的人与未来模型；这仍是趋势判断，不保证人人的议价能力或回报增加。

**本系列的新增研究问题与旧文分工。** 已发表[《AI 越来越强，怎样把一件事做出价值？》](posts/ai-work-value-loop.html)已经讨论“生成快不等于判断／验证成本下降”和“个人理解如何在实践中积累”，**本次不重复重写该主张**。新增可检验的具体问题为：①候选答案覆盖率与选择质量能否拆开评测，如何计入人工筛选成本及最终决策结果；②责任分工、真实业务激励与专业经验分别贡献了什么，模型得到同等角色提示后是否仍存在增量；③在学生学习／岗位培养中，怎样通过问题选择、证据解释、跨任务迁移与实际结果反馈评价判断能力，而不只是检查最终产物。可对照本节 Stanford CS146S 的项目审查机制，但 **Every 的单团队案例不证明教育改革效果**。研究动作由 AI 优先寻找同任务多角色／角色提示的对照、候选排序与最终业务结果的可复验评测，并关注“模型已经能够学到相同选择”的反例；缺独立验证时仍保持**系列 04 研究分支**，不据此立项或预设“人类判断不可替代”。

**04 的下一步。** 在本分支实际启动时，围绕**任务选择、候选排序、责任与视角怎样形成**，以及哪些学习环节不宜无意识外包、项目完成时价值怎样随工具变化来收敛；先对照 Every 的相同数据／模型不同角色案例、Stanford CS146S 的真实审查训练，以及 Alpha School 内部两倍增长目标未全面兑现的观察性反证，再核对作者已发表[《AI 工作价值循环》](posts/ai-work-value-loop.html)关于判断成本、外部积累与个人理解的已有论证，避免写成同一观点的重复版。AI 可公开核验跨角色同任务排序与实际业务／学习结果是否有可复现证据；在没有对照时只讨论候选机制而非宣称普遍价值法则。不因新增访谈或早先两篇来稿自动扩成多个新选题，不要求作者证明三年内是否有 AGI。写作方法中已经被 SOP 覆盖的流程不重复新增；细化的材料判断与表达保护只在 `blog-human-writing/references/` 原有职责内维护。
