# Blog 正文生图工作流

版本：2.0｜更新：2026-11-28

本文件定义正文自制视觉资产的任务选择、逐图 Prompt Packet、模型交接、有界迭代、验收和资产交接。它不替代写作 SOP、图表语义规范或网站发布契约。

## 1. 职责与边界

- `blog-sop.md`：决定何时规划配图、配图承担什么阅读任务，以及何时进入制作；不维护提示词工程和图片处理细节。
- `blog-charts-spec.md`：决定图表是否必要、图形关系如何表达、流程/决策逻辑是否准确；不规定生图风格。
- `.agents/skills/blog-image-prompting/SKILL.md`：负责图片任务分类、Prompt 结构、视觉探索、参考图角色和有界迭代；模板在 references/prompt-recipes.md，逐图文件格式在 references/prompt-packet-template.md。
- `tools/blog/IMAGE_REVIEW_CHECKLIST.md`：负责单图硬性拒绝条件、视觉评分、语义门和资产入稿门；不替代实际网页 QA。
- `VISUAL_GUIDE.md`：维护视觉语言、图像类型选择、资产规格、图文一致性与实际页面验收；本文件补充生图的执行步骤。
- `blog-review-checklist.md`：在终审时检查图文协同、事实边界和最终交付；不重复维护生图操作说明。
- `WRITING_GUIDE.md` 与发布脚本：维护 Markdown、metadata、资产登记、HTML 生成和公共产物发布契约。

生图是视觉制作方式，不是事实来源，也不自动获得改变正文论点、数据、流程或产品行为的权限。

**生图优先是本项目的默认视觉制作策略。** 对新文章的开篇首图、概念/场景/隐喻插图，以及承担理解任务的编辑型关系图，默认先使用当前可用的内置图像生成模型探索视觉方案，而不是先用代码绘制矩形卡片。只有当图片必须呈现真实产品界面、人物/事件现场、论文原始图或可核实证据时，才优先使用原始来源素材；来源素材的许可、署名、裁切及资产登记仍由 `VISUAL_GUIDE.md` 管理。生图不是事实来源，也不自动获得改变正文论点、数据、流程或产品行为的权限。

## 2. 先定义图片任务，再决定是否生图

每张候选图先写一行图片简报：

- **位置**：对应正文哪一段/哪一节；
- **阅读任务**：进入主题、具象化场景、说明抽象概念、呈现对照、解释机制或帮助回顾；
- **核心对象与关系**：画面必须出现什么，谁与谁对照/连接/共同完成什么；
- **文字策略**：纯视觉、标题加少量标签，还是精确节点文字；
- **证据边界**：哪些内容来自事实，哪些只是概念隐喻；哪些数字、UI、Logo、品牌或产品细节禁止虚构；
- **与相邻图文的分工**：它新增什么视觉信息，是否重复正文或其他图片。

按任务选择表示方式：

| 表达任务 | 首选方式 | 边界 |
|---|---|---|
| 概念、场景、隐喻、封面 | **默认优先调用内置图像生成模型**探索独立视觉；只有真实证据图更适合时才改用来源素材 | 不伪装成实测或纪实素材；不生成网页截图代替预览 |
| 图文结合的编辑插图 | **优先生图模型**，再按需叠加精确文字层 | 文字必须短、已确认且逐字校对 |
| 精确流程、决策树、数据与比较关系 | 先冻结可核验的逻辑/数据源，再**优先用生图模型探索视觉构图与主体**；最终文字、数值、节点、箭头和分支由确定性图层精确排版 | 不让模型发明数据或改变关系；所有语义逐项对照逻辑源校验 |
| 真实产品界面、研究截图、原始证据 | 原始来源素材 | 不得用生图重绘冒充真实截图 |
| 复杂图文混合 | 先判定是否真需要新图；必要时可用生图底图 + 精确排版层 | 生图只负责氛围/主体，准确文字和关系由确定性图层负责 |

不能因为生图更漂亮，就让它替代需要精确表达的流程图或数据图；也不能因为 SVG 可控，就把所有概念插图都做成矩形卡片。**采用“模型负责视觉创作、确定性图层负责精确表达”的默认组合**：先冻结可编辑的逻辑源，再用生图模型探索主体、构图、材质、空间和视觉层次；精确节点、中文标签、数字、箭头与条件由 SVG/HTML 排版层承载，或对生成图逐项校验后再合成。纯数据图、证据截图和无法可靠校验的复杂文字不强行生图；只有通过语义、文字和可读性校验的结果才能成为最终展示图。

### 生图调用前的任务与事实门槛（默认优先探索）

每一次生成请求仍必须明确一个**具体图像任务**，不能把“整篇博客”“文章全文”“完成完整预览”“检查页面”作为生图任务。默认优先生图不等于每一节都要生成一张图，也不因页面单调而凑数量；它意味着当某张图片已被确认具有独立阅读任务时，视觉探索的第一选择是内置图像生成模型，而不是先做模板化代码插画。

1. **锁定单一交付物**：明确插入哪一节/哪一段、图片类别（独立场景插画/封面/局部视觉底图等）、主体及关系、目标尺寸和图中文字。未经用户要求网页设计时，禁止输入全文让模型生成网站截图、预览 mockup、整篇信息图或虚构的“已完成”验收面板。
2. **区分证据素材与概念视觉**：真实照片、论文原图、产品截图等证据型图片使用可核实原始来源；概念、场景、隐喻和编辑插图默认先用生图模型探索。若只是数值曲线、精确表格或密集节点文字，保留确定性数据/逻辑源，不让模型生成数据。
3. **记录净增价值与风险**：生成图是否比现有图片/文字/图表更具体、易懂或能营造必要阅读节奏？会否引入不真实的品牌、装置、文字、关系或不可验收的内容？若只有装饰收益、风险或成本更高，默认不生图。
4. **最小调用预算**：默认每张图一次初始生成 + 最多一次定向编辑/重生成。首轮出现任务或媒介错误时，先重写 Brief，不在错误方向上连续修补；第二次仍不合格，转用确定性 SVG/精确叠加层、正文表格或文字，不继续循环。只有两个完全不同的视觉命题确实值得比较时，才允许两个首轮候选。
5. **交付可验证资产**：产物必须是真正的独立图片，不是模型生成的整页截图；读取真实像素并按 Visual Guide 验证桌面与移动端实际显示。只有已选图片进入预览；废弃候选不入仓库、不放页面、不借用其描述宣称已完成改版。
6. **授权和预览边界**：生图请求的主体、样式和事实边界必须已明确；图片若涉及真实厂商设备但没有证据，不能用生成式设计冒充实拍。若用户仅要求对文章、规范或已有页面进行审校，不因此推导出新的生图任务。

此门槛属于**生成前的执行许可和成本控制**；文字稿的图文机会识别不等于图像生成许可。工作流由本文件维护，SOP 只要求先决策是否调用；Checklist 只检查是否实际通过门槛。

### 防止全文摘要图：Prompt Scope Lock（强制）

本项目近期出现过同一失效模式：提示词把文章标题、全文结构、多个章节内容和全部指标同时交给模型，模型便将任务理解为“制作一张完整指南/总结海报”，而不是某段正文的独立插图。即使成品是单张图片、没有网页边框，也仍然是错误媒介。

**提示词上下文规则**

1. 全文只供助手理解文章，不作为模型默认输入。最终 Prompt 只引用当前图片所在段落的必要信息；局部上下文最多两句，必要时再加一句主结论，不附其他章节、案例或参考资料。
2. 先在 tools/blog/visual-prompts/<slug>.md 写出当前图片块，再生成。每篇文章只有一个 Prompt Packet；同一张图的 Brief、Final Prompt 和尝试记录都在原位更新，不创建 prompt-v2、(1) 等副本。
3. Prompt Packet 是项目记录，不是一次生成请求。实际调用只取当前图片块的 Final Prompt 与必要的短风格锚点；不得把整份 Packet、全文、完整大纲、整篇预览或其他图片任务一起发送。
4. 若当前 ChatGPT 生图入口会继承对话上下文，调用前使用只含当前图片 Prompt 的干净交接消息；需要强隔离时，使用新会话，只载入当前 Prompt 和必要参考图。保存文件本身不会自动隔离模型上下文。
5. 简单场景/概念图优先使用 1–3 句清晰 Prompt；只有复杂流程、决策或层级图才使用短结构化字段，字段只列本图节点、连线、条件和必要文字。
6. 一个精确框架可以包含自身必要节点，但不得混入无关案例、参考资料、其他章节标题或第二套框架。默认禁止完整指南、全文总结、章节导航海报、网页截图和多章节拼贴。
7. 生成前逐字复核实际交接文本，确认没有混入正文、完整大纲、其他图片 Prompt、助手解释或流程讨论。

**整篇摘要图的一票否决**

候选图若同时概括多个章节/独立论点，采用总标题 + 多个编号模块/宫格/卡片复述全文，或试图把流程、指标、案例、建议和结论一起塞进画面，即使中文字正确、风格统一，也直接 Reject。不得通过裁切、删标题或缩小文字补救；回到局部 Brief 重做。

**允许的多节点单图**：四步框架、前后流程对照、指标层级图可以有多个节点/区域，因为它们各自回答一个明确问题。禁止的是把多个独立章节任务合并，不是机械限制节点数。
 
### 独立图片资产与输出尺寸验收

当任务需要正文插画/照片时，生成或检索的目标必须是**可直接插入文章的独立图片资产**，而不是网页截图、文章 mockup、UI 页面或把多章内容塞在一起的信息图。生成结果必须在加入预览前检查实际宽高、主体、文字、边缘和压缩；尺寸不符合 `VISUAL_GUIDE.md` 源图门槛时，不得仅靠插值放大。若生成模型连续返回错误媒介或低清候选，应停止无效重试，转用许可明确的原始照片，或暂时不放图，并说明原因。

## 3. 建立整组视觉约定

同一篇文章先确定整组视觉方向，再逐张生成。至少明确：

- 画面风格与媒介（编辑插画、纸雕、扁平矢量、轻 3D 等）；
- 主色、强调色、背景与明暗；
- 画幅比例、主体位置和留白；
- 人物/物体的视觉一致性（若跨图复用）；
- 图中文字的字体气质、字号层级、字重和标签样式；
- 禁止元素：无意义科技装饰、无来源数字、虚构 UI、误导性品牌标识、难读小字等。

风格统一不等于每张图使用同一构图。图片可以分别承担场景、机制、对照和回顾任务，但应像同一篇文章中的一组编辑视觉。

## 4. 提示词与生成迭代

先读取 .agents/skills/blog-image-prompting/SKILL.md，按任务使用 references/prompt-recipes.md。**最终 Prompt 必须先写入 tools/blog/visual-prompts/<slug>.md，再进入模型交接。** 不把整份 Packet 交给模型。

### 简单图片：优先短 Prompt

概念、场景、封面和单一关系图通常只需要 1–3 句，包含独立交付物、唯一视觉任务、主体关系、画幅/构图和少量关键约束。不要机械填满字段，不要堆砌“高级、精致、专业、科技感”等抽象形容词，也不要附文章全文作为背景。

### 复杂图：先冻结逻辑，再写局部 Prompt

流程图、决策树、指标层级和比较图先在 Prompt Packet 中冻结节点全集、精确短标签、顺序、边的起终点与方向、真实分支条件、回退/暂停/终止、数字/单位/数据来源和证据边界。简单线性流程直接把结构写进 Prompt，不必先画 SVG；复杂分支只有在确有助于核验空间布局时，才用 Mermaid/SVG/HTML 作中间逻辑草图。中间草图不自动成为最终资产。生图模型负责视觉探索；准确节点、数字、标签和箭头必须逐项核验，必要时用确定性层收口。

### 一次只改一个问题

1. 首次调用默认只生成一张，不默认生成多版本。
2. 先检查任务/媒介是否正确，再检查主体关系、构图、视觉层级、文字和技术质量。
3. 若主体、任务或媒介错了，拒绝候选并重写 Brief；不要在错误方向上反复要求“再漂亮一点”。
4. 若只有局部视觉问题，引用上一张图做一次定向编辑，并明确只改什么、哪些必须保持不变。
5. 若文字、节点或关系错误，缩短标签或修订逻辑后最多重生成一次；不得把语义错误当成配色问题。
6. 默认每张图最多两次模型调用（一次初始生成 + 一次修订/重生成）。确需比较两个完全不同的首轮方向时，最多两个候选，随后停止。
7. 两次后仍不能通过语义/质量门，转用确定性 SVG、精确叠加层、Markdown 表格或正文文字，不继续消耗循环。

### 同篇风格一致性

选定一张合格图作为风格锚点。后续只引用其配色、材质、光线、字体气质和视觉密度，不复制主体与构图；每次 Prompt 仍只包含当前图片任务。废弃候选不作为风格参考。

## 5. 图片文字规则

图片文字可以是有效的编辑设计元素，不再默认要求概念插图完全无字。但文字必须帮助识别主题、对象或关系，而不是把整段正文塞进画面。

- **可直接由生图模型绘制**：短标题、短标签、少量关键词；提示词应逐字给出确切文案。
- **优先后期精确排版**：长句、数据标签、复杂术语、法律/技术细节、密集列表、需要严格对齐的文字。
- **禁止无依据内容**：未经来源支持的数字、客户数量、可用率、性能指标、产品 UI、Logo、功能清单或看似真实的仪表盘数据。
- **逐字校对**：检查错别字、漏字、重复字、标点、大小写、数字和单位；模型画对大意不代表文字准确。
- **控制文字密度**：通常一个核心标题加少量对象/关系标签即可；详细解释交给正文与图注。
- **文字与画面冲突时**：先改构图或删减文案，不把不可读小字视为可接受折衷。

如果图片只承担概念搭配，图中文字不应引入正文未建立的新结论；若文字承担论证内容，必须由正文和来源支撑。

## 6. 选图与整篇组合

不要按生成顺序自动选第一张，也不要把所有候选全部塞进文章。逐张判断：

1. 是否准确服务对应段落？
2. 是否让读者更容易进入、理解、比较或回顾？
3. 是否与正文/现有图表重复？
4. 是否包含虚构事实、错误标签或误导性隐喻？
5. 缩小到实际正文宽度后，主体和文字是否仍清楚？
6. 与整组图片的风格是否一致？
7. 对流程图/决策图，是否与可编辑逻辑源逐项一致；生图是否只改变视觉表达，没有改变语义？
8. 是否逐张通过 `IMAGE_REVIEW_CHECKLIST.md` 的硬性门和视觉评分？候选图未通过不得入稿或进入预览。

最终组合应有视觉节奏：概念插图可以引入问题，精确图表负责解释结构或决策；不是每张都要承担同一功能。保留必要正文解释，不因图片存在而删除证据、条件和边界。

## 7. 从候选到正式资产

1. 原始候选放在 Git 忽略的 `build/blog-image-work/<slug>/`，不得直接写入正式图片目录。
2. 只选通过内容与视觉检查的图片；使用 `scripts/prepare-blog-image.js` 生成符合 `VISUAL_GUIDE.md` 的规范化 WebP。对于用户已选定且文字/标题需要完整保留的 4:3 概念图，可以使用 `--aspect 4:3` 输出 1280×960，不强行裁成 16:9；分辨率、图中文字和页面实际显示仍要验证。不得自行改扩展名伪装格式，不得覆盖已存在的正式资产。
3. 精确图继续使用静态、自包含 SVG；不把生成式位图改名为 SVG，也不把 SVG 转成位图后再声称可编辑。
4. 将最终资产写入 `assets/images/blog/<slug>/`，使用能说明图片任务的 kebab-case 文件名。
5. 在 `docs/blog/<slug>.md` 的独立图片行中登记 alt/caption，并在 `posts-meta.json` 的 `visuals.inline` 中同步 src、alt、caption、width、height；两处必须完全一致。
6. 运行图片契约检查、文章生成、搜索资产生成、taxonomy 与 search foundation 检查、public dist 构建和检查。不得只改 Markdown 或 metadata 就声称图片已发布。
7. GitHub Pages 工作流只负责仓库检查、公共产物构建与部署。**不要为了上传图片或生成文章而临时修改部署 workflow、扩大其权限或把写仓库逻辑塞进部署 job。** 应在发布前的本地/Codex/Work 写入阶段准备并提交源稿、资产、metadata 和生成 HTML；标准 CI 验证后再部署。
8. 发布后核对线上文章实际加载的图片、目录/精选入口（如适用）及图片顺序；未做浏览器截图验收时，明确标注未验收，不以 CI 全绿代替视觉检查。

### 未发布稿的配图登记与预览前验收

未发布文章以 `drafts/blog/<slug>.md` 作为唯一正文源；不能为了预览提前把它加入正式 `posts-meta.json`。通过视觉与语义检查的配图需要有可复核的预览期登记，而不只是将图片字节上传仓库。

- **三处同时登记。** 当前 draft 中的独立图片行，`tools/blog/previews/<slug>.html` 里的 noindex 对应 `<figure>`，以及 `scripts/public-dist-manifest.js` 中明确列出的预览地址和实际图片资产路径必须完全一致。图片的 alt、caption、宽高、文件名不能只在预览 HTML 中维护。正式发布时再把同一资产登记到正式 metadata，不能提前混入正式文章索引。
- **预览资产检查先行。** 图片检查器将已纳入 public-dist 白名单、且源稿与预览严格一致的 noindex 草稿图片视为临时合法登记，仍对格式、尺寸、字节大小、SVG 静态安全及完整解码执行相同检查。其他图片继续作为孤立资产报错，不为草稿一概豁免。
- **原子提交与失败分流。** 一次交付同时提交图片资产、草稿引用、预览 HTML、manifest 和必要检查器测试；先核对引用和图片匹配，再触发 Pages。出现 `Orphan blog image` 时先判断是合法预览图遗漏登记、图片有误还是误入资产目录，不得默认删掉已选合格配图只为了让部署通过。
- **真源分离。** 预览期的图片使用权不等于正式发布。得到作者明确发布确认后，才由正式发布流程把 draft 迁移到 `docs/blog/`，登记 `posts-meta.json` 并将预览重定向；保持一份当前正文和一份当前图片资产。

## 8. 失败处理与完成状态

- 生图失败或质量不足时，先按 Prompt Packet 记录失败原因并做一次定向修订；仍不合格则改用经授权来源图、精确 SVG/叠加层或正文表格/文字，不继续无目标重试。新文章首图不合格时不得声称完整图文预览已经通过验收。
- 未完成单图 Review Checklist 的候选，不得标记为最终资产；生成成功、像素足够或 CI 通过都不能替代视觉与语义验收。
- 如果当前环境不能把图片字节写入 GitHub，不能只创建 Markdown 引用。应明确指出二进制写入缺口，保留已验证的候选资产与可执行交接；不能声称线上已更新。
- 如果预览文件无法打开或下载，优先修复预览交付或直接发布；不要把失效的中转文件当作用户必须完成的步骤。
- 区分候选生成、最终资产规范化、文章登记、构建通过、Pages 部署成功、线上视觉验收六种状态；只报告实际完成的阶段。
- 交付时列出最终采用图片的资产路径、制作方式、Prompt Packet 路径、实际提交的 Final Prompt、模型调用次数、失败/修订原因及未完成验收项。若界面不提供模型内部改写 Prompt，只记录实际提交文本，不推测隐藏改写内容。

## 9. 本工作流的经验边界

本流程由 SaaS Build vs Buy 文章的视觉实验沉淀：生成式图文插图适合表达客户自建与供应商交付、功能复刻与真实替代、可信替代与议价条件；成本结构与决策框架仍由精确 SVG 承担。该案例证明混合工作流在此文可行，不证明所有博客都应使用五张图或同一风格。
