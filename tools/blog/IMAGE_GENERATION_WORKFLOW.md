# Blog 正文生图工作流

版本：1.3｜更新：2026-11-08

本文件定义正文概念插图、图文结合插图的实际制作流程。它不替代写作 SOP、图表语义规范或网站发布契约。

## 1. 职责与边界

- `blog-sop.md`：决定何时规划配图、配图承担什么阅读任务，以及何时进入制作；不维护提示词工程和图片处理细节。
- `blog-charts-spec.md`：决定图表是否必要、图形关系如何表达、流程/决策逻辑是否准确；不规定生图风格。
- `VISUAL_GUIDE.md`：维护视觉语言、图像类型选择、资产规格、图文一致性与实际页面验收；本文件补充生图的执行步骤。
- `blog-review-checklist.md`：在终审时检查图文协同、事实边界和最终交付；不重复维护生图操作说明。
- `WRITING_GUIDE.md` 与发布脚本：维护 Markdown、metadata、资产登记、HTML 生成和公共产物发布契约。

生图是视觉制作方式，不是事实来源，也不自动获得改变正文论点、数据、流程或产品行为的权限。

**生图前先判断是否应使用来源素材。** 真实设备、人物、事件或论文证据图可能比概念示意更适合；此类素材由 `VISUAL_GUIDE.md` 的来源、许可、署名、裁切及资产登记要求管理。本文件仅在已决定自行生成图像时负责提示词、视觉迭代和验收，不要求每张图都由生成式模型制作；来源不明确或权限不足时不抓取或热链发布。

## 2. 先定义图片任务，再决定是否生图

每张候选图先写一行图片简报：

- **位置**：对应正文哪一段/哪一节；
- **阅读任务**：进入主题、具象化场景、说明抽象概念、呈现对照、解释机制或帮助回顾；
- **核心对象与关系**：画面必须出现什么，谁与谁对照/连接/共同完成什么；
- **文字策略**：纯视觉、标题加少量标签，还是精确节点文字；
- **证据边界**：哪些内容来自事实，哪些只是概念隐喻；哪些数字、UI、Logo、品牌或产品细节禁止虚构；
- **与相邻图文的分工**：它新增什么视觉信息，是否重复正文或其他图片。

按任务选择表示方式：

| 表达任务 | 首选方式 | 边界 |
|---|---|---|
| 概念、场景、隐喻、封面 | 内置生图模型 | 不伪装成实测或纪实素材 |
| 图文结合的编辑插图 | 生图模型，可含短标题/标签 | 文字必须短、已确认且逐字校对 |
| 精确流程、决策树、数据与比较关系 | 先用 SVG/HTML 建立可核验的逻辑源；核心流程图完成后默认进行一次生图视觉化探索 | 生图结果是视觉候选，不是逻辑真源；节点、箭头、条件、分支和文字必须逐项对照逻辑源校验 |
| 真实产品界面、研究截图、原始证据 | 原始来源素材 | 不得用生图重绘冒充真实截图 |
| 复杂图文混合 | 生图底图 + 精确排版层 | 生图只负责氛围/主体，准确文字和关系由确定性图层负责 |

不能因为生图更漂亮，就让它替代需要精确表达的流程图或数据图；也不能因为 SVG 可控，就把所有概念插图都做成矩形卡片。**流程图采用双阶段制作：确定性绘图先保证逻辑，生图模型再探索视觉表达；只有通过语义与文字校验的结果才能成为最终展示图。**

### 独立图片资产与输出尺寸验收

当任务需要正文插画/照片时，生成或检索的目标必须是**可直接插入文章的独立图片资产**，而不是网页截图、文章 mockup、UI 页面或把多章内容塞在一起的信息图。生成结果必须在加入预览前检查实际宽高、主体、文字、边缘和压缩；尺寸不符合 `VISUAL_GUIDE.md` 源图门槛时，不得仅靠插值放大。若生成模型连续返回错误媒介或低清候选，应停止无效重试，转用许可明确的原始照片，或暂时不放图，并说明原因。

## 3. 建立整组视觉约定

同一篇文章先确定整组视觉方向，再逐张生成。至少明确：

- 画面风格与媒介（编辑插画、纸雕、扁平矢量、轻 3D 等）；
- 主色、强调色、背景与明暗；
- 画幅比例、主体位置和留白；
- 人物/物体的视觉一致性（若跨图复用）；
- 图中文字的字体气质、字号层级、字重和标签样式；
- 禁止元素：无意义科技装饰、无来源数字、虚构 UI、误导性品牌标识、难读小字等。

风格统一不等于每张图使用同一构图。图片可以分别承担场景、机制、对照和回顾任务，但应像同一篇文章中的一组编辑视觉。

## 4. 提示词与生成迭代

提示词至少包含以下信息，按实际任务取舍，不要求机械填满：

```text
Purpose: <这张图要完成的阅读任务>
Core message: <只写已确认的文章判断>
Subjects and relationship: <对象、对照、连接、共同目标>
Composition: <横/纵构图、主体位置、留白、视觉层级>
Style: <整组约定的媒介与视觉语言>
Palette: <整组颜色及强调色角色>
Text: <无文字，或逐字给出已确认的短标题/标签>
Evidence constraints: <禁止虚构的数字、UI、Logo、品牌和事实>
Do not: <乱码、小字、无意义图标、误导性隐喻、装饰噪声>
```

生成时遵循：

1. 对重要图片先探索少量有实质差异的候选构图；候选应测试不同视觉表达，不是只换随机装饰。
2. 先判断画面是否表达正确，再判断美观；检查对象、数量、角色、方向、因果和隐喻是否与文章一致。
3. 发现明确问题时做定向迭代，例如只调整标题位置、删去虚构数字、改变双方角色或简化背景；不要每轮同时改动所有维度。
4. 一旦选定方向，后续图片引用已选图作为风格参考或沿用整组提示词约定，避免每张重新发明视觉系统。
5. 生图候选与最终发布资产分开保存。未选中的候选不进入正式资产目录。

对于承担主要论证的流程图/决策图，逻辑源确认后默认生成一张生图视觉化候选；简单流程或纯数据图若没有明显视觉收益，可以跳过。候选数量由图片重要性、生成成本和差异程度决定，不设固定轮数或张数配额。若一轮已得到满足任务的候选，不为凑数量继续生成。

### 核心流程图的视觉化重绘

1. 先按 `blog-charts-spec.md` 完成唯一、可编辑的 SVG/HTML 逻辑源，确认节点、方向、分支、必要/充分条件、回路和图注；逻辑未冻结前不进入生图。
2. 将逻辑图或逐字确认的节点文案交给生图模型，明确要求只改善构图、层次、图标、留白、材质和视觉节奏，不得新增、删除、合并节点，不得改变箭头方向、分支条件或因果关系。
3. 将生图结果与逻辑源逐项对照：节点全集、节点文案、箭头起终点、分支标签、条件限定、数字/单位、反馈方向及图注必须一致；再检查实际正文宽度和手机视口下的可读性。
4. 若生成图有任何文字错误或关系偏差，不得直接采用。可做一次定向修正；仍不准确时，只吸收它的视觉风格，由确定性 SVG 重建最终图，或使用生图底图加精确排版层。
5. 保留可编辑逻辑源。生成式位图即使被选为展示资产，也不能被称为可编辑流程图；未来修改流程时先改逻辑源，再重新渲染和校验。

## 5. 图片文字规则

图片文字可以是有效的编辑设计元素，不再默认要求概念插图完全无字。但文字必须帮助识别主题、对象或关系，而不是把整段正文塞进画面。

- **可直接由生图模型绘制**：短标题、短标签、少量关键词；提示词应逐字给出确切文案。
- **优先后期精确排版**：长句、数据标签、复杂术语、法律/技术细节、密集列表、需要严格对齐的文字。
- **禁止无依据内容**：未经来源支持的数字、客户数量、可用率、性能指标、产品 UI、Logo、功能清单或看似真实的仪表盘数据。
- **逐字校对**：检查错别字、漏字、重复字、标点、大小写、数字和单位；模型画对大意不代表文字准确。
- **控制文字密度**：通常一个核心标题加少量对象/关系标签即可；详细解释交给正文与图注。
- **文字与画面冲突时**：先改构图或删减文案，不把不可读小字视为可接受折衷。

如果图片只承担概念搭配，图中文字不应引入正文未建立的新结论；若文字承担论证内容，必须由正文和来源支撑。

## 6. 选图与整篇组合

不要按生成顺序自动选第一张，也不要把所有候选全部塞进文章。逐张判断：

1. 是否准确服务对应段落？
2. 是否让读者更容易进入、理解、比较或回顾？
3. 是否与正文/现有图表重复？
4. 是否包含虚构事实、错误标签或误导性隐喻？
5. 缩小到实际正文宽度后，主体和文字是否仍清楚？
6. 与整组图片的风格是否一致？
7. 对流程图/决策图，是否与可编辑逻辑源逐项一致；生图是否只改变视觉表达，没有改变语义？

最终组合应有视觉节奏：概念插图可以引入问题，精确图表负责解释结构或决策；不是每张都要承担同一功能。保留必要正文解释，不因图片存在而删除证据、条件和边界。

## 7. 从候选到正式资产

1. 原始候选放在 Git 忽略的 `build/blog-image-work/<slug>/`，不得直接写入正式图片目录。
2. 只选通过内容与视觉检查的图片；使用 `scripts/prepare-blog-image.js` 生成符合 `VISUAL_GUIDE.md` 的规范化 WebP。不得自行改扩展名伪装格式，不得覆盖已存在的正式资产。
3. 精确图继续使用静态、自包含 SVG；不把生成式位图改名为 SVG，也不把 SVG 转成位图后再声称可编辑。
4. 将最终资产写入 `assets/images/blog/<slug>/`，使用能说明图片任务的 kebab-case 文件名。
5. 在 `docs/blog/<slug>.md` 的独立图片行中登记 alt/caption，并在 `posts-meta.json` 的 `visuals.inline` 中同步 src、alt、caption、width、height；两处必须完全一致。
6. 运行图片契约检查、文章生成、搜索资产生成、taxonomy 与 search foundation 检查、public dist 构建和检查。不得只改 Markdown 或 metadata 就声称图片已发布。
7. GitHub Pages 工作流只负责仓库检查、公共产物构建与部署。**不要为了上传图片或生成文章而临时修改部署 workflow、扩大其权限或把写仓库逻辑塞进部署 job。** 应在发布前的本地/Codex/Work 写入阶段准备并提交源稿、资产、metadata 和生成 HTML；标准 CI 验证后再部署。
8. 发布后核对线上文章实际加载的图片、目录/精选入口（如适用）及图片顺序；未做浏览器截图验收时，明确标注未验收，不以 CI 全绿代替视觉检查。

## 8. 失败处理与完成状态

- 生图失败或质量不足时，允许改用精确图、简化视觉任务或无图；不得因此阻断文章正文发布。
- 如果当前环境不能把图片字节写入 GitHub，不能只创建 Markdown 引用。应明确指出二进制写入缺口，保留已验证的候选资产与可执行交接；不能声称线上已更新。
- 如果预览文件无法打开或下载，优先修复预览交付或直接发布；不要把失效的中转文件当作用户必须完成的步骤。
- 区分候选生成、最终资产规范化、文章登记、构建通过、Pages 部署成功、线上视觉验收六种状态；只报告实际完成的阶段。
- 交付时列出最终采用图片的资产路径、制作方式（生图/精确绘图/混合）、最终提示词或必要的制作说明，以及未完成的验收项。

## 9. 本工作流的经验边界

本流程由 SaaS Build vs Buy 文章的视觉实验沉淀：生成式图文插图适合表达客户自建与供应商交付、功能复刻与真实替代、可信替代与议价条件；成本结构与决策框架仍由精确 SVG 承担。该案例证明混合工作流在此文可行，不证明所有博客都应使用五张图或同一风格。
