# 产品分析博客生成 SOP v32

---

## 职责与读取边界

**本 SOP 只负责探讨、收敛、大纲确认和正式写稿时的决策。** 写完后的逐项审查、直接修复和交付验证由 `tools/blog/governance/blog-review-checklist.md` 负责；图表的内容设计、实现与 QA 由 `tools/blog/governance/blog-charts-spec.md` 负责。

> **长期真源**：本文件在 GitHub 的固定路径为 `tools/blog/governance/blog-sop.md`。Project Source 旧副本只视为迁移前快照，不再更新。

`$blog-human-writing` 负责两项补充工作：大纲确认前的材料承载力检查仍按需触发；**初稿完成后的活人感审校对正式博客默认必选，除非用户明确要求跳过，无需再次确认。** 它不能替代本 SOP、正式大纲确认或最终 Checklist。其长期权威来源固定为 GitHub `.agents/skills/blog-human-writing/`：`SKILL.md` 定义职责与入口，`references/` 保存详细执行规则。已安装的 ChatGPT Skill 只是运行时入口或缓存副本，不再与 GitHub 并列为第二真源；正式执行材料检查或活人感审校时，应先读取 GitHub 当前 `SKILL.md` 及对应 reference。若当前环境能够调用已安装 Skill，可在读取 GitHub 当前规则后使用它执行；若两者存在冲突，以 GitHub 当前内容为准并在本轮规范复盘中处理。GitHub 文件读取失败时必须说明该阶段未执行，不得假称已经完成。

博客 taxonomy 的长期权威来源固定为 GitHub `tools/blog/data/blog-taxonomy.json`。ChatGPT Project Source、本地副本或已安装兼容副本不再与 GitHub 并列维护；本 SOP 只规定**何时读取、如何判断、何时触发 taxonomy change**。网站发布契约和确定性校验以 GitHub `tools/blog/WRITING_GUIDE.md` 及相关发布脚本为准。

项目级硬约束、规范更新和单一当前版本原则统一由项目指令管理，本文件不重复维护。执行某一阶段时，只读取本 SOP 的相关章节；涉及图表、活人感、taxonomy、终稿 metadata 或最终审查时再进入对应规范。

### GitHub 规范真源与动态读取节点

正式博客使用以下长期真源：

- **分类 / tags / topics / concepts 规则**：`tools/blog/data/blog-taxonomy.json`；
- **历史文章 metadata 与关系现状**：`tools/blog/data/posts-meta.json`；
- **活人感 / 材料承载力规则**：`.agents/skills/blog-human-writing/SKILL.md` 及 `references/`；
- **网站发布契约**：`tools/blog/WRITING_GUIDE.md` 及相关脚本；
- **写作流程与终稿判断**：`tools/blog/governance/blog-sop.md` + `tools/blog/governance/blog-review-checklist.md`；
- **图表规则**：`tools/blog/governance/blog-charts-spec.md`。

为兼顾“动态更新”和“避免每轮重复读取”，固定使用以下节点：

1. **新文章启动**：读取最新 `blog-taxonomy.json`；系列文章另读对应 Series Brief。这里只建立当前合法 taxonomy，不提前替文章强行定类。`posts-meta.json` 属于历史文章资产，仍须遵守下文“历史检索前独立起点快照”：先形成原始问题与独立起点，再读取历史 metadata，避免旧文反向锚定新选题。
2. **材料检查 / 活人感阶段**：每次真正执行 `$blog-human-writing` 时读取 GitHub 当前 `SKILL.md` 与对应 reference，不依赖模型记忆或旧安装副本。
3. **研究或写作中发现 taxonomy 缺口**：立即进入 taxonomy change 流程，不等到 Codex 发布时再猜。
4. **终稿 metadata 冻结前**：重新读取最新 `blog-taxonomy.json`，因为文章可能跨多天完成，且正文主线或 taxonomy 均可能变化。
5. **Codex 发布**：发布端再次读取同一 taxonomy，只做合法性与一致性校验，不重新做内容判断。
6. **每篇正式博客完成后**：默认执行一次“规范沉淀复盘”，把本轮暴露的可复用规则变化同时纳入 SOP、Checklist、图表规范、taxonomy、GitHub `blog-human-writing`、发布规范/脚本和（如适用）Series Brief 的评估范围；不再额外询问“要不要复盘”。只有确认存在跨文章、可复用且已经被本轮事实验证的规则变化时才更新对应真源，文章专属经验不进入长期规范。

### Taxonomy change 流程

如果当前文章无法被现有 `category / tags / topics` 准确表达，不得临时造词、选择“最接近”的值或把问题留给发布 Codex。先提出 taxonomy change，至少说明：

1. 变更层级（category / tag / topic）；
2. 候选名称；
3. 准确定义；
4. 现有词为什么覆盖不了；
5. 与最接近现有词的边界；
6. 可能受影响的历史文章；
7. 变更类型（新增 / 重命名 / 合并 / 废弃 / 定义调整）。

用户确认后，优先更新 GitHub `blog-taxonomy.json`，再执行历史 taxonomy audit。audit 只列出需要人工复核的历史候选，不因为新增词或定义变化自动批量重分类旧文章。当前文章只有在 taxonomy 真源更新后才能正式使用新值。

## 第一步：探讨（对话阶段）

先用苏格拉底式提问摸清以下几个维度，不要跳过直接输出。**进入实质探讨后，只要核心判断涉及可外部验证的事实、案例、趋势、厂商路线、数据或实践，默认主动联网补证，不等待用户提供链接；搜索用于推进判断，不用于堆砌材料。**

### 主动证据搜索与证据角色

外部证据检索是探讨阶段的伴随能力。新文章形成最基本的问题或初步判断后，凡是存在可验证的事实、案例、行业趋势、厂商路线、数据或实践，应主动搜索，而不是等待用户先提供链接或案例。

默认按证据角色组织，而不是按“来源数量”堆叠：

- **一手文件 / 官方发布**：用于确认产品能力、发布日期、架构说明、厂商自身战略重点；厂商 Blog 可以证明“该厂商正在重点解决什么问题、产品边界如何变化”，不能单独证明客户已普遍采用、效果已被验证或行业已经形成共识。
- **独立第三方研究 / 主流研究机构**：用于验证市场规模、采用情况、跨厂商趋势和行业共性，避免只从厂商叙事推导行业结论。
- **真实企业实践 / 客户案例**：用于说明问题在实际运行中如何暴露。厂商自述的内部实践需注明其来源性质，不自动等于独立效果证据。
- **开发者、研究者、行业从业者社媒或社区讨论**：用于提供具体问题、反例、实践者视角或早期信号，不能单独证明行业普及率、共识或效果。正式引用时首次出现交代与当前问题有关的最低必要身份背景，不用点赞数、粉丝数替观点增加权威性。
- **作者第一手观察**：适合作为问题触发、现实锚点或边界校准，但不能从单次交流直接外推整个行业。

当核心判断依赖“多家厂商正在收敛”时，优先使用多家彼此独立的一手信号，并尽量补第三方研究、客户实践或从业者证据交叉验证。证据已经足以支撑当前主张后停止扩充，不为了显示研究量继续增加相同作用的品牌和案例。

**厂商发布与真实采用分层。** 官方发布、PR 稿、路线图和融资材料首先证明“能力已经提供 / 厂商准备往哪里走 / 公司如何叙述自己”，不自动证明用户已经迁移、形成稳定习惯、获得可重复效果或市场结构已经变化。当核心判断从“功能存在”升级为“用户采用 / 效果 / 趋势 / 迁移”时，默认继续做一次发布后的时间线与反向检索：至少区分发布时点、后续真实用户或客户实践、独立第三方数据/研究。后两层缺失时，主动把结论降级为“产品路线 / 早期信号 / 待验证实践”，不得把 PR 的未来时态改写成已经发生的市场事实。

用户主动提供的新闻、链接、人物观点或案例，默认作为**候选证据**进入上述体系；除非它推翻当前核心机制，否则不因为材料本身有趣或宏大就改写文章主线。

### 历史文章动态关联检索

历史文章检索属于探讨阶段的伴随能力，不是开题时执行一次后就结束的固定步骤。目标不是增加内链数量，而是利用作者过去已经公开发表的判断、框架、案例和认知变化，提高新文章的内容增量与观点连续性。**它首先是碰撞检查和资产复用机制，不是新文章的选题生成器。** 搜到历史文章只意味着值得检查，不意味着当前文章应该向它靠拢；最终确认不相关时，正常结果就是不引用、不建立关系，也不为了制造连续性修改当前主线。

#### 历史检索前先保留独立起点快照

在第一次读取历史文章 metadata 或正文之前，当前选题一旦已经形成最基本的问题和初步判断，先在内部留下一个极简的**独立起点快照**。它不是正式大纲，也不增加一次用户确认，只用于给后续历史检索提供未受旧文影响的比较基准。

快照通常记录五项：

1. 当前原始问题是什么；
2. 当前最初判断或待验证假设是什么；
3. 为什么现在值得研究或写这篇；
4. 当前初步边界和明确不讨论什么；
5. 如果完全不知道自己以前写过什么，接下来原本准备往哪里研究。

如果用户一开始只有非常宽泛的主题，可以先完成形成问题所必需的第一轮探讨，再立即留下快照，然后才做历史检索。快照不锁死后续判断；新证据、重复风险或旧观点冲突都可以让主线变化，但后续需要能够解释变化的内容理由，而不是只因为某篇旧文“看起来能连上”。

#### 首轮扫描什么时候执行

完成独立起点快照后，读取 GitHub 最新的 `tools/blog/data/posts-meta.json`。不要为了遵守流程，在问题尚未成形时机械检索历史文章；也不要让历史候选反过来替代原始问题的形成过程。

粗召回主要使用 `title`、`summary`、`concepts`、`topics`、`tags`、`category`。其中 `title + summary + concepts` 承担主要语义召回，`topics / tags / category` 用于辅助判断和范围过滤。元数据命中只表示“值得进一步检查”，不能直接推出“正文应该引用”。

#### 候选池与正文深读

粗召回阶段不设置固定的候选数量上限。候选可在内部区分为：

- **高相关候选**：当前就值得读取正文，可能改变论点、大纲或避免内容重复；
- **潜在相关候选**：当前关系尚不够清楚，先保留，等讨论进一步收敛后再决定是否深读；
- **弱相关候选**：只有关键词、公司、模型或大类重合，不继续处理。

正文深读数量根据实际相关度控制。高相关只有 1 篇就读 1 篇；确有多篇都可能影响当前判断时，不因人为数量上限提前截断。也不要为了“召回完整”而把大量弱候选全部深读。

历史文章进入候选池后，默认只允许它们承担三类作用：发现已写过的内容、复用必要前提、暴露新旧观点变化。**“发现一篇相关文章”本身不能成为新增一级章节、扩大题目、引入旧框架或改变文章主线的充分理由。** 如果某个新方向只有在看到旧文后才出现，应回到独立起点快照检查：它是因为重复/冲突等真实信息而必要变化，还是只是为了让文章更容易互链。后者不进入当前文章。

#### 历史正文读取优先级

历史文章关联判断关注的是作者最终公开发表给读者的内容，因此正文读取优先级为：

1. 当前线上正式发布页面；
2. GitHub 中的 `tools/blog/posts/<slug>.html`；
3. `docs/blog/<slug>.md`。

线上页面或 HTML 优先用于回答“过去实际发表了什么观点”；Markdown 仍然是新文章写作、修改和长期维护的正文源。如果线上页面与 Markdown 有差异，不应默认用 Markdown 覆盖历史发表事实。

#### 什么叫实质关联

只有满足以下一种或多种情况，历史文章才进入后续引用或结构设计：

- 两篇文章回答相同或直接承接的问题；
- 使用相同或高度相关的因果机制；
- 新文章明显延伸旧文章的判断；
- 新证据修正、挑战或重新限定旧判断；
- 旧文章已经完整解释了当前文章需要使用的概念或框架；
- 旧文章中的案例、事实或分析能直接参与当前论证；
- 不说明两篇文章的连续关系，会让读者误解作者当前判断。

同属 AI、Agent、产品、商业等宽泛大类，出现相同公司、模型、人物或产品名称，或者只有关键词重合，都不构成实质关联。不要为了增加站内链接数量而引用旧文。

#### 探讨过程中的动态重搜

首轮召回不是最终候选集。探讨过程中出现以下变化时，按需再次检索：

- 一句话核心论点发生明显变化；
- 出现新的核心概念、因果机制或决定结论的限制条件；
- 案例从引子转为核心案例，或承担的论证角色发生变化；
- 文章讨论范围明显扩大或缩小；
- 用户或模型自然意识到某个判断可能在历史文章中写过；
- 准备新开一个章节，而该章节可能重新完整解释过去已经展开过的问题。

不要每轮对话重复全库检索。只有讨论对象发生实质变化时才触发。

#### 必要时使用全文兜底搜索

如果当前已经形成一个明确而重要的概念、机制或判断，但 metadata 没有召回预期历史文章，或者有理由怀疑以前写过相关内容，可以对已发布历史文章做定向全文搜索作为兜底。全文搜索用于弥补 metadata 的召回缺口，不替代 metadata 第一阶段筛选，也不意味着需要建设向量数据库、知识图谱或新的平行索引。

#### 大纲确认前做最终覆盖扫描

当核心论点基本稳定、准备输出正式大纲时，基于当前版本重新提炼一句话主结论、核心问题、主要因果机制、每个一级章节准备回答的问题、核心案例和概念，再对历史文章完成一次覆盖扫描。

这一轮重点确认：

1. 是否存在应该承接的重要旧文章；
2. 当前准备完整论证的内容是否以前已经完整写过；
3. 新文章真正新增的判断是什么；
4. 当前观点与旧文是否存在需要解释的变化或冲突。

如果这一轮没有确认任何高相关历史文章，记录“无实质历史关联”，不为了完成流程继续寻找关系，直接进入正式大纲确认。

#### 条件必选：历史独立性与增量评审

只有最终覆盖扫描确认存在一篇或以上**高相关历史文章**时，才在正式大纲确认前自动执行本评审；没有高相关旧文时跳过。它的目标不是再做一次历史检索，而是检查历史材料有没有反向塑造当前选题，并验证新文章是否值得独立成文。

评审集中回答六个问题：

1. **独立性**：如果完全没有看到这些历史文章，当前核心问题、标题方向和主线是否仍大体成立？若明显变化，变化是否来自“发现重复”“发现旧观点冲突”“新证据要求收窄/修正”等内容理由，而不是为了形成站内连续性？
2. **核心问题差异**：最相关旧文究竟回答什么，当前文章究竟回答什么？不能用公司、模型、关键词或大类不同代替问题差异。
3. **内容增量**：读过旧文的人，当前文章新增了什么？有效增量可以是新问题、新机制、新证据、新边界、新反例、决策方法或旧判断修正；只换近期案例、模型或表述通常不够。
4. **深度增量**：当前文章是否至少在机制、粒度、因果链、边界、决策落地或证据强度中的一个方向明显深入，而不只是“比旧文更长”。
5. **关系必要性**：对每篇高相关旧文判断“必须承接 / 有价值但非必要 / 仅同主题 / 不相关”。系统召回不自动意味着正文引用，更不自动意味着发布层强关系。
6. **删掉旧文测试**：暂时移除历史文章名称、链接和承接段后，新文章的核心问题与主体论证是否仍能独立成立？如果不能，必须说明它究竟推进了旧文哪一层，否则应考虑合并、缩小或暂缓成文。

评审结果只需形成简洁结论，不新增一套长报告。可得出“独立成立 / 需收窄或重构 / 与旧文重复度过高不宜单独成文”等结果。只有评审通过，历史文章关系才进入正式大纲确认。

#### 历史检索对当前文章的三个结果

历史检索至少服务三个问题：

- **可复用资产**：旧文中哪些观点、定义、框架、案例或证据可以通过行内链接承接；
- **重复风险**：哪些内容已经在旧文完整展开；新文章原则上只复述理解当前论点所需的最小前提，然后链接旧文，把正文篇幅用于新增量；
- **观点变化**：新旧文章明显不一致时，判断究竟是条件变化、讨论范围不同、新证据导致修正，还是旧判断本身需要更新。不要无意隐藏过去的不同判断。

内部可使用“应引用 / 可选引用 / 不应引用”进行判断，但不要求每次完整向用户展示候选列表。只有会影响核心论点、章节设计、作者立场或文章增量的历史关系才主动提出。

#### 元数据召回失败的反馈闭环

如果某篇历史文章最终被确认高度相关，却没有在合理的 metadata 查询中进入候选，应反查原因。仅当遗漏的信息本来就是该历史文章的重要内容时，才考虑更新它的 `summary` 或 `concepts`；如果这种关联只是由当前新文章的特殊语境临时产生，而不是旧文自身的核心主题，不修改 metadata。

不要为了让每一次偶然关系都可召回而不断扩充 `concepts`、建立文章关系或增加新的平行索引。**历史检索召回与面向读者的显式文章关系是两层机制：前者追求发现候选，不能通过人为绑定提高召回率；后者只有在历史正文精读已经确认存在明确的前提承接、观点延伸、观点修正或直接互补时，才可在发布 metadata 中沉淀。普通引用、案例复用、关键词或主题相似不形成显式关系。**

### 探讨阶段的收敛与确认节奏

探讨的目标不是无限延长对话，而是在不跳过关键判断的前提下，尽快收敛到可确认的大纲。默认遵守以下节奏：

1. **只确认会改变文章方向的分叉。** 需要用户判断的通常包括：核心论点、文章类型、案例角色、覆盖边界、作者立场和第一手经历。术语命名、局部章节位置、可直接推导的定义压缩等低影响事项，默认自行判断并在收敛摘要中说明。
2. **不要逐点滴灌式推进。** 用户回答一个问题后，应主动整合本轮已解决的相关问题，继续完成同一层级的分析，不要每次只追加一个新问题再等待“继续”。
3. **把“继续”理解为收敛授权。** 当用户只回复“继续”时，默认表示允许完成当前阶段剩余分析。此时应批量处理尚未解决的同类问题，并尽快输出收敛摘要或大纲确认稿，而不是再拆出多轮单点讨论。
4. **每 2—3 轮实质讨论做一次收敛。** 输出“已确定 / 仍待确认”摘要，至少包括：一句话论点、最强反驳、案例作用、方法框架、明确不讨论的内容。待确认项控制在 1—3 个真正影响结构的分叉。
5. **避免换一种说法重复确认。** 一个判断一旦得到明确答案，后续只在新证据或结构冲突出现时重新打开。
6. **没有实质待确认项时，主动进入大纲确认。** 不为了“多讨论几轮”继续延展术语或边缘问题；长文写作仍需在大纲确认后获得用户许可。

### 研究树与单篇主线锁定

探讨可以形成比单篇文章更大的研究树，但研究树用于保存分支，**不等于当前文章目录**。当一句话核心问题、主结论边界和“明确不讨论”已经收敛后，当前文章进入主线锁定状态。

锁定后的新材料默认只进入四类：

1. **核心证据**：直接支撑当前核心机制或结论；
2. **反证 / 边界**：限制当前主张、提供最强反例或说明适用条件；
3. **背景材料**：提高现实感或解释上下文，但不承担核心论证；
4. **后续分支**：有独立研究价值，但会把当前文章带到新的问题。

只有以下情况才重新打开主线：新证据直接推翻当前核心判断；暴露核心因果机制错误；或证明当前文章与历史文章缺乏独立内容增量。**“更有趣”“更宏大”“更像战略问题”“又找到一家大厂”都不是换主线的充分理由。**

如果需要改主线，必须先明确说明：原主线哪一处失效、新证据改变了什么、为什么不能只作为证据或后续分支处理。否则继续按已确认主线推进。

### 候选选题的承载力与作者站位

当同一研究树存在多个可成文分支时，不按“哪个题目更大”选择，优先比较：

- **证据承载力**：现有一手、第三方、企业实践和反证是否足以压住主张；
- **作者承载力**：作者是否有真实工作观察、使用经验或可信观察位置，避免只靠 AI 浏览公开信息宣布宏大终局；
- **历史内容增量**：相比已发布文章是否存在清楚的新问题、新机制或新边界；
- **现实用途**：是否能提升作者当前工作、学习或产品判断，而不只是得到一个漂亮观点。

证据或作者承载力不足时，优先缩小主张、改成开放问题、暂缓成文或保留为研究分支，不为了维持选题规模强行写完。

### 产品分析类

1. **产品定位**：它解决了什么人的什么问题，真实用户画像是谁
2. **核心产品决策**：关键设计选择是什么，每个选择的 trade-off 是什么
3. **商业逻辑**：盈利路径、开源/闭源选择、生态策略
4. **边界与局限**：哪些场景走不通，为什么
5. **竞争格局**：谁会来抢这个市场，从哪个方向打

同时收集作者的**第一手经验**：
- 你什么时候开始用，使用路径是什么
- 工作中有没有遇到过相关场景
- 对产品前景有多大把握，判断依据是什么

### AI 产品 / AI Builder 文章的增量判断

当文章明确采用 AI Product Builder、AI PM 或垂直 AI Builder 视角时，不能只复述通用 PM 的“理解需求—设计流程—完成闭环”。至少需要补出 AI 带来的增量判断：

1. **需求与业务结果**：用户为什么提出需求，现有流程的真实痛点是什么，解决后改变哪个业务结果；
2. **AI 适用性**：任务是否适合生成式 AI，还是更适合检索、规则、确定性计算、传统自动化或流程改造；
3. **AI 参与边界**：哪些环节交给模型，哪些必须由规则、系统或专业人员完成；
4. **运行条件**：模型需要哪些上下文、权威数据、工具和权限；
5. **不确定性治理**：如何评测、暴露置信不足、人工审核、失败回退和保留责任记录；
6. **业务流转**：结果由谁使用、写回哪里、触发什么后续动作。
7. **长期约束与当前实现分离**：判断一项 AI 产品、技术或机制的长期价值时，区分“真实任务长期需要解决的问题 / 约束”与“今天承载它的实现形式”。底层需求持续存在，不代表当前 Prompt、Workflow、Skill、GUI、人工确认或其他载体也会持续存在；反过来，当前载体被模型、Agent 或平台吸收，也不代表它解决的业务对象、状态、规则、权限、责任或验收要求已经消失。

不要求每篇文章机械展开七项，但作者建议必须体现至少一项 AI 特有的判断，否则应降低“AI Builder”限定或补足 AI 增量。

### 现象/趋势类

1. **现象的边界**：这个现象在哪些场景下成立，哪些场景下不成立
2. **作者的第一手观察**：你是从什么角度接触到这个现象的，有没有具体经历可以作为佐证
3. **核心反直觉判断**：这篇文章和“大家都知道的结论”有什么不同，差异在哪里
4. **最强的反驳**：什么证据能推翻你的判断，你怎么应对

### 科普/手册类

1. **覆盖范围**：文章覆盖哪些概念、技术环节或决策阶段，哪些明确不在范围内
2. **目标读者**：深度落在概念层（是什么/为什么）、决策层（trade-off/选型），还是实操层（参数/代码）
3. **叙述视角**：纯技术工程师视角、AI PM 决策视角，还是混合
4. **文章用途**：读者读完后要建立什么认知地图、作出什么决定或完成什么工作
5. **手册变体**：属于技术链路手册、决策/流程手册，还是概念总览；不同变体不强行套用同一节内模板

科普/手册类文章不强制使用反直觉论点或第一人称贯穿全文，但仍需确定一个读者最终应记住的主结论。完整性不能替代主线，所有分类、流程和表格都应服务于这一个结论。

技术链路手册通常需要业务场景分类框架与固定节内结构；决策/流程手册则更需要尽早提供全局地图，并沿真实判断链逐步展开。两类文章都应保持跨节术语与映射一致。

### 关于引子和核心论点的关系

在探讨阶段需要确认：这个产品或现象在文章里是主角还是引子？如果是引子，作者真正想讨论的更大判断是什么？这个区分会直接影响标题视角和结构设计。

### 近期新闻/商业事件作为引子的处理

近期新闻适合作为“触发问题的信号”，不自动等于核心论点的证据。开头优先控制为三步：交代事实 → 说明边界（它不能证明什么）→ 抛出本文问题。若同一个问题在后续又被重新提出，应合并成一次，避免引入阶段连续出现两个含义相同的提问。

上市、融资、产品发布、客户数字等商业事件，可以用来说明“这个方向开始进入现实商业系统”，但不能直接证明通用技术路线已经成熟。

### 知识密度较高文章的现实锚点

纯概念或方法论文章容易显得过硬。只要存在合适材料，应主动寻找 2—4 个与核心论点直接相关的产品发布、企业部署、平台能力或治理事件，作为现实锚点。每个案例必须先明确其角色：

- **问题触发**：说明为什么这个问题值得讨论；
- **现实信号**：说明某种架构或治理需求已经进入真实产品；
- **对照案例**：说明同一目标可能采用不同实现；
- **反例或压力测试**：检验本文判断的适用边界。

案例不能只用于“增加热度”，也不能把厂商发布直接写成技术路线已被证明。若案例不改变或支撑任何判断，宁可不写。

### 历史文章承接与系列文章关系

历史文章的关系不限于上一篇或正式系列。

如果当前文章依赖某篇旧文已经建立的判断、概念或框架，应在真正使用该前提的位置自然插入行内链接，并用一两句话复述理解当前文章所需的最小前提，不要求读者先完整读完旧文。

如果新文章是在旧文章判断上继续推进，应明确本次新增问题是什么；不要把旧文章已经完整论证的内容再次作为主体展开。如果新判断修正或重新限定旧判断，应说明发生变化的条件、证据或讨论边界，而不是让两篇文章形成无解释冲突。

正式系列文章仍需说明与上一篇的递进、并列或修正关系，但“上一篇”只是历史文章关系的一种特殊情况，不限制对更早文章或跨系列文章的引用。

### 历史文章关系与发布层显式关系

正文历史内链与发布层显式文章关系承担不同职责，不能自动等同：

- **正文历史内链**用于当前文章真正使用旧文中的判断、定义、框架、案例或观点连续性时，为读者提供必要前提；
- **显式文章关系**用于文章发布后的“继续阅读”等导航，表达更强的认知连续性，只在关系经过正文精读确认后沉淀；
- 正文出现旧文链接，不自动意味着两篇文章存在显式关系；普通案例引用、背景材料和同主题文章不升级为强关系；
- 可沉淀的强关系只覆盖明确的前提承接 / 继续推进、观点修正 / 重新限定，以及直接互补；具体 metadata 字段和值由网站发布规范维护，本 SOP 不复制实现细节；
- 新文章若确认与旧文存在强关系，只记录本次新文需要声明的关系即可；历史正文不因未来文章出现而自动回改，读者侧的反向“后续延展 / 后续修正”等展示由网站机制负责；
- 没有明确强关系时允许不沉淀关系，不为了 SEO、填满“继续阅读”或形成知识图谱而强行绑定。

### 关于作者使用经验和第一手观察的诚实性处理

如果作者没有直接使用经验，不要假装用过。把“为什么没用”或“用了替代品”本身作为切入角度——这个视角往往比“我用了 7 天”更有辨识度，也更诚实。

工作中的真实经历可以作为第一手锚点，但采用**最小必要披露**：只保留会改变论证的信息。领导层级、客户全名、项目细节或内部组织关系如果不参与判断，优先改成自然的匿名表达，如“工作群”“一家头部券商”“一次客户交流”。只有具体身份本身与论证直接相关、且适合公开时才点名。匿名不能改变事实含义，也不能虚构不存在的模糊经历。

### 目标语境与术语校准

如果文章面向特定地区、行业或组织语境，遇到 `Pilot`、`Owner`、`Stage Gate` 等可能来自海外方法论、公司内部黑话或边界不统一的术语，应先验证目标读者是否真的这样使用，再决定是否保留。

- 行业边界不统一的概念，首次出现时给出“本文工作定义”，不要写成唯一标准；
- 目标语境中不常用的术语，优先改为读者熟悉的普通语言；
- 只有当术语差异会改变流程、责任或判断时才展开，不为了显得专业增加名词；
- 对不熟悉或存疑的行业用语，可在探讨阶段联网搜索本地厂商、采购文件和一手实践进行校准。\n- 中文正文中，非品牌名且确有必要保留的英文术语，首次出现优先采用“中文解释（English Term）”，后文优先使用中文；只有英文原词能显著提高精度时才继续保留。避免连续堆叠 Prompt / Context / Harness / Runtime / Loop / Graph 等术语而不给普通中文读者建立含义。

### 厂商自我定位与本文分析分类

厂商、项目或作者给自己的命名，只能证明其**公开定位和产品叙事**，不自动决定本文的架构或品类判断。分析时优先看实际承担的职责、能力边界和运行方式：

- 官方自称用于准确说明“它如何定义自己”，不得替厂商改写官方定位；
- 本文可以基于实际职责采用不同的分析视角，例如某产品官方称自己为 Assistant，但从运行职责看同时承担大量 Harness 能力；
- 当官方定位与本文分析分类不同，首次出现时同时说明“官方定位是什么 / 本文从什么维度如何理解”，避免让读者误以为厂商自己使用了本文术语；
- 不因项目名称里出现 Harness、Agent、Assistant、Platform 等词就直接完成分类；名字是证据之一，实际能力与职责才决定分析位置。

## 按需阶段：材料承载力检查（大纲确认前）

仅在用户明确要求“材料检查”“材料承载力检查”或显式调用 `$blog-human-writing` 时触发。优先按已安装 Skill 的材料检查模式执行；普通 Chat 无法调用时，先读取 GitHub 镜像后执行同一模式。按其判断“已足够 / 需补证 / 应缩小”，再回到本 SOP 完成正式大纲确认；详细检查方法不在本文件重复维护。

## 第二步：大纲确认

探讨结束后，输出大纲确认清单，**用户确认后才进入写稿**：

- 论点一句话版本（产品分析/现象类）或“主结论 + 覆盖范围边界”（科普/手册类）
- 候选发布分类（从 GitHub 当前 `blog-taxonomy.json` 选择；终稿 metadata 冻结时必须按最终正文再次复核）
- 文章类型（产品分析 / 现象趋势 / 科普手册 / 混合型）及手册变体（技术链路 / 决策流程 / 概念总览）
- 标题中的行业、角色和技术限定语，以及这些限定具体改变正文的哪些判断
- 节结构列表
- 每节回答的核心问题、承接的上一节结论，以及为下一节提供的前提
- 核心案例和图表各自承担的角色
- **历史文章关系与本文增量**：列出真正会影响本文的历史文章及其角色（前提承接、概念/框架/案例复用、观点延伸、观点修正或冲突处理）；同时说明哪些旧论点不再重复展开，以及本文相对历史文章真正新增的判断。没有实质关联时标注“无”，不强行寻找内链。若存在高相关旧文，同时带入已经完成的“历史独立性与增量评审”结论，至少说明核心问题差异、主要增量/深度和关系必要性。若其中存在值得面向读者公开的强关系，同时标记关系类型；“正文应该引用某篇旧文”和“应该形成显式文章关系”是两次判断，前者不自动推出后者。

### 分类、文章类型与标题限定语

正式分类和文章类型是两个维度：一篇文章可以是“产品分类的科普手册”，也可以是“商业分类的趋势分析”。分类应由正文的**核心问题与主要论证对象**决定，而不是由作者职位、标题关键词、案例公司数量或是否提到销售/技术决定。

当前四类可用一个问题快速区分：

- **技术**：能力为什么成立？
- **产品**：产品应该怎么做？
- **商业**：企业如何创造并捕获价值？
- **行业**：整个领域正在怎么变？

其中“商业”不再只等同于狭义财务分析。只要正文核心在解释企业如何把能力变成持续商业价值、为什么某类公司能获得这部分价值、价值如何在参与者之间分配，都属于商业问题；定价、收入、成本、TCO、采购经济性、Build vs Buy、单位经济、GTM、商业护城河、价值链、利润池、公司战略、TAM 与估值都只是这一问题的具体表现。

“行业”则用于解释产业/职业结构、市场演进、跨公司路线、生态与标准、组织形态或行业级竞争重心如何变化。**企业怎么赢**和**游戏本身怎么变**不是同一个问题：前者更接近商业，后者更接近行业。

上述四句只用于快速判断；合法值、完整定义和边界始终以 GitHub 当前 `blog-taxonomy.json` 为准。如果本 SOP 与 taxonomy 冲突，以 taxonomy 为准并在本篇完成后的规范复盘中修正本 SOP 的摘要性描述。

标题若加入“AI”“金融”“B 端”“中国”等限定语，正文必须明确说明这些限定改变了哪些判断、约束或方法。如果主体框架其实通用于更大范围，应写清“通用骨架 + 特定语境中被放大的增量”，而不是只靠标题和案例暗示特殊性；如果限定语没有实质作用，应删除或降低标题承诺。

### 唯一主结论与框架预算

即使是查阅型手册，也要先确定一个读者离开文章后最应记住的结论。其余判断应作为该结论的推论，而不是多个平行金句互相竞争。

大纲阶段同时控制框架密度：默认优先保留一张主地图和少量承担不同问题的辅助框架。不要为了“完整”连续制造“三层、四类、六项”等近义清单；数量不是框架成立的理由。若多套框架回答同一问题，合并；若回答不同问题，明确它们的上下位关系。

### 历史内容增量预算

大纲确认不仅检查文章内部有没有重复框架，也检查与历史文章之间有没有重复论证。

如果历史文章已经完整解决某个问题，新文章原则上采用“最小必要前提 + 历史文章行内链接 + 本文新增判断”，而不是重新复述整套旧框架。

只有在旧框架本身需要修正、当前读者无法在没有完整重述的情况下理解新论点，或者新的证据实质改变了原框架时，才允许重新完整展开，并需要说明这次为什么值得重写。

### 论点确定后的自查

找最强的反驳——什么证据会推翻这个结论？如果反驳成立，论点需要修正边界而不是整体放弃。常见漏洞是论点过于绝对，修正方向通常是加限定条件。

### 核心概念是否需要内部拆分

如果一个概念包含多个层次，需要确认案例和论点指向的是同一个层次，否则论点覆盖范围会比证据更宽，显得过于绝对。

如果标题或正文使用了自定义比喻/命名（如“屏幕内工作”“物理世界的 LLM 时刻”），需在引入后尽早给出工作定义，说明本文具体指什么、不指什么，避免读者用自己的理解代入。

### 论点延伸时的结构一致性检查

如果文章论点从具体案例延伸到更大范围，后续每一节都需要检查覆盖范围是否一致——延伸出去的节不能在下一节悄悄缩回去。这类脱节需要在大纲阶段就发现，不要留到写完再改。

### 章节问题链与全局地图位置

一级章节应构成连续的问题链：每一章只承担一个主要问题，承接上一章已经得到的结论，并为下一章提供必要前提。大纲确认时不要只列标题，还要用一句话说明“本章回答什么、为什么现在回答、回答后下一步才能做什么”。

对于决策/流程型手册，全局流程图或决策地图通常放在概念边界之后、详细分析之前：

1. 先让读者知道文章讨论的对象是什么、不是什么；
2. 随后提供一张短而完整的导航地图；
3. 后文章节沿地图逐站展开。

地图如果放得过晚，会退化为总结图而失去导航作用。大纲阶段只确认地图承担的结论、主要节点及其与后文章节的映射；节点容量、分叉、回退和视觉实现遵循 `blog-charts-spec`。

### 假设前置与证据后验

决策型文章要区分“开始前提出的假设”和“执行后得到的证据”。业务价值、成功标准、风险边界等不能等到评测章节才第一次出现：

- 开始阶段建立业务基线、价值假设和决策目标，说明为什么值得验证；
- 验证阶段再用结果判断价值是否发生、幅度多大、成本和风险如何；
- 成熟产品选型中，项目层面的价值可能已被认可，此时重点验证的是不同方案实现价值的能力、成本和适配风险。

同一个概念前后出现不算重复，只要前面是待验证假设，后面是验证证据，并明确写出两者关系。

### 自创框架的单一归属

如果文章使用自创框架（如“六层能力”），大纲阶段就指定一个唯一的完整展开位置，并明确标注“本文归纳/暂且归纳”。后续章节只能引用框架、选择其中一层深入，不能换一个角度再次完整枚举，否则会造成重复和割裂。

### 框架与图表候选

大纲阶段先判断某个分类、表格或流程图是否真的承担独立问题：

- 它回答的自然问题是什么；
- 与前后框架是否重复；
- 删除后是否影响主线理解；
- 是行业框架还是本文归纳；
- 最终采用正文、Markdown 表格还是正式图表。

详细的表格分类说明、覆盖边界、流程图画法和技术规范由 `blog-charts-spec` 管理；发布前是否满足这些要求由 `blog-review-checklist` 复查。

### 相邻框架的层级与映射

如果相邻章节连续出现两套框架，需要在大纲阶段判断它们是否处于同一抽象层：

- 如果回答的是同一个问题，应优先合并或压缩，不保留两套近义清单；
- 如果一套用于发现问题、另一套用于落地实现，需要明确写出上下位关系和映射；
- **多套框架共存时，除说明上下位关系，还需明确关系类型**：是一一对应、一对多还是只展开其中一个节点；是时间顺序、依赖顺序还是并列维度；表达的是必要条件、充分条件、观察指标还是解释机制。
- **两个框架恰好拥有相同数量的条目，不得默认逐项对应。** 如果后一框架只展开前一框架中的某一层、某一道分界或某个节点，应在首次出现时显式说明。
- 同一框架的一级字段应保持相近抽象层级。工具、状态等实现项如果可归入更高层概念，不应与业务结果、权限等并列硬凑；
- 如果后文反复只使用原框架的一部分，需回头检查原框架是否可以直接压缩。
- 如果前一框架列的是“资产/能力”，后一框架列的是“机制/功能”，先建立明确映射。后一组只是前一组的落地形态时，优先在同一节合并说明，不要换一套标题再次完整枚举。

### 章节层级与编号规则

- `###` 子标题用于同一章节中存在两个或以上并列子问题，或存在明确的内部结构时；避免一节下面只放一个孤立子标题。
- 只有真实的时间、推导或操作顺序才编号。并列概念不为了视觉整齐强行编号。
- 中文长文中的步骤标题优先使用“第一步 / 第二步 / 第三步”，同一组内保持一致。
- 同层级章节的命名方式应一致：都是问题句、判断句或动作句，不要无理由混用。

### 角色与责任的抽象层级

跨组织、跨公司的文章不要默认存在统一岗位名称。优先按“谁提供事实、谁组织过程、谁作专业判断、谁拥有最终授权”等责任与决策权组织，再在需要时补充常见甲乙方岗位示例。

- 只有当岗位差异会改变输入、判断标准或决策权时才单独区分；算法、后端、数据、测试等在高层流程中可合并为“技术研发方”；
- 过程牵引与最终决策必须区分：负责协调和汇总证据的人，不必然有权批准预算、采购或接受风险；
- `Owner` 等非统一岗位称呼若需使用，必须说明是本文工作称呼及其边界，不把作者的“Owner 意识”包装成行业标准职位；
- 人员可以重叠，责任不能消失或混写。

### 案例角色与贯穿强度
