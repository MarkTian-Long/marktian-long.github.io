# 博客评审官 Checklist v30

> **长期真源**：本文件在 GitHub 的固定路径为 `tools/blog/governance/blog-review-checklist.md`。Project Source 旧副本只视为迁移前快照，不再更新。
**使用时机**：内部完整初稿完成后、用户首次细看完整正文前，以及后续实质修改后的终审阶段。目标不是只列问题，而是完成“全量审查 → 直接修复确定性问题 → 再审查 → 汇报改动”。

**角色设定**：假设自己是一个对这个话题有真实了解、对 AI 生成内容有警觉、对逻辑漏洞敏感的读者。不是友善的编辑，是挑剔的同行。

---

## 审查执行协议

1. **先扫全文，后动手。** 不在发现第一个问题后立刻停下来汇报，先完成全部类别的扫描。
2. **区分确定项与待确认项。** 能根据正文、来源、规范直接判断的，属于确定项；涉及作者经历、立场、分类选择或多种方案均合理的，属于待确认项。
3. **确定项直接修改。** 不需要先向用户逐条申请确认，也不只给修改建议。
4. **一次性覆盖。** 同一轮尽量完成引用、事实、逻辑、叙述、格式和标题的全部修复，不采用“每次改一点”的方式。
5. **修改后重跑。** 每次修改后重新检查全部标题、摘要框、正文链接、参考资料和新增段落，直到不再发现新的确定性问题。
6. **正式博客默认先完成活人感审校，再做 Checklist。** 活人感规则的长期权威来源是 GitHub `.agents/skills/blog-human-writing/`。每次执行时先读取当前 `SKILL.md` 与 `references/prose-review.md`；已安装 `$blog-human-writing` 可作为运行入口，但不得覆盖 GitHub 当前规则。其改写属于实质修改，不能默认事实强度、引用对应和逻辑关系自动保持不变；若用户明确跳过、或 GitHub 当前规则读取失败导致审校未执行，需准确记录，不把流程描述成已完整执行。
7. **最后再汇报。** 向用户列出本轮已经修改的主要问题；只把真正无法自行判断的事项集中提出。
8. **不随意另起版本。** 默认修改当前稿；除非用户要求保留版本，否则不生成内容相近的 `v2`、`v3` 文稿。
9. **交付文件必须真实写入。** 修改或导出后重新读取关键片段，确认链接指向本轮实际生成的文件；工具报错或覆盖失败时，不得声称已经更新。
10. **完成状态必须准确。** 只有在占位符、链接、标题、表格、文件写入和确定性内容问题全部复查通过后，才能声称“已全部修改完成”。仍有草稿项时需明确列出，不把“完成首轮扫描”写成“无遗留问题”。
11. **多轮实质修改后做回归扫描。** 初稿形成后如果经历多轮局部重写、章节重组或一次以上结构性改动，终审不能只检查最后一轮改动；必须重新扫描全文，确认此前已经解决的问题没有因为后续 patch 或整体重写重新出现。
12. **首个完整正文默认先过审再交付。** 除非用户明确要求查看原始初稿，首次把完整正文交给用户细看前，应先完成活人感审校、本 Checklist 的全部适用项、确定性修复与必要复查；探讨阶段的局部试写、章节预览和图表确认不受此限制，但不得表述为已完成完整审查。

## 职责与触发边界

**本 Checklist 只负责初稿完成后的批判性审查、确定性修复、复查和交付验证。** 探讨、大纲与正式写稿方法由 `tools/blog/governance/blog-sop.md` 管理；图表出现时按 `tools/blog/governance/blog-charts-spec.md` 做完整图表 QA；活人感审校以 GitHub `.agents/skills/blog-human-writing/` 为长期权威来源，经过该阶段修改后，本文件重新核对事实、引用、逻辑和格式。taxonomy 的合法值和详细定义不在本文件复制，以 GitHub `tools/blog/data/blog-taxonomy.json` 为唯一真源。

所有文章执行第零至第三类，并执行第五类的历史文章关系基础检查；正式博客默认已在进入本 Checklist 前完成活人感审校，因此 3.22 默认执行；科普/手册、正式系列文章和图表专项仍按条件触发。**当本轮目标是导出/生成正式发布 Markdown，或当前 Markdown 已含 frontmatter 时，第六类“终稿 Metadata 与 Taxonomy”必选。** 项目级硬约束、规范更新和单一当前版本原则由项目指令统一管理，本文件只验证它们是否在当前交付物中落实。

## 触发顺序

第零类（格式、行内链接与引用完整性）→ 第一类（事实诚实性）→ 第二类（逻辑一致性）→ 第三类（叙述质量）→ 第四类（科普/手册类专项，按需触发）→ 第五类（历史文章关系与观点增量；基础检查默认执行，系列专项按需触发）→ 第六类（终稿 Metadata 与 Taxonomy；正式发布 Markdown 时必选）。

发现问题数量超过 5 个时，内部优先修复第零类、第一类和第二类，但**不要因此把审查拆成多轮用户确认**；仍应在同一轮完成所有可确定修改。

## 第零类：格式、行内链接与引用完整性

### 0.1 开头摘要框是否唯一且完整

逐项确认：

- 标题下是否有且只有一个 blockquote 摘要框？
- 摘要是否控制在一至两句话，覆盖全文主线与边界？
- 摘要是否没有堆砌全部技术名词、章节目录或过度展开论证？
- 摘要框之后是否有视觉分隔，再进入正文引入？
- 是否错误地把摘要框和 `## 引言` 同时当作两套必备结构，造成重复开场？默认只保留摘要框，正文直接进入引子。

### 0.2 正文是否误用 blockquote

除标题下摘要框外，正文不得使用 blockquote。逐段检查：

- 作者自拟的核心问题是否被写成 `>`？应改为普通段落或加粗提问。
- 工作定义、阶段结论和表格注释是否被写成 `>`？应改为普通段落、加粗落点或注释样式。
- 外部人物直接引语是否被写成 blockquote？应优先改为引号 + 行内链接 + 来源说明。
- 代码块、HTML 标签中的 `>` 不属于本项。

### 0.3 正文引用是否都有行内链接

逐段检查：正文中所有引用了具体新闻、报告、数据、合同条款、产品设计、政策规划的地方，是否都嵌了行内超链接？按优先级（数据/数字 > 具体事件 > 人物引用 > 一般观点），优先确保数字类引用有链接。

### 0.4 参考资料与正文引用是否一一对应

- 参考资料列表里的每一条，正文中是否能找到对应的行内链接？
- 正文中的行内链接，是否都在参考资料列表中有对应条目？
- 有没有“参考资料列表里存在、但正文从未引用”的来源？这类应删除。
- 正文替换或删除来源后，文末对应条目是否同步更新？

### 0.5 参考资料是否按来源可信度分层

参考资料列表是否分组呈现？分组至少包括：一手文件/官方发布、学术研究（同行评审或接近同行评审）、工具厂商数据（官方声称，需单独标注）、行业博客/分析文章（非同行评审，供参考）、近期商业信号/主流媒体、公司官方披露或招股书、创业项目/路演（如适用，需注明“早期、未经市场验证”）、社区讨论（如适用，需注明“代表观点/情绪，非客观数据”）。

工具厂商数据、公司披露与学术研究混在同一组是常见错误，需单独拆开。

### 0.6 草稿占位符与交付状态

- 是否遗留 `TODO`、`TBD`、`<!-- INSERT_CHART -->`、内部交接说明或尚未决定的备选段落？
- 如果图表最终不需要，是否直接删除占位符；如果只需信息组织，是否改成简洁 Markdown 表格？
- 交付给用户的是可阅读初稿还是图表交接稿？只有后者可在明确说明的情况下保留占位符。
- 是否在仍有上述遗留项时错误声称“自查已全部完成”？

---

### 0.7 文件写入与当前版本是否真实

- 修改或导出的文件是否实际写入成功，而不是只在工具调用前完成了计划？
- 是否重新读取标题、修改段落和文件尾部，确认内容属于本轮结果？
- 下载链接是否指向本轮实际生成的当前稿，而不是旧文件或失败前的文件？
- 平台无法原地覆盖时，是否准确说明限制，并避免把内容相同的副本包装成新版本？

## 第一类：事实诚实性

### 1.1 引用强度是否超出来源支持范围

对每一处引用，回头对照原文问：我写的因果关系，原文支持了吗？

- 来源说“A 用于 B”，我有没有写成“A 受 B 委托”或“A 专门为 B 设计”？
- 来源说“X 比例达到 Y”，我有没有直接推断出原文没说的原因？
- 来源是分析文章的推断，我有没有当成确定事实陈述？
- **案例数字是否来自研究数据但被写成了“某企业实测”**：如果案例里的具体数字来自研究引用而非真实企业，需改写为“以 XX 场景为例，研究数据显示……”，不能写成“某 XX 公司……数字从 A 提升至 B”。

### 1.2 推断是否被当成事实说

检查所有因果句——“因为……所以……”“这说明……”“这意味着……”。如果是推断，有没有显式标注不确定性？

### 1.3 自创框架是否标注

检查所有分类、阶段划分、维度框架。自己归纳的，首次出现时有没有说“这是本文归纳”或类似表述？框架的子概念，各自有没有来源支撑？独立推导后发现与已有框架重合，有没有按“先呈现自己的推理链，再说明行业里有类似提法”的顺序处理？

同时检查：这个框架是否只有一个完整展开位置？后续章节如果再次逐项枚举同一框架，即使角度略有不同，也可能造成重复和割裂；应改为引用框架并只深入其中的关键层。

### 1.4 第一手经历是否诚实

有没有把“我听说”写成“我经历过”？业务场景描述有没有夸大自己的介入深度？对某个产品或判断的把握程度，有没有在文中如实表达？

假设案例是否明确写成“简化案例”“示意场景”，避免让读者误以为来自真实企业流程？\n\n同时检查第一手工作信息是否采用最小必要披露：领导层级、客户全名、项目内部信息或组织关系如果不改变论证，是否可以自然匿名为“工作群”“一家头部机构”“一次客户交流”等？匿名是否仍保持事实含义，没有虚构或夸大？

### 1.5 外文引用是否标注

所有来自外文来源的直接引语，有没有注明“译自英文原文”？有没有把外文的推断性表述译成中文后当成确定结论？

### 1.6 任务影响是否被写成岗位替代

来源支持的是任务使用率、自动化比例、职业适用性，还是已经发生的岗位缩减？如果证据只到任务层，正文有没有越级写成“某岗位已被替代/将被淘汰”？应区分任务自动化、岗位结构重组和岗位消失。

### 1.7 近期新闻在论证中扮演什么角色

上市、融资、部署规模、产品发布等新闻，是用作开头触发、现实商业信号，还是技术效果证据？正文有没有把“进入商业系统”过度解读为“通用技术路线已经成熟”？

当正文从“某能力 / 产品已发布”进一步写成“用户正在迁移、形成新习惯、效果已经成立或行业趋势已经发生”时，是否补查了发布后的时间线、真实用户 / 客户实践和独立第三方数据？如果目前只有厂商 PR、路线图或融资叙事，是否仍把它准确写成产品路线、早期信号或待验证实践，而没有把厂商预期改写成市场事实？

### 1.8 知识密集文章是否有合适的现实锚点

当文章以抽象概念、方法论或系统设计为主时，检查是否需要少量真实产品、企业实践或治理事件帮助读者理解。若已加入案例，逐个确认：

- 它是问题触发、现实信号、对照案例还是反例？
- 案例后是否写清“它证明了什么、不能证明什么”？
- 是否只堆品牌或新闻，却没有改变任何论证？
- 厂商自述、产品发布和真实效果数据是否被混为一谈？

现实锚点不是每篇文章的硬性数量要求；没有合适证据时，不为了“显得不硬核”强行加入弱相关新闻。

### 1.9 厂商、社媒与社区证据是否越级

逐个检查这类来源承担的证据角色：

- 厂商 Blog、路线图和产品发布可以证明该厂商的产品能力、重点问题和路线变化，是否被错误升级成“客户普遍采用”“效果已验证”或“行业已形成共识”？
- 多家厂商出现相似动作时，是否有彼此独立的一手信号，并尽量有第三方研究、客户实践或从业者材料交叉验证，而不是只把同类营销文案相加？
- 开发者、研究者、行业从业者的社媒/社区观点是否只承担问题信号、实践者视角、反例等合适角色？是否被错误当成行业普及率、共识或效果证据？
- 社媒人物第一次出现时，是否只交代与当前问题有关的最低必要身份背景，而不是堆履历借权威？
- 是否用点赞数、粉丝数、转发量替代观点本身的证据质量？如有，应删除。

## 第二类：逻辑一致性

### 2.1 标题和正文覆盖范围是否一致

文章标题承诺的话题，和正文实际讨论的边界，是否对得上？摘要框的表述范围，和正文最终落脚点是否一致？候选/最终 `category` 是否与正文核心问题和主要论证对象匹配，而不只是与作者视角、标题关键词或是否出现多家公司匹配？

分类复核不在本 Checklist 维护第二套完整定义，必须读取 GitHub 当前 `blog-taxonomy.json`。快速检查可用四个问题：技术＝能力为什么成立；产品＝产品应该怎么做；商业＝企业如何创造并捕获价值；行业＝整个领域正在怎么变。若当前 taxonomy 的正式定义与这里的摘要冲突，以 taxonomy 为准。

### 2.2 节标题和节内容是否对得上

逐节检查：节标题比内容窄（标题说“专用芯片的问题”，内容也讨论了通用芯片）？节标题比内容宽（标题说“三个原因”，内容只展开了两个）？发现错位时，优先改标题，不要改内容迁就标题。

特别检查“先/后/最终/真正/因此/为什么会”等词：正文是否真的建立了时间顺序、程度比较或因果关系？如果只证明“更容易”，标题写“先发生”就是额外承诺。

同时检查“反而 / 居然 / 其实 / 并非”等认知反转词：正文是否已经建立了一个真实的常见预期，或作者本人此前明确持有的判断？如果没有，标题是否为了制造冲突而虚构了读者预期？如是，改成直接陈述实际结论。

### 2.3 论点覆盖范围有没有在某节悄悄缩回去

如果文章在某节建立了一个大范围论点，检查后续节有没有某节的案例或结论悄悄缩回了小场景而没有说明原因。

### 2.4 节间因果链是否显式桥接

找出所有“前一节结论是下一节前提”的位置：下一节开头有没有一句话说明两者的因果关系？还是只靠节的顺序暗示？

**图表和下一节之间同样需要桥接**：图表后必须有一句话说明图表揭示了什么结论，再衔接下一节。

### 2.5 并列案例有没有说清楚差异

多个案例并列时，每个案例各自说明了什么不同的维度？偏差来源、后果代价、责任归属不同的地方需要明确。有没有“说了三遍同一件事”？

### 2.6 多个案例是否来自同一来源/同一事件

如果多个支撑同一论点的案例来自同一事件/同一时间窗口，正文有没有说明这种关联？有没有把“同源”错误地解释为“独立证据”？

### 2.7 相邻框架是否重叠、层级是否一致

如果相邻章节连续出现两套分类或字段，检查：

- 两套框架是否其实回答同一个问题，可以合并？
- 如果一套用于发现问题、另一套用于落地，正文是否明确写出映射关系？
- 多套框架共存时，是否明确说明它们是一一对应、一对多、局部展开，还是彼此独立但相关？是否区分时间顺序、依赖顺序和并列维度，以及必要条件、充分条件、观察指标和解释机制？
- 两套框架恰好拥有相同数量的条目时，正文是否错误暗示逐项对应？如果后一框架只展开前一框架的某一层、某一道分界或某个节点，是否已在首次出现时明确说明？
- 一级字段是否处于相近抽象层级，还是把工具、状态等实现项与目标、权限等业务边界强行并列？
- 后文是否反复只使用框架中的部分字段，暴露出原框架可以进一步压缩？
- 前一框架若列“资产/能力”，后一框架若列“机制/功能”，两者是否建立清楚映射？后一组只是前一组的落地形态时，是否应合并而不是再次完整枚举？

### 2.8 章节层级与编号是否表达真实结构

- 某个 `##` 章节下是否只有一个孤立的 `###` 子标题？如无必要，应取消子标题或补齐真实并列结构。
- 只有真实步骤、时间顺序或推导顺序才编号；并列分析是否被无意义编号？
- 同一组步骤是否统一使用阿拉伯数字或“第一步 / 第二步”，避免混用？
- 两个内容高度相关的章节是否被拆开，中间插入案例后又回到前面的抽象问题，造成逻辑回跳？


### 2.9 标题限定语是否被正文真正支撑

- 标题或摘要中的“AI”“金融”“B 端”“中国”“AI PM”等限定语，是否实质改变了正文中的判断、约束或方法？
- 如果正文主体通用于更大范围，是否明确写出“通用骨架 + 特定语境增量”，而不是只靠案例或作者岗位暗示特殊性？
- 如果限定语没有承担作用，是否应删除、弱化或调整标题？

### 2.10 决策/流程手册的全局地图与章节问题链

- 概念边界之后、详细分析之前，是否及时提供了全局地图？
- 地图中的主要节点，是否能映射到后续一级章节，而不是独立存在或放到文章过半才出现？
- 每个一级章节是否只回答一个主要问题，并明确承接上一章、为下一章提供前提？
- 地图如果与实际章节顺序不同，正文是否解释了组织顺序与真实执行顺序的差异？

### 2.11 假设是否前置、证据是否后验

- 业务价值、成功标准、风险边界等核心判断，是否在项目或论证开始前以假设、基线或目标出现？
- 后文是否用实际证据验证这些假设，而不是到评测章节才第一次讨论价值？
- 同一概念前后出现时，是否清楚区分“待验证假设”和“验证结果”，避免被误判为重复或前后倒置？

---

### 2.12 AI 产品建议是否体现 AI 特有增量

当文章使用 AI Product Builder、AI PM、垂直 AI Builder 等角色限定时，逐项检查：

- 是否先说明业务痛点和目标，而不是从模型能力或聊天界面出发；
- 是否判断任务是否适合生成式 AI，并与检索、规则、确定性计算、传统自动化或流程改造比较；
- 是否明确模型参与哪一段，哪些环节必须保持确定性或由专业人员负责；
- 是否说明所需上下文、权威数据、工具、权限、评测和失败回退；
- 是否同时追溯上游需求来源和下游业务流转，而不是只问“回答之后呢”；
- 如果删除“AI”二字后仍然只是通用 PM 建议，是否应补足 AI 增量或降低角色限定？

### 2.13 主线是否因新增材料发生无依据漂移

对照大纲确认时的一句话核心问题、主结论边界和“明确不讨论”：

- 初稿是否因为新增了一个有趣案例、厂商、概念或更宏大的问题，就把背景材料升级成新的一级主线？
- 新材料是否可以归入“核心证据 / 反证与边界 / 背景材料 / 后续分支”，却被错误地用来改写当前文章题目或结论？
- 如果主线确实发生变化，正文和大纲是否能明确说明原主线哪里失效、新证据改变了什么，而不是无解释漂移？
- 是否出现“越研究越大”的情况，使文章从一个可承载的问题滑向行业终局、平台战争或泛趋势总结？如是，优先恢复已确认边界或拆成后续选题。

## 第三类：叙述质量

### 3.1 论点和证据的层次是否匹配

用来支撑论点的数据，是在说同一件事吗？数据说明的是现象还是原因？有没有混用？多层因果有没有区分直接原因和结构性原因，而不是用“以及”简单并列？

### 3.2 重复表达和重复论点

同一个关键词有没有在不同节重复解释？同一个论点有没有在两节都完整展开，而不是一节点到、一节展开？

开头是否连续用两种说法提出同一个问题？新闻引子、作者经历、上一篇承接各自是否承担不同功能，还是都在重复“这让我想到一个问题”？

### 3.3 节内框架承诺和内容是否一致

如果某节开头承诺了“两种方式”“三个层次”，后续每个子项有没有和承诺的分类逻辑对得上？发现错位时优先改框架承诺，不要强行调整内容迁就原有分类。

### 3.4 全文分析框架的一致性应用

如果文章引入了一个分析框架（如“两个维度”“三个阶段”），这个框架需要在全文所有相关节中一致应用，不能只在引入框架的节使用，后续节悄悄放弃。检查方法：通读全文，确认每个节的内容都能对应到框架的某个维度。

### 3.5 语气和全文基调是否一致

全文如果是留余地、开放性的，有没有某个节标题或某句话用了绝对化表达？

### 3.6 结尾落脚点是否和标题主线一致

最后一句话收尾的话题，和标题、摘要框承诺的主线，是否是同一件事？结尾是否回收了开头的真实经历、核心问题或关键概念，而不是突然切换到另一篇文章？

### 3.7 标题随正文发展的一致性审查

每轮修改完成后需要专门检查：文章总标题是否仍然准确覆盖当前正文落脚点？摘要框是否和当前版本正文的核心论点一致？逐节检查节标题是否随内容扩展/收缩而更新？

### 3.8 加粗是否落在推理链的“落点”上

每个有明确结论的推理链，是否有且仅有一处加粗标出其落点？有没有同一条推理链里加粗超过 1 处？有没有纯背景铺陈、过渡段落被加粗？

正文中原本为了视觉突出而使用 blockquote 的问题、定义或结论，改成加粗后，是否导致加粗过密？加粗仍需服从“每条推理链最多一个落点”的规则。

### 3.9 冗余导航性注释是否已清理

逐段检查是否存在形如“注：xxx 见 x.x 节”“详见第 x 章”的纯导航性说明。只起指路作用、不传递实质内容的注释应删除；有实质意义的技术关联说明保留。

### 3.10 术语一致性

文章中涉及非 AI 领域的专业术语，需检查两点：一是同一概念在全文前后是否用了同一表达，不能混用同义词；二是术语对目标读者是否足够清晰，必要时用括号补充通俗解释。

特别检查：作者自创的工程表达（如“业务语义层”）是否与行业正式概念（如 Ontology、本体、知识图谱、语义层）清楚区分，避免中途重新混用。\n\n中文正文还需检查：必要英文术语首次出现时是否提供中文解释（英文原词），后文能否优先使用中文；是否连续堆叠 Prompt、Context、Harness、Runtime、Loop、Graph 等英文词，导致普通中文读者需要先理解黑话才能理解论点？

同时检查**分类轴是否漂移**：前文如果已经按某个维度建立对比或分类（例如“单任务模型 / 基础模型”），后文是否突然用另一组词（例如“传统模型 / 专业模型”）继续承接同一对比，却没有说明维度已经变化？如果后者其实是另一属性，应明确写出两个维度的关系，不能把不同分类轴当作同义词替换。

### 3.11 来源表述的过度解读

引用来源时，陈述的因果关系不能超出来源原文的支持范围。常见问题是来源说“A 服务于 B 的目的”，被写成“A 受 B 委托”，无意间强化了原文没有支持的控制关系。

### 3.12 段落节奏是否碎片化

逐段检查一句话单独成段的使用：它是否真的是钩子、关键提问、转折或推理落点？解释、举例、证据、限定条件是否被拆成多个连续短段，形成“每句话都在强调”的 AI 文风？连续两个以上一句话段落时，优先尝试合并。

### 3.13 自定义概念是否及时定义

标题或开头使用“XX 时刻”“屏幕内工作”等自定义比喻时，正文是否在读者形成误解前给出工作定义，并说明它不包括什么？定义是否早于后续论证，而不是等到文章中段才补？

### 3.14 发布格式是否干净

- 是否遗留草稿注释、工具调用标记、`utm_source=chatgpt.com` 等不必要参数？
- 是否同时保留了 Markdown 表格和已经生成的 HTML 表格，造成重复展示？
- 是否在文章中重复嵌入大段全局 CSS，而现有站点已有共享样式？如必须保留，样式类名是否局部、无硬编码颜色？
- 表格注释是否使用普通说明文字或专用样式，而不是正文 blockquote？
- 文件名是否使用简洁英文关键词，不使用中文标题或冗长描述？

### 3.15 次级概念是否突然出现

Prompt、Ontology、组织机制等次级概念第一次出现时，前文是否说明了它要解决什么问题？如果上一段一直讨论 A，下一段突然写“B 不是第四个字段”，读者是否能理解为什么此时要谈 B？必要时补一句自然问题或桥接句。

### 3.16 句子与段落是否完成单一功能

- 一个长句是否同时承担概念定位、实现方式和验证机制，导致首尾重复同一概念？
- 是否可按“定义 / 落实 / 验证”或“现象 / 原因 / 结论”拆成两段？
- 段落拆分后是否各自有明确作用，而不是为了短而短？


### 3.17 主结论是否唯一，框架密度是否过高

- 摘要、开头、主体和结尾是否回到同一个主结论？
- 文中是否存在多句都像“唯一结论”的平行金句，导致读者不知道该记住哪一句？
- 是否连续出现多套“三层、四类、六项”框架，虽然各自合理，但共同削弱主线？
- 相近框架能否合并，次要框架能否降为普通说明或删除？

### 3.18 表格是否说明分类依据、同行关系与覆盖边界

正文含表格或图形时，必须按 `blog-charts-spec` 的“共同内容前提”和“发布前格式检查”逐张完成完整 QA。本项重点确认四个结果：表格回答的问题清楚；行列与同行比较维度成立；来源性质和覆盖边界已说明；表格没有替代本应由正文解释的因果、顺序或例外。图表规范中已有的列数、说明列、表头、占位符和技术实现细则不在此重复维护。

### 3.19 角色责任与岗位命名是否清楚

- 是否为了显得专业罗列过多岗位名称，而这些差异并不改变判断或决策权？
- 是否优先按事实输入、过程组织、专业判断和最终授权等责任组织角色？
- 负责推进的人是否被错误写成拥有全部业务、预算或风险决策权？
- `Owner`、`Sponsor` 等非统一称呼是否给出工作定义，且没有被包装成行业固定岗位？
- 人员可以兼任时，是否仍然保持责任边界清楚？

### 3.20 案例角色与出现强度是否匹配

- 案例究竟是触发、现实锚点、局部示例、贯穿案例还是完整复盘，正文是否清楚？
- 被称为“贯穿案例”的内容，是否在多个关键章节持续产生新的推理，而不是机械重复套用框架？
- 案例只在少数段落有用时，是否应降级为局部示例？
- 删除案例后主线若不受影响，是否应直接删除，避免制造虚假的案例完整感？
- 案例首次出现时是否自然介绍，而不是使用暗示前文已介绍的措辞？
- 案例首次出现是否提供**最低必要背景**：至少让读者知道“它是什么 / 谁做的 / 为什么此处引用”；不展开与当前论点无关的完整履历、产品历史或机构背景。

---

### 3.21 是否残留讨论过程和写作元话语

逐段检查是否把对话中的纠错、取舍和编辑说明直接留在正文，例如：

- 解释某个缩写为什么不能使用，但该纠错与读者理解主线无关；
- “这里值得注意”“这个案例真正揭示”“这一章可以收敛为”等只说明作者正在写什么的过渡；
- 为来源选择、章节调整或删改决定辩护，而不是继续论证主题；
- 同一节先总结“接下来回答什么”，后文又把相同内容完整说一遍。

这些内容只有在确实帮助读者理解边界时才保留；否则删除，或改写成直接推进事实、机制和判断的句子。

同时检查是否残留没有承担必要事实边界的模板化审稿腔 / 证据免责声明，例如“现有证据不足以支持”“这并不意味着”“更准确地说”“需要避免过度推断”。如果它们只是在判断前套模板，应改为更直接的“事实 → 判断 → 必要边界”；必要的证据限定、对正文已建立误解的反驳仍应保留。

- **反驳对象必须先在正文成立。** 出现“不能简单说 X”“这并不意味着 X”“不能证明 X”“不是 X，而是 Y”等反驳或纠偏句时，检查 X 是否已由正文、外部常见观点或读者自然预期建立。若 X 只来自此前聊天、用户临时假设或编辑过程，不把纠偏痕迹带进正文；直接改写为“事实 → 当前判断 → 必要边界”。

检查“越来越、仍然、重新、后来、回头看、开始意识到”等认知轨迹是否有作者经历、正文前文或历史观点支持；没有依据时改成当前直接判断，不把编辑或研究过程写成作者经历。

### 3.22 活人感审校是否执行且没有越界

正式博客默认必须在本 Checklist 前经过活人感审校；执行时读取 GitHub 当前 `.agents/skills/blog-human-writing/SKILL.md` 与 `references/prose-review.md`，只有用户明确要求跳过时才省略。已安装 Skill 只是可选运行入口，不能替代 GitHub 当前规则。先确认流程是否实际执行：仓库里存在文件但本轮未读取，不等于已审校。再按其“修改后的保护性复核”检查：改写没有虚构作者经历或业务细节，没有提高判断强度，也没有删除必要事实、限定、反例、术语或行内链接；第一手工作锚点如需匿名，是否只做最小必要匿名而没有抹掉真实问题来源。通过后仍须继续完成本 Checklist 的全部适用类别。每篇正式博客结束后的统一规范沉淀复盘会再次判断 GitHub Skill 本身是否需要更新；不再维护“安装版与镜像双向同步”这一双真源机制。

### 3.23 多轮修改后的回归检查

仅当初稿形成后经历过多轮实质修改、章节重组或整体重写时触发。不要只检查“本轮改了什么”，重新扫描全文，重点确认：

- 已经删除或合并的重复案例、重复结论、近义框架是否重新出现；
- 已经修复的一句话段落和连续短段是否因重写再次碎片化；
- 总标题、节标题和摘要是否仍对应当前内容重心，没有沿用旧版本承诺；
- 曾经压缩或解释过的术语是否重新变复杂，或中英混用重新增加；
- 历史文章在终稿中的角色是否发生变化，正文内链、显式关系判断与最终发布交接是否仍一致；
- 参考资料分组、行内链接、加粗密度、表格边界等此前已通过的问题是否被新段落破坏；
- 如果本轮只是局部 patch，未受影响的章节是否被无必要改写；如果确实整体重写，是否能说明核心论点、边界或大纲发生了什么实质变化。

本项的目标是防止“修一个新问题，又把旧问题生成回来”，不是要求每轮保存完整 diff 报告。

### 3.24 结论是否由正文实际承载

逐个检查承担总结、归纳或升级判断作用的句子，尤其是带有“因此 / 这说明 / 真正的区别 / 核心变化 / 最重要 / 主要 / 有的……有的…… / 可以分为……”等表达的句子：

- 这句话中的**比较维度、分类、因果、机制或程度判断**，是否已经由前文事实、案例、解释或图表逐步建立；
- 是否在总结句里第一次出现一个正文此前没有解释过的新区别、新分类、新机制或新阶段；
- 使用“更重要 / 最重要 / 更深 / 主要 / 核心”等比较或程度词时，前文是否给出了清楚的比较基准和足够证据；
- 前文案例是否真的分别支持总结中的各个分支，而不是只支持其中一侧，却在结论里扩成“两类 / 多种路径 / 不同阶段”；
- 图表中的节点或分叉如果被正文总结成一般规律，正文是否已经说明它只是认知地图、特定案例还是可泛化机制。

**总结句只能收束已经建立的内容，不能承担第一次发明框架的职责。** 如果前文只能支持较弱结论，直接缩小结论；如果新的区别或机制确实值得保留，应先在前文补足定义、案例或证据，再保留总结。不要用一句漂亮的归纳替代正文承载。

## 第四类：科普/手册类文章专项检查

仅当文章定位为科普手册（非论点驱动）时触发。

### 4.1 手册变体与节内结构是否匹配

先判断文章属于技术链路手册、决策/流程手册还是概念总览，不强制所有科普文章使用同一模板。

- **技术链路手册**：核心技术节点是否稳定覆盖概念介绍、评估维度、场景取舍和协作要点；同类节点格式是否一致？
- **决策/流程手册**：主要阶段是否回答当前判断、判断依据、关键责任和下一步条件；是否沿全局地图逐站展开？
- **概念总览**：是否围绕一个主结论组织概念关系，而不是堆成百科条目？

### 4.2 全文同类元素的格式一致性

文章中凡是同一类型的内容，其呈现格式应在全文保持统一。不只是协作要点，场景取舍、评估维度、对比说明等任何多次出现的内容类型都适用：

- **同类内容格式统一**：如果某类内容在某节用了表格，其他节也应当用表格；如果用文字列表，则全文统一。不应一处用表格、另一处用散文段落。
- **汇总表格与正文表格的列结构一致**：如果文章末尾有全文汇总表格，其列结构（有哪些列、列的顺序）必须与正文各节对应表格完全一致。
- **内容归属正确性**：表格中的内容是否放在了正确的维度/层级下，有没有把属于 A 层的内容写进了 B 层的表格。

### 4.3 评估维度是否系统覆盖

逐个技术节点检查评估维度列表：

- 有没有重要的评估维度被遗漏
- 某个概念是否在某节完整介绍，但在其他相关节只字未提
- 是否存在“只讲了选型选谁，没有讲怎么评估”的节点

### 4.4 场景分类框架是否有效

- 场景标签框架是否做到全集覆盖——所有真实场景（包括无特殊约束的普通场景）能否都找到对应标签？
- 是否有使用示例帮助读者对号入座？示例是否包含“所有维度均无特殊约束”的普通场景？
- 各节中引用场景标签的位置，是否引用了框架中定义的标签，而不是临时另起标签？
- 场景标签的使用在全文是否术语统一？
- 分类框架的设计维度是否一致——不能把运行态约束和生命周期阶段标签混为并列类型，后者需单独说明“这个标签会随时间退出”。
- **并列路径/方案的全集说明**：当文章引入多条并列技术路径或方案时，是否明确说明了两者合起来构成的完整全集——各自覆盖哪些数据形态/场景，由谁来决定走哪条路径。

### 4.5 流程图与正文的一致性

如果文章包含流程图或架构图，按 `blog-charts-spec` 做完整流程图 QA；本项只确认图中节点、分支、回退、暂停或终止路径与正文一致，图与章节顺序的差异已有说明，且图后正文明确提炼了图表结论。

### 4.6 章节归属与执行顺序

- 每个技术节点是否放在了功能归属正确的章节下？
- 章节顺序是否与实际执行顺序一致？如不一致，开头是否用图或文字显式说明？
- 同一概念在多个节点都会涉及时，是否在主节点完整介绍，在其他节点简短说明其局限性？

### 4.7 内容完整性检查

逐层检查是否有重要内容被遗漏：

- 有没有文章覆盖的技术链路中，某个常见决策点完全未提及？
- 跨层机制是否在正确的位置说明？
- 系统演进类内容是否覆盖？
- 如果有“冷启动场景的建议”分散在各节，是否有集中的最小可行系统建议？
- **可选组件是否标注了其可选性**：文章中介绍的技术组件，凡是非必须引入的，应明确说明“这是可选的，不是标配”，并给出引入条件。


### 4.8 决策/流程手册专项检查

仅当文章属于决策/流程手册时触发：

- 全局地图是否在概念边界后及时出现，并且没有塞入全部角色、指标和检查项？
- 业务价值等核心标准是否先以假设和基线出现，后以证据接受验证？
- 各章是否依次完成“决定什么 → 用什么标准 → 怎样验证 → 怎样判断 → 怎样交接”，或解释了为何采用其他顺序？
- 流程中的回退、暂停和终止是否真实存在，而不是默认所有路径必然向前？
- 最终交接是否区分已证明、成立条件、剩余未知和下一阶段范围？

## 第五类：历史文章关系与观点增量

所有新文章执行基础检查；只有文章属于正式系列时，再执行本节末尾的系列专项检查。

本类不要求在终审阶段重新无差别深读全部历史文章。优先复核探讨和大纲阶段已经识别的历史关系；如果初稿相较大纲新增了核心判断、概念、案例或章节，再针对新增内容补做历史检索。

### 5.1 应承接的重要旧文是否遗漏

检查探讨和大纲阶段已经发现的高相关历史文章：

- 正文真正使用了旧文已经建立的判断、定义、框架或案例时，是否在对应位置自然加入行内链接；
- 是否因为改稿、章节移动或删减而丢掉了原本必要的历史承接；
- 是否存在不说明历史关系就会让读者误以为这是首次提出的核心判断。

只有内容存在实质关系时才补链，不为了增加站内链接数量机械引用。

### 5.2 当前引用是否真的存在实质关联

逐个检查历史博客内链：

- 两篇文章是否回答相同或直接承接的问题；
- 是否共享真正参与论证的因果机制；
- 是否存在观点延伸、修正、框架复用、案例复用或读者需要理解的观点连续性；
- 链接后的旧文是否真的包含正文所声称的内容。

如果只是关键词、公司、模型、行业或宽泛主题相同，应删除正文内链。

### 5.3 是否重复完整展开旧文章已经论证过的内容

如果某个概念、框架或判断过去已经完整展开，检查当前文章是否又重新用大篇幅完成同一套论证。默认处理方式应是：

1. 复述理解当前文章所需的最小前提；
2. 在前提处链接旧文；
3. 尽快进入当前文章真正新增的问题、证据或判断。

只有旧判断需要被实质修正、新证据改变了原有机制或边界、当前文章面向不同问题而必须重构旧框架，或不完整重述会明显破坏本文独立可读性时，才允许重新完整展开。仅为了“让文章更完整”重复旧内容，应压缩。

### 5.4 本文相对历史文章是否存在清楚的内容增量

检查正文能否回答：**“如果读者已经读过最相关的旧文章，这篇新文章还新增了什么？”**

增量可以是新问题、新机制、新证据、新案例、新边界、新反例、原判断在新条件下的修正，或将旧框架推进到新的决策和业务场景。

如果无法指出实质增量，应重新检查选题范围、章节结构或是否值得单独成文，而不是仅靠新案例和新表述制造一篇近义文章。

### 5.5 新旧观点冲突或修正是否被准确处理

如果当前文章与历史文章存在明显不同判断，检查：

- 是作者观点发生变化，还是讨论条件发生变化；
- 是新证据推翻旧判断，还是两篇文章讨论的对象和范围不同；
- 正文是否需要主动说明这种变化；
- 是否错误地把过去的判断描述成和现在一直一致。

如果变化本身有认知价值，可以把“为什么改变判断”作为文章内容；如果只是边界不同，说明边界即可，不人为制造观点反转。

### 5.6 历史正文是否使用了正确的发布事实源

历史文章的内容判断优先以作者最终正式发布的内容为准：

1. 当前线上正式发布页面；
2. GitHub 当前发布 HTML；
3. Markdown 源稿。

如果 Markdown 与已发布 HTML 存在差异，不应未经核对就引用 Markdown 中读者从未看到或已经被删除的观点。本项只规定历史引用的事实核对；当前新文章自身的写作和维护仍以当前有效源稿为准。

### 5.7 是否出现 metadata 召回缺陷

如果终稿依赖一篇高度相关的历史文章，而该文章在探讨阶段通过合理的 `title / summary / concepts / topics / tags / category` 检索长期难以召回，检查：

- 是 metadata 确实遗漏了该旧文的核心概念或判断；
- 还是这种关系只是当前文章语境下偶然产生。

只有前者才进入 metadata 修正建议。不要因为一次偶然关联给旧文大量追加 `concepts`，也不要为了提高召回率、SEO 或填满“继续阅读”而建立显式文章关系；如果正文已经确认存在前提承接、观点推进、修正或直接互补，则按发布规范继续检查其显式关系是否成立。

### 5.8 显式文章关系是否与正文事实一致

当发布 metadata 中存在面向读者的显式文章关系时，逐项检查：

- **承接 / 继续推进**：当前文章是否真的建立在旧文已经形成的判断、框架或必要前提上，或明确把旧问题推进到新的问题；不能只因同主题、同公司或共享概念就建立强关系。
- **观点修正 / 重新限定**：当前文章是否确实改变、挑战或重新限定了旧文判断；普通补充、新案例或条件变化但结论未变，不包装成“观点修正”。
- **直接互补**：两篇文章是否回答直接互补的问题、共同阅读价值明显高于普通同主题；如果只是宽泛相关，交给自动同主题即可。
- 正文出现历史文章链接是否被错误地自动升级为显式关系；案例引用、背景材料、参考资料和普通内链不自动形成强关系。
- 是否为了 SEO、系列完整感、填满推荐位或构建“知识图谱”而增加并不成立的关系；没有强关系时允许不写。
- 同一强关系是否按发布规范只维护一次；历史文章无需为了反向展示而重复维护同一关系，也不因未来文章出现而回改历史正文。
- 如当前交付包含“继续阅读”结果，本 Checklist 只复核**显式关系的语义真实性与最终展示是否忠于已确认关系**：已经确认的强关系不应仅因其同时出现在正文或参考资料中就被降级或排除；自动“同主题”主要承担内容发现作用。具体展示数量、排序、正文/参考资料去重、同主题补位与动态反向计算全部由网站发布规范负责，本 Checklist 不维护第二套展示算法。

### 5.9 最终稿是否被历史文章无依据地反向塑形

如果探讨阶段保留了“历史检索前独立起点快照”，尤其是大纲前曾触发“历史独立性与增量评审”，用最终稿做一次轻量回看：

- 当前核心问题、标题方向和主线相较独立起点发生的主要变化，是否能由新证据、重复风险、旧观点冲突、边界收窄或其他内容理由解释；
- 是否出现为了与历史文章建立连续性而新增章节、扩大论点、重新引入旧框架或调整题目，但这些变化删除历史链接后并没有独立必要性；
- 若最相关旧文全部暂时隐藏，最终稿的核心问题和主体论证是否仍然独立成立；如果文章明确定位为续篇，则是否清楚说明真正推进了旧文哪一层，而不是只依赖“这是上一篇之后的文章”；
- 成文前已经判定“仅同主题 / 不相关”的旧文，是否在写稿过程中又无新证据地被升级成正文承接或显式强关系。

本项只复核最终结果是否偏离成文前已经确认的独立性结论，不重新执行完整的六问评审，也不要求所有正常的观点演进都回到原始快照。

### 5.10 正式系列文章：与上一篇的关系是否清楚

仅当本文属于正式系列时触发。开头或首次承接处是否明确说明这篇与上一篇是什么关系：递进、并列、补充还是修正？读者不看上一篇是否仍能理解本文所需的最小前提？

### 5.11 正式系列文章：核心概念是否发生无解释冲突

系列内同一个核心概念的定义是否前后一致？如果概念发生变化，是术语优化、范围调整还是作者认知变化？需要说明时是否已经说明？

### 5.12 正式系列文章：是否重复上一篇主论点

当前文章的核心论点是否其实已经由上一篇完整解决？如果存在交叉，两篇的分工和本文新增量是否清楚？

### 5.13 正式系列文章：上一篇链接是否自然且不形成阅读门槛

如果正文依赖上一篇，是否在真正需要的位置使用行内链接，而不是只在参考资料中列出？同时，本文是否复述理解当前论点所需的最小前提，避免把“先读上一篇”作为强制阅读顺序？

## 第六类：终稿 Metadata 与 Taxonomy

**触发条件**：本轮目标是导出 / 生成正式发布 Markdown，或当前 Markdown 已经包含 metadata frontmatter。普通初稿审校尚未进入发布交付时，不要求提前生成完整 frontmatter，但第二类的 category 一致性检查仍照常执行。

本类检查使用 GitHub 当前 `tools/blog/data/blog-taxonomy.json` 作为 category/tags/topics/concepts 规则的唯一真源；不依赖模型记忆、早期大纲、Project Source 或其他旧副本。

### 6.1 终稿前是否重新读取最新 taxonomy

文章可能跨多天完成，且正文主线或 taxonomy 均可能变化。检查最终 metadata 冻结前是否重新读取 GitHub 当前 `blog-taxonomy.json`。启动阶段读过一次不能替代终稿前复核。

### 6.2 category 是否对应最终核心问题

检查：

- 是否属于当前 active category；
- 是否按最终正文的核心问题和主要论证对象判断；
- 是否只是因为作者身份、案例公司数量、标题关键词或局部章节而误分类；
- 大纲阶段的候选分类在正文演化后是否仍成立。

快速区分只用于辅助：技术＝能力为什么成立；产品＝产品应该怎么做；商业＝企业如何创造并捕获价值；行业＝整个领域正在怎么变。详细定义始终以 taxonomy 为准。

### 6.3 tags 是否正确回答“这篇文章在做什么”

逐个检查：

- 是否存在于当前 active tags；
- 是否描述全文主要分析动作，而不是局部方法；
- 是否存在近义重复；
- 数量是否符合 taxonomy 当前规则。

发现现有 tags 无法准确表达时，不在 Checklist 临时造词，回到 taxonomy change 流程。

### 6.4 topics 是否正确回答“这篇文章主要讨论什么”

逐个检查：

- 是否存在于当前 active topics；
- 去掉该 topic 后，文章的核心问题是否会失去重要边界；
- 是否只是案例、实现路径、引用来源或偶然提及；
- 第二个 topic 是否同样属于核心问题，而不是为了扩大关键词覆盖。

### 6.5 concepts 是否适合未来语义召回

按 taxonomy 当前规则检查：

- 数量是否合规；
- 是否包含泛词；
- 是否与 tags/topics 精确重复；
- 是否只是正文偶然提到的品牌或术语；
- 是否覆盖文章真正重要的对象、机制、框架和判断边界；
- 历史已有稳定命名时，是否无理由创造新同义表达。

concepts 不追求把文章所有关键词列完，只保存未来值得召回的语义锚点。

### 6.6 share_quote 是否真实来自最终正文

逐字确认：

- 在最终正文中真实存在；
- 是完整原句；
- 后续 patch 没有把它删除或改写；
- 单独阅读仍成立；
- 没有从标题、summary 或多个句子重新拼接；
- 没有为了分享效果另造更夸张版本。

正文没有合适原句时，应回到正文调整或请用户确认，不能只在 metadata 中创造一句话。

### 6.7 relations 是否仍由终稿内容支持

逐项检查：

- 目标文章已经正式发布；
- slug 正确；
- type 属于当前发布契约允许值；
- `builds_on / revises / companion` 的语义由新旧文章正文真实支持；
- 不是因为同关键词、同分类、同公司、同模型或为了填满“继续阅读”而建立。

没有强关系时 `relations: []` 完全合法。

### 6.8 frontmatter 是否自包含且没有重复真源

新文章最终 Markdown 应在文件最顶部持久保存：

- `category`
- `tags`
- `topics`
- `concepts`
- `share_quote`
- `relations`

同时确认没有在 frontmatter 重复：

- `title`（由 H1 决定）
- `summary`（由 H1 后唯一 blockquote 决定）
- `slug`（由 Markdown 文件名决定）
- `date`（由发布流程决定）
- `url`（由 slug 派生）

正式交付文件应脱离当前聊天后仍足以完成确定性发布，不允许依赖 Codex 根据上下文补齐内容语义字段。

### 6.9 Metadata 是否随最后一次实质修改同步

如果最后一轮 patch 改变了核心判断、标题语义、结论、主要研究对象、章节重心或历史关系，必须重新执行 6.2–6.8。纯错别字、标点和排版修复不要求重新分类。

### 6.10 发布端是否被错误赋予内容判断

检查最终交付说明中是否还要求 Codex：

- 自行选择 category；
- 自行创造或替换 tag/topic；
- 自行增加 concepts；
- 另造 share_quote；
- 从正文相似度重新推断 relations。

上述操作均应在网页版写作阶段完成。Codex 只负责读取最新 taxonomy、校验、同步、生成和测试；冲突时应 fail 并返回写作阶段，而不是静默修正。

## 每篇正式博客完成后的规范沉淀复盘

终稿 metadata 冻结后、发布交接完成前，默认自动执行一次，不额外询问用户是否需要。检查本轮是否产生了值得长期沉淀的跨文章规则，并按唯一职责归属评估：

1. `blog-sop`：新的写作决策或流程节点；
2. `blog-review-checklist`：新的稳定终审缺陷；
3. `blog-charts-spec`：新的图表设计 / QA 规则；
4. GitHub `blog-taxonomy.json`：category/tags/topics/concepts 规则；
5. GitHub `.agents/skills/blog-human-writing/`：材料承载力 / 活人感审校规则；
6. GitHub `WRITING_GUIDE.md` 与发布脚本：Markdown metadata 或发布契约；
7. Series Brief：仅限系列主线、文章地图、跨篇稳定边界或运行方式实质变化。

只有同时满足“跨文章可复用、已被本轮实际问题验证、有明确唯一归属”才更新。文章专属修辞、案例、一次性异常或未经验证的猜想不进入长期规范。没有变化时明确记录“本轮无长期规范更新”，不要为了完成复盘制造新规则。

如果当前环境能直接修改对应真源，按单一当前版本原则原位更新；不能写入 GitHub 时，生成精确的 Codex 变更交接。**不把文件修改劳动转回给用户，也不再逐项询问用户要不要更新。**

## 使用方式

以当前初稿执行本 Checklist：

1. 完整扫描所有适用类别；
2. 直接修改所有能够确定的问题；
3. 修改后重新跑一遍 Checklist；
4. 输出更新后的完整正文或直接覆盖当前文件；
5. 最后列出已经修改的主要问题；
6. 仅把不确定事项集中交给用户确认；
7. 正式发布 Markdown 再执行第六类 metadata/taxonomy 审查；
8. 终稿冻结后自动完成一次规范沉淀复盘，只在确有长期规则变化时更新对应真源。

不要只输出“第 X 段有问题”的长清单后等待用户逐项批准。问题说明应服务于修改记录，而不是替代修改。

**每轮修改完成后**：重新过一遍文章总标题、唯一摘要框、每个节标题、正文中的 blockquote、行内链接、参考资料和结尾落点。

需要生成或覆盖发布文件时，文件名使用简洁的英文关键词（如 `human-ai-boundary-shift.md`），不使用中文标题或冗长描述；写入与单一当前版本规则以项目指令为准。
