## 图文协同与适用场景

**主动寻找正文配图机会，不以“文字说不清”或“图能替代文字”为准入门槛。** 相关图像可以让读者更愿意进入问题、看见具体对象、理解关系、比较差异、回顾主线或在长文中获得有意义的阅读停顿。图与文字可以共同表达同一内容；有图不要求删掉对应文字，图也不必每次引入新结论。

按当前段落的阅读任务选择表达，可使用导入/场景插图、机制/分步图、比较/导航图、截图/证据图或回顾图。这些是可组合的用途，不是每篇必须集齐的模板；概念插图也可以只承担贴合主题的搭配表达，不冒充证据。

- 一个概念、两个状态或两三个数据点，也可以通过示意、前后对照或坡度图表达；对象少不是拒绝画图的理由。只含少量观测值时如实展示，不用平滑曲线暗示不存在的趋势。
- 多对象比较、层级、因果、流程、分叉、空间或数据变化，优先检查是否有更直观的视觉表达；简单列表仍可用文字，但不自动排除有组织价值的图形。
- 不用二维坐标伪装离散分类，不因版式对称改变层级、顺序或因果。生成式示意图不构成独立事实证据，不伪造数据、产品界面或真实事件。

## 大纲阶段的视觉机会检查

沿正文问题链主动寻找配图位置，再决定采用或不采用。每个候选只需在现有大纲或制作说明中写清：对应段落与阅读任务、采用何种表达、与文字怎样配合、素材/证据边界。无需另建报告或增加逐图确认轮次。

判断收益包括兴趣、具体感、理解、比较、回顾与阅读节奏；删除图后文字仍完整，不是删除图片的充分理由。反向也检查：是否让纯文字独自承担过重的关系解释或比较任务。只有确实无阅读收益、偏题、误导或制作代价不相称时才舍弃，不以“尽量少图”为默认目标。

复杂机制可以采用“总览 → 局部 → 状态变化”的递进图组，同一对象和视觉编码保持一致。每步承担新的观察或解释任务，不机械重复完整总图。正文图片数量、样式和制作方式以 [视觉发布规范](../VISUAL_GUIDE.md) 为准。

**候选不等于占位符。** 只有已决定制作但尚未完成的图才允许内部占位；可阅读交付物仍须完成图表或明确取消，不留下未决占位符。

## 图表类型与使用规范

### 表格与图形的共同内容前提

任何表格或自创图形在制作前，先写清四件事：

1. 它回答什么自然问题；
2. 行、列、节点或坐标轴按什么依据划分；
3. 它是行业标准、来源框架还是本文归纳；
4. 是否覆盖全集；如不覆盖，边界和例外是什么。

如果这些问题无法回答，说明当前还只是并列清单，不应因为“看起来更专业”就转成图表。两张列结构相同的抽象表与案例表，优先合并为一张，让框架和案例直接对应。

对于横向对比表，还需多问一句：**同一行为什么能够横向比较？** 如果答案只能在作者脑中成立、读者无法从表内直接看出，就应把共同维度显式写成首列，而不是依赖读者自行配对。

### 对比表格

适用场景：多个对象在固定维度上的横向比较。

**内容规范：**
- 列数不超过 5 列，超过则拆分或精简维度
- 单元格优先短语表达；15 字只作精简参考，不能为达标删掉必要条件或把有意义的对比改得含糊。较长解释移入相邻正文。
- **同行对应原则**：横向对比表中，同一行的多个单元格必须回答同一个比较维度的问题，不能只是把两个相关列表机械并排
- **比较维度显式化**：如果同行之间“为什么可以比较”不能从内容本身立即看出，应增加首列“比较维度 / 维度 / 环节”，让读者无需自行推断对应关系
- **说明列克制使用**：增加比较维度后，如果同行关系已经清楚，不再为了完整额外增加“说明”列；只有说明本身提供新的条件、边界或例外时才增加，否则放到表格前后正文
- **对照不等于二分法**：如“更易商品化 / 更可能升值”这类表格，两侧可以表示同一维度上的相对方向，而非互斥全集；同行两侧仍需保持相近抽象层级
- 程度差异可用 badge 辅助，但必须保留“高/中/低”等可读文字或其他非颜色标记，不能只靠颜色编码。
- 表格底部加注释说明分类逻辑，尤其是有从属关系、方向性对照或并非全集覆盖的情况
- **表头视觉一致性**：同一篇文章中的 Markdown 表格应采用一致的表头强调方式；如果站点样式不能明显区分表头，可显式使用 `**表头**`

**技术规范：**
- 可使用 HTML 内联实现，不用图片文件
- 页面内的 HTML/SVG 颜色优先使用共享 CSS 变量（`var(--color-*)`），不逐图复制独立十六进制配色；需要导出为图片的独立图源，使用视觉发布规范确定的共享样式参数
- badge 的深色模式需单独用 `@media (prefers-color-scheme: dark)` 声明
- 表格容器用 `border-radius` 和 `overflow: hidden`，视觉上和博客风格一致
- 如果站点已有共享表格样式，优先复用共享样式，不在每篇文章重复嵌入相同 CSS

### 层级/闭环关系表

适用场景：多个概念不是同一层级的竞品或类型，而是分别处于数据、映射、预测、执行、验证等不同环节。

**内容规范：**
- 首先明确这是行业通用分层还是本文归纳；自创框架需在表格前标注
- 推荐列为：层级/环节、代表概念、补齐的能力、缺失后果，列数不超过 4 列
- 行顺序按真实流程或依赖关系排列，不按热度、知名度或视觉均衡排列
- 不使用“高/中/低”badge，除非这些概念确实存在同一维度上的程度比较
- 同一套层级表全文只完整出现一次，后文引用具体层即可，避免再次换角度重复列全表

**技术规范：**
- 草稿阶段可先用 Markdown 表格确认逻辑；发布版可转为 HTML 表格或复用站点表格组件
- 表格底部必须说明分类是“行业标准”还是“本文归纳”，并指出相邻层之间不是严格互斥关系时的例外
- 单元格仍应尽量控制在 15 字以内；解释性内容放在表格后的正文中
- 表格注释不得使用 Markdown blockquote。使用普通注释段落、斜体说明或 `<p class="chart-note">`，避免和标题下唯一摘要框混淆

---

### 横向还是纵向：先看关系，再看使用场景

横竖构图不是固定风格，也不能用“手机更方便”代替语义判断。横向适合短的时间/推理链、并列维度、方案对照与多路汇合；纵向适合多层条件分叉、回退、逐站解释，以及确需长文字的节点。**同一图可以上下一次交代前提、横向放置并列因素、再向下汇合到后续判断**，但并列比较不能画成有编号的连续步骤，分叉结果不能为了视觉对称暗示互斥或固定顺序。

优先按实际文章宽度评估横向紧凑图，避免把只有几项并列关系的示意不断叠成长比例卡片。移动端若图形需要保留宽度，提供真实可操作的横向滚动或同源重排；不直接缩小成难以辨认的缩略图。图意确认后再确定画布尺寸，具体规格和视觉验收仍由 `VISUAL_GUIDE.md` 负责。

### 流程图 / 决策树

适用场景：存在真实的执行顺序、阶段门、条件分叉、回退、暂停或终止路径，且普通段落难以同时表达这些关系。

**内容规范：**
- 主图优先回答“当前在哪一阶段、需要作出什么判断、可能走向哪里”，不把完整角色矩阵、全部指标和详细检查项塞进同一张图
- 单个节点通常采用“动作或判断问题 + 1—3 个关键词”；解释性长句放在正文
- 只有真实条件才画分支；并列说明不画成伪分叉
- 判断节点必须对应真实分叉：如果节点使用疑问句或判断语气，但后续只有一条路径，应改成陈述性动作 / 状态节点；不要用‘问题形状’制造不存在的选择
- 节点中的 `/` 不承担关系推断：如果两个词是前后步骤、包含关系、同时成立或不同抽象层级，应改用“与 / 进入 / 再”明确关系，必要时拆成两个节点；只有读者不会误解为二选一或同义词时才保留斜杠简写
- `Adjust`、重试或回退必须标明返回哪个具体环节，不能用一条含糊的箭头统一指向“前面”
- 终止、暂停、补条件和正式进入下一阶段应在视觉上区分
- 节点名称与正文术语保持一致，但不在图内嵌入章节编号
- 全局导航图通常保持 5—8 个主节点；超过后优先合并阶段或拆成主图与局部图
- 角色关系只有在改变流程走向时才进入主图；否则用责任表或泳道图单独表达

**位置与正文关系：**
- 决策/流程手册中，全局图通常位于概念边界之后、详细分析之前
- 图前说明它展示的是导航地图还是实际执行流程
- 图后明确最重要的分叉或回退结论，并说明后文章节如何沿图展开
- 若文章组织顺序与真实执行顺序不同，必须显式说明

**技术规范：**
- 简单线性流程可使用 Mermaid 或站点现有流程组件；复杂分叉、回退和视觉分组优先使用 SVG
- SVG 节点尺寸与文字行数保持一致，避免为了容纳长文而不断扩大节点
- 主路径使用实线，回退或可选路径可使用虚线，但同一含义全图保持一致
- 深色模式下箭头、边框、节点填充和文字均需可读
- 移动端应允许横向滚动或改用纵向布局，不缩小到无法阅读
- **多级分支图的连线空间单独验收。** 箭头尖端须与目标节点边框和内部文字分离；条件标签不能贴在线条、箭头或节点上；分支汇合处要留下可辨别的纵横距离。若固定画幅使箭头、标签和节点拥挤，先扩展图高或重新排布，不能为了保持统一长宽比牺牲可读性。实际显示宽度下检查，而不只看 SVG 坐标。


#### 已有图表重绘 / 发布表示迁移：语义保真门（必选）

当流程图、决策树、分层机制图从 Mermaid、Markdown、HTML 或旧 SVG 换成新视觉表示，**先锁定当前已确认的逻辑，再做视觉压缩**。目的不是保留每个旧矩形的外观，而是不能把原有信息关系改掉。适用于图表重绘、横竖版切换、节点合并、换设计系统和发布格式迁移，不为只调整颜色、字号且关系未变的操作增加繁琐记录。

1. **确认权威基线。** 同时查看当前已确认的流程定义、对应正文和线上/仓库已发布图，明确哪些是“作者已确认的业务/概念关系”，哪些只是展示形式。存在冲突时先识别差异；不能只依据旧截图或只看最近生成的 SVG 推断逻辑。可直接从旧 Mermaid/流程文字提取节点与连线作为本次对照。
2. **提取不能丢的关系。** 用最小关系表核对：关键节点与角色、先后依赖、每个判断问题及其互斥或可并行情形、边的条件/方向、分支后果、回退/终止、输出和适用边界。不能仅比较节点文字是否仍出现。
3. **先后顺序与分类轴不可混合。** “是否需要某种输出”属于任务需求判断，“由模型内部还是系统外部实现”属于能力实现路径；不能为了凑同一行/缩短高度，把前者和后者改成三个同级选项。对于多选、可并行或非穷尽路径，不因对称布局擅自画成互斥选择。
4. **视觉变更必须语义等价。** 可以调整布局、合并纯装饰容器、换行和颜色；删掉真实条件、调换前后层级、改变箭头方向、增加不存在的因果/排他关系，属于内容变更，不得以“精简排版”名义静默执行。若确实要改图意，应同步修改正文并完成相应内容确认，再将它视作新版本。
5. **验收分四关。** ① 与基线逐关系核对（关键节点、条件、路径、后果）；② 与图前图后的正文及图注一致；③ 在桌面/移动、浅色/深色下看真实渲染、文字和箭头指向；④ 再跑图片契约、HTML、构建与发布测试。后一关通过**不能**替代前面三关。
6. **高风险变更留下最小证据。** 本轮改动涉及条件分支、节点层级或箭头重构时，在当轮变更说明中记录“保留的决策与路径 / 合并的纯展示节点 / 已确认的语义变更”。有已知旧图的，可针对关键分支补自动断言；自动断言只能防止已知关系被误删，仍不能代替图形视觉复核。不要求每幅图新增独立规范文件。

**失效案例（《多模态到底统一了什么？》，2026-10）：** 原稿是“共同理解 → 判断是否需要非文本媒体 → 否：文字回答；是：媒体生成路径 → 模型内生成 / 系统调用 → 媒体输出”。一次 SVG 重绘把最后两层压成“文字回答 / 模型内生成 / 系统调用”三个并列框，虽然渲染、资源与 GitHub Pages 构建均能通过，却改变了**任务输出与实现路径的层级**。因此，版面压缩的验收对象必须是**原有关系是否还成立**，而不只是节点是否都在图中。

### 二维定位图

适用场景：需要用两个维度同时定位多个对象，且两个维度都是连续的，不是离散分类。

**内容规范：**
- 两个维度必须都有明确语义，在坐标轴两端标注极值描述（如“宽（通用）”和“窄（专用）”）
- 节点数量不超过 8 个，超过则考虑拆成两张图
- 有从属关系的节点用虚线框圈出，并标注大类名称
- 节点位置要反映真实的相对关系，不能为了美观随意摆放

**技术规范：**
- 用 SVG 实现，viewBox 固定为 `0 0 680 H`（H 根据内容高度确定）
- 节点颜色从同篇共享视觉方案中选取，分类含义由当前图的对象与论证确定并注明；不把某篇芯片文章的颜色—类别对应关系套用为所有文章的通用语义
- 同一颜色在同图及同篇有语义关联的图中含义一致；关键分类同时保留文字或形状，不只依赖颜色区分
- 坐标轴用 0.5px 细线，末端加箭头 marker
- 分隔虚线用 `stroke-dasharray="4 4"`

## 图表实现交接

只有图表必要性和内容逻辑已经确认、但仍待代码实现时，才在 md 对应位置使用：

```html
<!-- INSERT_CHART: [图表名称] -->
```

交接说明统一包含图表目的、类型、内容数据、分类或路径边界、图前导语、图后结论和与正文的映射，并引用按视觉发布规范锁定的同篇视觉约定；不同图表再补充：

| 类型 | 必需补充信息 |
|---|---|
| 对比表格 | 行列定义、单元格内容、badge 逻辑、底部注释 |
| 层级/闭环关系表 | 分层依据、真实环节与依赖、来源性质、边界说明 |
| 流程图/决策树 | 主节点与顺序、分叉条件、回退/暂停/终止、线型规则 |
| 二维定位图 | 两轴名称与端点、节点位置、从属关系 |

交接对象可以是代码 Agent 或人工实现者，不把某一工具名称写成规范前提。

## 占位符使用与交付规则

- `<!-- INSERT_CHART -->` 只用于**已经确认需要制作**、但尚待代码实现的图表，不用于记录“也许可以画图”的灵感。
- 可阅读初稿交付给用户前，每个占位符必须有明确结果：生成真实图表、改为 Markdown 表格，或直接删除。
- 只有用户明确要求“图表交接稿 / Claude Code 交接稿”时，才可以在交付文件中保留占位符，并需同时给出完整制作说明。
- 自查报告中只要仍有未决占位符，就不能声称最终格式问题已经全部完成。

## 草稿与发布文件的单一表示原则

- 内部草稿阶段可以保留已确认图表的 `<!-- INSERT_CHART -->` 占位符和 Markdown 表格，便于确认逻辑。
- 一旦发布文件已经包含完整 HTML/SVG 图表，应删除对应占位符和重复的 Markdown 表格。
- 同一图表在最终 md 中只能保留一种生效表示，避免重复渲染；这不禁止配套正文、无障碍文字说明或有明确递进作用的局部图。
- 如果表格只承担信息组织而不需要额外视觉编码，标准 Markdown 表格可以直接作为发布版本，不必为了“更像图表”强制转换为 HTML。
- 文章内嵌样式应保持局部作用域；如果多篇文章反复使用相同样式，应迁移至站点共享 CSS，而不是继续复制。

## 图表与正文的衔接规范

- 图表前：用一句话说明“接下来这张图展示了什么”，不要让图表突兀出现
- 图文可以共同表达同一结论：图提供结构、对照、场景或视觉记忆，文字解释原因、证据、条件和例外。允许必要信息重合；不强制图另造结论或正文删字，也不把同一来源的图文当成两份独立证据。
- 图表后：用一句话说明“图表揭示了什么结论”，再衔接下一节内容
- **相邻表格存在上下位关系时显式映射。** 如果前表给出机制 / 框架，后表用具体对象验证其中部分维度，需在后表出现前用正文说明“后表展开前表的哪一部分”；不要让读者仅凭列名猜两张表之间的关系。
- **全量对比表不要夹在同层比较之间。** 如果一张表先集中比较多个对象，后文再把这些对象分成若干组深入分析，表格应放在对象的最低必要定义之后、第一组分析之前；除非表格本身只总结前一组，否则不要插在两个并列比较组中间。
- 避免无组织地连续堆图；有清楚编号、图注或共同说明的前后对照与递进图组可以相邻呈现，不为形式要求插入空泛过渡。
- 图表底部注释用于说明分类边界，不承担新的核心论证；核心结论仍写在图表后的正文中

---

## 数据准确性要求

- 图表中的产品名称、版本号需要搜索验证，不能使用过时信息
- 分类标注（如“ASIC 的一种”）需要在正文中有对应解释
- 图表底部注释用于说明分类逻辑或特殊情况，不是可选项
- 自创框架的表格标题、列名与正文术语必须完全一致；正文修改概念后，图表需同步更新

## 发布前格式检查

- 每张表或图是否说明了它回答的问题、划分依据、来源性质和覆盖边界？
- 横向对比表中，同一行两侧是否确实回答同一个比较维度，而不是两个相关列表被机械并排？
- 如果同行对应关系不自明，是否增加“比较维度 / 维度 / 环节”首列？增加后是否还存在无必要的“说明”列？
- 对照表两侧是否保持相近抽象层级，并避免把“相对方向”误写成互斥全集？
- 同一篇文章中多张 Markdown 表格的表头、注释和强调方式是否一致？
- 是否按 [视觉发布规范](../VISUAL_GUIDE.md) 完成同篇图片一致性、当前图源与预览对应、实际显示尺寸的视觉验收，而不只是检查标签和文件存在？
- 是否存在两张列结构相同、只是在“抽象框架”和“案例应用”之间重复的表？如是，优先合并
- 流程图中的节点、分叉和回退是否与正文一致，是否因塞入角色和指标而信息过载？
- **若图表重绘/格式迁移**：是否以已确认旧图为基线，逐条核对条件、方向、节点层级与分支后果，确认没有以美观、横版或节点压缩之名悄悄改变逻辑？是否完成实际页面上的箭头/文字/移动端复核？
- 是否还残留 `<!-- INSERT_CHART -->` 占位符？除明确的图表交接稿外，发布稿和可阅读初稿都应删除或完成
- 是否检查了图文搭配的阅读收益，也反查了应图未图的位置？不能因文字仍可独立阅读就删图，也不能用无关配图填空。
- 是否同时存在 Markdown 与 HTML 两份相同表格？应只保留一份
- 表格注释是否错误使用 blockquote？应改为普通注释段落或专用样式
- HTML 标签是否闭合，深色模式是否可读，横向滚动是否正常
- 文章是否重复嵌入已有的全局样式？如是，迁移到共享 CSS
